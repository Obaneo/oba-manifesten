# B01.CH01.P05 — Reading guide: how this book applies the core (without repetition)

This paragraph defines the **reading route** and the **module boundaries** of Book 1. The purpose is to prevent duplication, synonym drift, and “re-definition by paraphrase”. Each chapter has a distinct function and can be used as a design module, but modules remain bound to the Kernel Spec and implemented through the Codex.

## B01.CH01.P05.S01 — How to use chapters as design modules (flows / R/B / caps / commons / ΔM)

Use the book modularly, depending on the task:

- **Flow classification and extraction diagnosis (P/E/C):**  
  Start with **CH02** for the flow-network model, attribution/consolidation, and the minimum measurement set needed to distinguish P/E/C.

- **Household order indicator and stability target (R/B ≥ α):**  
  Use **CH03** to define B→T→N→L→R, specify L-minimum boundaries, set α and reporting requirements, and prevent Goodhart-style manipulation.

- **Bounded accumulation (W-MAX / I-MAX):**  
  Use **CH04** for cap design variants, functional equivalents, transition regimes, and anti-avoidance. This chapter is the primary module for “cap effectiveness” and consolidation rules.

- **Parasitic-flow phase-down (E reduction as program):**  
  Use **CH05** to build the typology of parasitic flows, handle edge cases, pick instruments, and sequence interventions while preventing shift-based evasion.

- **Commons as base layer (ΔG and quality):**  
  Use **CH06** for commons regime design: rights, governance minima, maintenance and financing, substitution strategy, and measurement of growth and quality.

- **ΔM channeling and governance (ΔM→commons):**  
  Use **CH07** to specify allocation channels (allowed/forbidden), criteria, governance, anti-capture rails, banking interface constraints, and accountability dashboards.

- **State/fiscal/debt boundary conditions:**  
  Use **CH08** to define the state’s order role, fiscal base shifts, debt regimes, expenditure framing, legal anchoring, and the link to R/B stabilization.

- **Sector implementations and reusable canvas:**  
  Use **CH09** for reference designs in housing/energy/healthcare/platforms and for the reusable sector canvas and minimum per-sector metrics.

- **Measurement, audit, and publication discipline:**  
  Use **CH10** for the minimum dataset, consolidation logic, audit architecture, public reporting rules, versioning, and privacy/proportionality constraints.

- **Risk model and hard stops:**  
  Use **CH11** for avoidance/arbitrage/capture/regression patterns, shock stress tests, early-warning indicators, hard stops, and automatic correction mechanisms.

- **Capstone compatibility test:**  
  Use **CH12** as the final economic-layer check: pillar presence, minimum KPIs, red flags, and fork protocol.

If you are designing or reviewing an implementation, the default route is: **CH01 → CH02 → CH03 → CH04 → CH06 → CH07 → CH10 → CH12**, and then fold in CH05/CH08/CH09/CH11 as required by sector and risk.

## B01.CH01.P05.S02 — Linkage to Kernel Spec and Codex: where definitions and templates live

Book 1 is not the home of canonical meaning or implementation templates:

- **Kernel Spec (Book 0) is the canonical source of truth** for:
  - definitions and invariants (including B,T,N,L,R; P/E/C; caps; ΔM; commons),
  - core rules for compatibility and fail-closed behavior,
  - the semantic boundaries that must not drift.

- **Codex (Book X) is the implementation authority** for:
  - schemas and identifiers,
  - calculation rules and validators,
  - audit packs, logging formats, and dispute flows,
  - publication tables and revision/restatement procedures,
  - legal and procurement templates where applicable.

Therefore:
- Book 1 may **reference** and **operationalize** the Kernel Spec, but must not redefine it.
- Book 1 may specify what must be implemented and audited, but concrete “how-to” artifacts belong in the Codex.
- When an implementation claim is made, it should link to both:
  - the **Kernel definition set** being applied, and
  - the **Codex artifacts** (schemas/validators/audit packs) that make the claim auditable.
