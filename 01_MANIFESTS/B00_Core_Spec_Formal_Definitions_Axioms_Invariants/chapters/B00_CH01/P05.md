# B00.CH01.P05 Reading contract for implementation and evaluation

This paragraph defines the **reading contract**: the canonical rules for how the Core Spec is to be interpreted when building implementations and when evaluating OBA-claims. The reading contract is not “style guidance”; it is a set of enforcement defaults that prevents ambiguity from turning into privilege.

In particular, evaluation is not permitted to rely on intent, rhetoric, or claimed alignment. Only **canonical references + auditable evidence** can move an implementation from “non-conform by default” to “conform by proof.”

---

## B00.CH01.P05.S01 Conservative interpretation: in doubt, no expansion of power or scope

### Conservative interpretation (normative)
Where a canonical term, threshold, boundary, or conflict rule admits multiple plausible readings, the implementation and evaluator MUST choose the reading that **minimizes**:

- expansion of power (control, benefit, block),
- expansion of scope (what counts as exempt, excluded, or “outside”),
- creation of privileges (carve-outs, exceptions, discretion),
- reliance on untestable assumptions.

This is a functional conservatism: it is designed to prevent “interpretation-as-loophole.”

### Scope cannot be widened by implication
If the Core Spec does not explicitly include a concept, an actor class, an instrument, or a channel, an implementation MUST NOT claim inclusion via analogy or “spirit of the rule.” Inclusion requires explicit canonical anchoring (definition-set reference and mapping).

### No “best effort” equivalence
“Close enough” semantics are forbidden when they change enforceability. If a concept is only partially aligned, the correct outcome is **partial non-conformance** (scoped claim), not semantic stretching.

---

## B00.CH01.P05.S02 Fail-closed: unmeasurable or unauditable = non-conform until specified

### Fail-closed rule (normative)
Any component that is not **measurable**, **auditable**, and **reproducible** under the Core Spec’s evidence standards MUST be treated as **non-conform** until the missing observables, methods, and audit access are specified and delivered.

This applies to:
- P/E/C classifications,
- B/T/N/L/R computations and cohort profiles,
- W/I cap bases and consolidations (UBC),
- ΔM channels and beneficiaries,
- commons status and ΔG metrics,
- anti-omzeiling (requalification triggers and enforcement logs).

### Black boxes do not earn compatibility
If a result depends on proprietary models, undisclosed data transformations, or “trust me” metrics, the result cannot support an OBA-claim. “Open method, closed data” is allowed only if a third party can reproduce outputs using the same inputs under controlled audit access.

### Partial failure is partial stop
Fail-closed is granular: if one module is unauditable, only that module is non-conform—*unless* it undermines invariants elsewhere (e.g., unauditable ΔM leakage that invalidates W/I caps or R/B outcomes). In such cases, the dependent claims are also non-conform.

---

## B00.CH01.P05.S03 Evidence and measurement duty: claims require reproducible testing

### Burden of proof (normative)
The burden of proof lies on the claimant. Anyone asserting “OBA-conform” or “OBA-compatible” MUST provide:

1. the **definitieset-ID and version** used,
2. an explicit **mapping** from implementation objects to canonical objects (terms, quantities, roles),
3. a **test plan**: which invariants are tested, how, and with what thresholds,
4. a **reproducible measurement pipeline**: input → transformation → outputs.

### Reproducibility requirement
A competent independent evaluator MUST be able to reproduce the claimed results within declared uncertainty bounds using:
- the same input datasets (or audit-access substitutes),
- the same transformation logic (versioned),
- the same parameter regime (declared).

If reproduction fails, the claim fails—unless the claimant can demonstrate a documented measurement defect and issue a restatement under the versioning discipline.

### Evidence hierarchy
Where multiple evidence streams exist (microdata, admin data, audits, sampling), the evaluator MUST prefer evidence that is:
- closer to the underlying transaction/contract reality,
- less gameable,
- more traceable,
- and independently attestable.

### No narrative substitution
Mechanism claims (“this improves R/B,” “this reduces E,” “this builds commons”) require explicit causal chains and supporting tests; narrative plausibility is not evidence.

## B00.CH01.P05.S04 Minimum documentation: what every implementation must publish to carry an “OBA claim”

An implementation may only carry a public OBA-claim if it publishes a **minimum documentation bundle** sufficient for independent verification. This bundle is required even if local law restricts raw-data publication; in that case, the bundle must include audit-access procedures and privacy-preserving disclosure methods.

### A. Canon reference and scope statement
- Definitieset-ID + version (Core Spec release reference).
- Compatibility label claimed (conform / compatible / inspired) and scope boundaries.
- Declared modules covered (P/E/C, R/B, caps, ΔM, commons, anti-omzeiling) and excluded parts (with justification).

### B. Object and data mapping
- Mapping from real-world entities/roles to canonical **actor/position/role** model (incl. UBC logic).
- Data dictionary: fields used, units, time index, cohort dimensions.
- Mapping from contracts/flows/channels to canonical flow objects and classifications.

### C. Methods and parameters
- Measurement procedures for core observables (P/E/C, B/T/L/R, W/I bases, ΔM channel logs, ΔG metrics).
- Parameter regime used (e.g., α, cap levels, baseline access quantities, indexation choices) with change control.
- Uncertainty reporting: intervals, sensitivities, and conservative defaults applied.

### D. Tests and results
- Invariant checklist and test suite results (pass/fail + evidence links).
- Distributional outputs where required (e.g., R/B profiles, under-α share, tails).
- Anti-omzeiling monitoring summary: triggers, findings, requalifications (aggregated if needed).

### E. Auditability and governance
- Audit trail description: lineage, logging, version control, immutability guarantees.
- Independent attestation (where required) and dispute/appeal procedure.
- Publication integrity: immutable releases, hashes/signatures where applicable, changelog policy.

### F. Minimal public artifact rule
At minimum, the public must be able to see:
- what was claimed,
- which canon was used,
- what was measured,
- what tests were run,
- and what failed or remains unknown.

If any of these elements are missing, the correct label is **non-conform** (or at most **OBA-inspired** with no compatibility claim).
