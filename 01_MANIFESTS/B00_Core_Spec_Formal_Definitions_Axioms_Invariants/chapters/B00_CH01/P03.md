# B00.CH01.P03 Definition-set identity and canonical reference

This paragraph defines how the canon is *addressed*, *versioned*, and *cited* without ambiguity. OBA compatibility requires that any claim, measurement, rule, or implementation can be traced to a specific **definition-set identity** and a specific **reference unit** within that set. The Core Spec therefore treats identifiers and registries as normative infrastructure: if identity and reference are sloppy, enforcement collapses into interpretation.

The objective is **semantic unicity**: at any point in time, a reader must be able to answer “*Which canon are we talking about?*” and “*Which exact rule is being invoked?*” with machine-checkable precision.

---

## B00.CH01.P03.S01 Definition-set ID: format and scope (global, sector, jurisdiction)

A **Definition-set ID** is the canonical handle for a particular set of rules (definitions, axioms, invariants, conflict rules) under which an OBA claim is made. It is mandatory metadata for:

- public claims (“OBA-conform/compatible/inspired”),
- audits and compliance reports,
- datasets and derived metrics,
- and any Codex/Standards artifact asserting traceability to canon.

### Format requirements
A Definition-set ID MUST be:
- **globally unique** within the OBA namespace,
- **stable** across time (identity does not change when content changes; versions do),
- **composable** with scope and version information.

Minimum fields (conceptual, not necessarily textual in one string):
1. **Book/Domain** (e.g., `B00`)
2. **Spec scope**: `GLOBAL` / `SECTOR` / `JURISDICTION`
3. **Scope name** (if not global): sector key or jurisdiction key
4. **Version** (semantic version; see version governance)
5. **Integrity reference** (hash/signature pointer to immutable release artifact)

Example shapes (illustrative):
- `B00.GLOBAL@1.2.0`
- `B00.SECTOR:HOUSING@0.9.3`
- `B00.JURISDICTION:NL@1.0.1`

### Scope constraints
- **Global** definition sets define kernel semantics and invariants.
- **Sector** definition sets MAY parameterize within allowed ranges and MAY add sector-specific *derived* procedures, but MUST NOT redefine kernel meaning.
- **Jurisdiction** definition sets MAY set parameters and institutional procedures, but MUST NOT violate invariants and MUST remain traceable to the global kernel.

### Compatibility rule
Any non-global definition set MUST declare:
- its parent (upstream) definition set ID,
- the list of parameters it instantiates,
- and an explicit statement of invariant preservation (or explicit fork declaration where invariants are broken).

If a scope document introduces new semantics without a declared parent link and invariant mapping, it is **non-canonical** by default and **cannot** carry an OBA compatibility label.

## B00.CH01.P03.S02 Canonical term registries (terms, symbols, quantities)

To prevent synonym drift and “same word, different meaning” failure modes, the Core Spec requires canonical registries. These registries are not documentation niceties; they are enforcement primitives.

### Registry classes
The canon maintains at least three registries:

1. **Term registry**  
   - Canonical spelling, allowed aliases (if any), and forbidden synonyms.
   - Term definition pointers (paragraph IDs where meaning is defined).
   - Deprecation status (active / discouraged / deprecated / removed).

2. **Symbol registry**  
   - Canonical symbols (e.g., `B,T,N,L,R`, `P/E/C`, `W-MAX/I-MAX`, `ΔM`, `ΔG`).
   - Type signatures and interpretation constraints (stock/flow; time index requirements).
   - Prohibited rebindings (no local symbol redefinition).

3. **Quantity registry**  
   - For measurable quantities: type, unit, domain, admissible aggregation operators, and required metadata.
   - Measurement method references (where measurement is specified or constrained).
   - Required uncertainty representation (e.g., interval, band, confidence class).

### Registry rules (normative)
- Every normative term, symbol, and quantity used in any canonical paragraph MUST be present in its registry.
- Any derived artifact (Books, Codex, Standards, sector/jurisdiction documents) MUST reference registry entries rather than introducing new definitions by prose.
- If an implementation introduces a term/symbol/quantity not in the registries, that element is **non-canonical** and cannot be used to justify an OBA claim unless and until registered via the change procedure.

## B00.CH01.P03.S03 Normative distinction: definitions vs parameters vs examples

A persistent source of drift is category confusion: treating examples as rules, treating parameters as semantics, or treating narrative as definitional. The Core Spec therefore enforces a strict normative taxonomy.

### (1) Definitions (semantic meaning)
**Definitions** specify what something *is* within OBA and how it must be interpreted. They are non-negotiable within a compatibility class and can change only through versioned governance.

Examples:
- what counts as `E` versus `P`,
- what constitutes “block power,”
- the identity `R = (B − T) − L`,
- the notion of traceability for `ΔM`.

### (2) Parameters (configurable values within rails)
**Parameters** are values or thresholds selected within allowed bounds that do not change meaning, only instantiation. Parameters MUST:
- have explicit domains and allowed ranges (or allowed procedures),
- have a change procedure,
- and never be introduced implicitly.

Examples:
- α (order threshold) value(s),
- cap levels, indexation schemes,
- baseline access volumes for commons.

A parameter choice that effectively changes meaning (e.g., nullifying an invariant) is a **semantic breach** and requires a major change / fork declaration.

### (3) Examples (illustrative, non-binding)
**Examples** are permitted to aid understanding, but they are never normative unless explicitly promoted. Examples MUST be labeled as such and MUST NOT be relied upon as a compliance basis.

### Priority rule under conflict
If a reader can interpret a statement as either an example or a definition, it MUST be treated as **non-normative** unless explicitly declared definitional and registered/cited accordingly. This is an anti-washing rule: ambiguity cannot generate authority.

## B00.CH01.P03.S04 Reference units: paragraph IDs and citation rules

The atom of canonical reference is the **paragraph unit**, identified by a stable ID. This enables precise citation, machine validation, and dispute resolution without “quote wars.”

### Reference unit model
- Canon is referenced by paragraph IDs and subparagraph IDs (e.g., `B00.CH01.P03.S04`).
- IDs MUST be stable across minor editorial changes; meaning-changing edits require versioned releases and documented diffs.
- Canonical meaning is defined by the *content of the referenced release artifact* (hash/signature), not by mutable repository state.

### Citation rules (normative)
Any OBA-relevant claim MUST cite:
1. **Definition-set ID + version** (which canon)
2. **Paragraph IDs** supporting the claim (which rules)
3. **Where applicable**: the measurement method or standard (how it was evaluated)

Minimum acceptable citation form (conceptual):
- `Definition-set: B00.GLOBAL@1.0.0 (hash …)`
- `Cites: B00.CH03.P03.S01, B00.CH04.P02.S05, B00.CH12.P04.S01`

### No “free interpretation” rule
If a claim cannot be grounded in paragraph-level citations, it is not a canonical claim. It may be commentary, proposal, or “OBA-inspired,” but it cannot be presented as “OBA-conform/compatible.”

### Dispute anchoring
All disputes over meaning are resolved by:
- the cited paragraph IDs,
- within the cited definition-set version,
- under the canonical conflict rules.
This prevents retroactive semantic substitution (“that’s not what we meant”) and forces correction through transparent version governance.
