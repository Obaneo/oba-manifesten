# B00.CH01.P02 Scope delimitation and layer model

This paragraph defines the **scope boundary** of the Core Spec and the **layer model** that governs how other artifacts (Books, Codex, Standards, implementations, commentary) may relate to it. The goal is to prevent category errors—e.g., treating narrative as canon, treating implementation details as semantics, or allowing sector documents to “backdoor” new meaning.

The Core Spec is the **kernel layer**: it contains only what must be stable, portable, and testable across contexts. Everything else is downstream and must reference canon rather than mutate it.

---

## B00.CH01.P02.S01 What belongs inside the Core Spec (definitions, axioms, invariants, conflict rules)

Only content that is required to make OBA **semantically closed and enforceable** belongs in the Core Spec. This includes four classes of normative material:

### (1) Definitions
Canonical definitions specify:
- terms, symbols, quantities, object types, and relationship tests,
- type/unit/domain/time-index requirements,
- and minimum metadata required for classification and evaluation.

A Core Spec definition is not “descriptive”; it is an interface contract. If an implementation claims to measure or enforce X, X must be definable in the Core Spec.

### (2) Axioms
Axioms are foundational statements that are assumed true within the system and used to derive invariants and tests. They must be minimal and non-redundant. Examples of axiom classes (not implementations) include:
- substance-over-form evaluation,
- default conservatism under uncertainty (where appropriate),
- and traceability requirements for claims about state change.

### (3) Invariants
Invariants are non-negotiable properties of OBA that **MUST hold** across any conforming implementation. Invariants:
- constrain permissible parameter choices,
- block “OBA-by-branding” interpretations,
- and define what it means to break compatibility (fork conditions).

### (4) Conflict rules and evaluation defaults
Because real systems produce ambiguity and collisions (data gaps, overlapping regimes, competing interpretations), the Core Spec must specify:
- hierarchy rules (which source wins),
- conflict resolution rules (how to decide when two rules apply),
- and default outcomes (fail-closed vs. fail-open) when required conditions are unmet.

**In-scope requirements (binding).**
- Anything necessary to define, test, audit, and enforce OBA claims **MUST** be representable as definitions/axioms/invariants/conflict rules in the Core Spec.
- Any ambiguity that could expand discretion **MUST** be closed by canonical defaults or explicit out-of-scope declarations.

## B00.CH01.P02.S02 What does not belong in the Core Spec (explanatory text, casework, implementation choices)

The Core Spec explicitly excludes content that increases interpretive degrees of freedom, depends on local context, or belongs to downstream engineering/policy design. Excluded classes include:

### (1) Explanatory or motivational narrative
Intuition, history, rhetoric, political framing, and persuasive argumentation are valuable for onboarding and legitimacy, but they are not canon. They do not determine meaning and cannot override formal rules.

### (2) Casework and sector-specific adjudication
Examples, sector stories, “typical patterns,” and applied interpretations may be published, but they remain non-canonical unless explicitly ratified into canon via a change procedure. Casework is inherently incomplete and therefore unsafe as a semantic source of truth.

### (3) Implementation choices and institutional architecture
Concrete choices such as:
- database schemas,
- software stack decisions,
- organizational charts,
- procurement rules,
- enforcement agency designs,
- and UI/UX details
do not belong in the kernel. These belong to derived layers (Codex/Standards) and to jurisdiction/sector implementations.

### (4) Parameter values (except as bounded ranges and governance rules)
The Core Spec may define parameter *names*, allowed *ranges*, and *change procedures*, but generally not jurisdiction-specific numerical values. Fixing values in canon increases fork pressure and undermines portability.

**Out-of-scope requirements (binding).**
- Narrative, casework, and engineering detail **MUST NOT** be treated as canonical authority.
- Sector documents and implementations **MUST NOT** import non-canonical material back into the kernel by implication (“as understood in practice”) or by redefining terms.

## B00.CH01.P02.S03 Relation to Books 1–4 (reference contract: refer, do not re-define)

Books 1–4 are downstream layers intended for explanation, expansion, pedagogy, and applied reasoning. Their role is to make canon usable, not to create it.

### Reference contract
- Books 1–4 **MUST** reference canonical paragraph IDs and definitions when discussing core concepts.
- Books 1–4 **MUST NOT** redefine canonical terms, symbols, quantities, or tests.
- Where books introduce additional concepts, those concepts are non-canonical unless (and until) they are promoted into canon via the change discipline.

### Handling divergence
If a book’s phrasing conflicts with canon:
- the Core Spec governs,
- the book is treated as commentary,
- and the inconsistency must be corrected by errata/restatement (without semantic change) or by a formal versioned change (with explicit semantic impact).

### Why this separation exists
Books optimize for comprehension and adoption. The Core Spec optimizes for enforcement and semantic stability. Collapsing the two layers causes drift: narrative starts to “act like” rules.

**Binding requirements.**
- Any statement in Books 1–4 that purports to be normative **MUST** be traceable to Core Spec clauses, or it is non-canonical by default.
- Any local glossary in Books 1–4 **MUST** be a pointer to canon, not a redefinition.

## B00.CH01.P02.S04 Relation to Codex/Standards (engineering artefacts as derived implementation layer)

Codex/Standards sit between canon and real-world implementations. They convert canonical requirements into **engineering-grade artifacts** (schemas, test harnesses, reference procedures, compliance checklists) without changing meaning.

### Role of Codex/Standards
Codex/Standards MAY provide:
- reference data models and object schemas aligned to canonical definitions,
- validation rules and conformance tests,
- audit logging formats and reproducibility checklists,
- interoperability specs (interfaces, portability requirements),
- and reference implementations (as examples), clearly labeled.

### Constraints (derived, not sovereign)
Codex/Standards are authoritative only insofar as they are **derived from** canon:
- They **MUST** cite the canonical clauses they implement.
- They **MUST NOT** introduce new semantics, exceptions, or scope expansions.
- When Codex/Standards and canon disagree, canon wins and the derived artifact must be updated.

### Evidence interface
Codex/Standards are the expected vehicle for specifying “how to show compliance” (evidence production), while the Core Spec defines “what compliance means.” This preserves kernel stability while enabling practical enforcement.

**Binding requirements.**
- Derived standards **MUST** be non-semantic: they operationalize canon, they do not redefine it.
- Any derived artifact that materially changes evaluation outcomes relative to canon is **non-conforming** and triggers a compatibility dispute (and potentially a fork if insisted upon).
