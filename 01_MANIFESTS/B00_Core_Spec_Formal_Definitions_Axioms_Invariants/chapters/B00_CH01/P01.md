# B00.CH01.P01 Purpose and Function of the Core Spec

The **Core Spec** is the normative kernel of OBA. Its purpose is to *fix meaning*, *bound permissible variation*, and *prevent semantic drift* across time, jurisdictions, sectors, and implementations. It does so by specifying a minimal set of **formal definitions, axioms, invariants, and conflict rules** that together form the canonical basis for any OBA claim.

The Core Spec is intentionally compact relative to the full OBA corpus: it is not meant to contain narrative motivation, persuasive rhetoric, or sector-specific casework. Its job is to make OBA **semantically closed, testable, auditable, and enforceable**—so that “OBA-compatible” cannot be asserted by branding or interpretation alone.

**Normative language.** Within the Core Spec, **MUST / MUST NOT / SHALL / REQUIRED** denote binding requirements. **SHOULD / SHOULD NOT** denote strong recommendations. **MAY** denotes permission within stated constraints.

---

## B00.CH01.P01.S01 Core Spec as canonical source of truth

The Core Spec is the **canonical source of truth** for OBA. “Canonical” means that the Core Spec is the highest authority for meaning: where other documents differ, the Core Spec governs, and conflicts are resolved using Core Spec conflict rules.

Canon status has three operational consequences:

1. **Authoritative semantics.** Canonical terms and symbols have stable, non-local meaning. Implementations do not “reinterpret” them; they either conform or they do not.
2. **Citeability.** Every OBA-critical claim is traceable to specific paragraph IDs (and a version), enabling independent verification and preventing “semantic laundering.”
3. **Portability.** OBA can be implemented across sectors and jurisdictions without redefining the kernel; local documents may apply and parameterize, but may not overwrite canonical meaning.

**Canonical obligations.**
- A canonical term register (terms/symbols/quantities) is not optional; it is the binding interface between text and evaluation.
- Canonical meaning must remain stable under restatement: improved phrasing is allowed only if semantics is preserved and traceable.

**Conformance requirements (binding).**
- Implementations **MUST NOT** redefine canonical terms, symbols, or object attributes.
- Any OBA claim **MUST** cite the applicable Core Spec paragraph ID(s) and the referenced release/version.
- When sources conflict, interpretation **MUST** follow the Core Spec hierarchy (Core Spec first) and the Core Spec conflict rules. Where conflict cannot be resolved canonically, evaluation **MUST** fail closed.

## B00.CH01.P01.S02 Objective: semantic closure, testability, enforceability

The Core Spec is designed to remove “interpretation debt.” If OBA’s core concepts require shared cultural context or discretionary judgment to evaluate, the system becomes unfalsifiable and therefore non-enforceable. The Core Spec therefore targets three properties:

### 1) Semantic closure
Semantic closure means that OBA’s critical reasoning does not depend on unstated assumptions. For any OBA-critical claim:
- the relevant terms are defined canonically, or
- the claim is declared **out of scope** for conformance until canonically specified.

Semantic closure does not require that every edge case is fully enumerated. It requires that the Core Spec defines: (i) what is known, (ii) what is unknown, and (iii) what the default evaluation outcome is when unknown.

### 2) Testability
A claim is testable when an independent party can determine whether it holds using the published definitions, procedures, and declared inputs. Testability implies:
- explicit observables (what must be measured, logged, or disclosed),
- reproducible procedures (how evaluation is performed),
- and well-defined handling of uncertainty (confidence bands, conservative defaults).

### 3) Enforceability
Enforceability requires that conformance is not a matter of persuasion. It must reduce to predicates that can be checked (pass/fail, or compliance within bounds), paired with:
- minimum evidence requirements,
- auditability requirements (traceable reasoning and lineage),
- and defined consequences for non-conformance under the compatibility regime.

**Conformance requirements (binding).**
- OBA-critical terms and rules **MUST** be semantically closed under the Core Spec (no hidden dependencies on commentary or narrative).
- OBA claims **MUST** be testable by an independent evaluator using the declared inputs and published procedures.
- Where required evidence is missing, non-reproducible, or unauditable, the evaluation **MUST** default to **non-conform** (fail closed) until canonically specified.

## B00.CH01.P01.S03 Objective: anti-washing and anti-drift (preventing fake alignment)

The Core Spec treats “washing” and “drift” as adversarial pressures, not as accidents.

### Anti-washing
**OBA-washing** is any attempt to claim alignment while preserving the behaviors or power structures OBA constrains. Common washing vectors include:
- **Vagueness laundering:** using morally appealing but undefined terms (“commons,” “fair,” “stability”) to evade constraints.
- **Selective adoption:** adopting slogans while omitting invariants, conflict rules, or evidence requirements.
- **Relabeling:** reclassifying extractive structures as productive or commons without a traceable rule-based justification.
- **Opacity:** using black-box methods (uninspectable models, proprietary metrics) to assert compliance without audit trails.

The Core Spec counters washing by making conformance depend on **traceable semantics + reproducible evaluation**, rather than intent.

### Anti-drift
**Semantic drift** is gradual meaning change without explicit, versioned canonical change. Drift can occur via:
- shadow definitions (local glossaries that override canon),
- synonym substitution (renaming a concept to smuggle a new meaning),
- “clarifications” that silently change thresholds or scope,
- or treating commentary/implementation notes as normative.

The Core Spec prevents drift by requiring:
- strict separation between canon and non-canon,
- an explicit interpretation hierarchy,
- versioned releases and change discipline,
- and conservative defaults that penalize ambiguity rather than rewarding it.

**Conformance requirements (binding).**
- Shadow definitions and synonym substitution **MUST NOT** override canonical terms.
- Black-box methods **MUST NOT** be used to assert OBA-critical classifications or outcomes where auditability is required.
- Any change that materially affects meaning (definitions, axioms, invariants, conflict rules, or binding parameters) **MUST** follow the canonical change procedure; otherwise it is **non-canonical** and **MUST** be treated as drift/washing.
- Where ambiguity would expand discretion, interpretation **MUST** be conservative and **MUST** not expand scope or authority beyond canon.

## B00.CH01.P01.S04 Non-goals: rhetoric, political platform, sector storytelling

The Core Spec is intentionally not optimized for persuasion, ideology, or narrative richness. Those may exist elsewhere in the OBA corpus, but they are not part of the canonical kernel unless explicitly ratified.

### Non-goal: rhetoric
The Core Spec is not a manifesto. Rhetoric tends to increase interpretive degrees of freedom; the Core Spec is built to reduce them. Persuasive framing may accompany the Core Spec, but must remain clearly non-canonical.

### Non-goal: political program
The Core Spec does not prescribe a party platform or legislative roadmap. Political strategies may reference the Core Spec, but are not part of the kernel. The Core Spec specifies what it means to be OBA-conform; it does not prescribe who must implement it or how political coalitions should form.

### Non-goal: sector storytelling and casework
Sector narratives and case studies are useful for comprehension and adoption, but they are not a source of canonical meaning. Sector documents may apply canon and fill permitted parameters, but may not redefine terms or weaken invariants.

### Non-goal: implementation choices (except evidence constraints)
The Core Spec does not mandate specific software architectures, procurement models, or institutional designs—except where specific artifacts are required as evidence for auditability (e.g., logs, registers, disclosed procedures). Engineering choices belong in derived standards/codices, not in the kernel.

**Conformance requirements (binding).**
- Narrative, motivational, rhetorical, or political text **MUST NOT** be treated as canonical authority.
- Sector-specific documents **MAY** exist, but **MUST** remain subordinate: they may apply canon and set allowed parameters, but **MUST NOT** redefine canon.
- Implementation guidance is **non-canonical** unless explicitly adopted through the canonical change procedure and framed as an evidence constraint.
