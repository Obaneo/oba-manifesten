# B00.CH01.P07 Publication and integrity rules

This paragraph defines the publication and integrity requirements for the canon and for any artefact that claims compatibility with it. The intent is to make the canon **publicly citable**, **tamper-evident**, and **operationally enforceable**, and to make “OBA claims” auditable rather than rhetorical.

A release that is not accessible, not archivable, or not integrity-verifiable is **non-canonical for enforcement purposes**, regardless of its authorship.

---

## B00.CH01.P07.S01 Publication requirements: accessibility, archiving, hash/signature, immutable releases

### Accessibility (public retrievability)
Each canonical release MUST be retrievable by third parties without private access arrangements. At minimum:
- a stable canonical distribution point (primary),
- at least one independent mirror,
- a human-readable rendering and a machine-readable form (where feasible),
- an index/manifest that enumerates all included artefacts by ID.

“Available on request” is non-compliant.

### Archiving (long-term citability)
Each release MUST be archived such that it remains retrievable for multi-year audit horizons. Archiving MUST include:
- an immutable snapshot (e.g., tagged release artifact),
- an archive identifier (date + version + hash),
- explicit retention guarantees or at least redundant archiving on independent infrastructure.

### Integrity (tamper evidence and provenance)
Each release MUST provide integrity verification material:
- cryptographic hashes for the full release bundle and for key files (manifest, registries),
- a digital signature from the canonical registrar/ratifier authority (or a published signing policy),
- a verification instruction that a third party can follow without proprietary tooling.

If signatures are not used, an explicit alternative integrity mechanism MUST exist; otherwise the release is treated as non-enforceable.

### Immutable releases (no silent edits)
Canonical releases MUST be immutable. Any change—no matter how small—requires a new release identifier (PATCH/MINOR/MAJOR per CH01.P06). Mutable “living docs” are allowed only as **non-canonical working drafts** and MUST be clearly labeled as such.

## B00.CH01.P07.S02 Transparency requirements: changelog, rationale, impact analysis on invariants

### Changelog (mandatory and structured)
Every release MUST include a changelog that is complete and machine-citable. Minimum fields:
- version (MAJOR.MINOR.PATCH), release date/time, release ID/hash,
- affected paragraph IDs and registries,
- change class per change (PATCH/MINOR/MAJOR),
- summary of edits and rationale,
- links/references to proposals, reviews, audits, and ratification record.

Absence of a changelog implies **non-canonical status**.

### Rationale (no “because we said so”)
Any change that alters interpretation boundaries, enforcement burden, or measurement expectations MUST provide rationale that is testable and contestable. Rationale must be framed in terms of:
- invariant preservation or correction,
- auditability and enforcement capability,
- anti-omzeiling coverage,
- interoperability implications.

### Impact analysis on invariants (required for MINOR/MAJOR; recommended for PATCH)
For MINOR and MAJOR releases, an impact analysis MUST state:
- which invariants are affected (or explicitly unaffected),
- expected directional effects on core outputs (e.g., classification or compliance outcomes),
- changes to evidence standards and observables,
- migration and bridging requirements for comparability across versions,
- known failure modes and how they will be monitored.

If the impact on invariants cannot be stated, the change is not ready for canonical publication.

## B00.CH01.P07.S03 Fork protocol: name usage, compatibility labels, boundaries

### Fork definition (normative)
A “fork” exists when an implementation or document set:
- changes an invariant,
- changes canonical meanings of terms/symbols,
- weakens auditability/evidence requirements,
- introduces exceptions that materially alter enforcement outcomes,
- or otherwise breaks compatibility tests.

Fork status is a classification, not an insult: it is a boundary for truth in claims.

### Name usage (anti-washing)
The label “OBA” (or “Core Spec”) MUST NOT be used without an explicit compatibility status bound to a definitieset-ID and version.

Permitted public labels (canonical):
- **OBA-conform**: satisfies all invariants and evidence/audit requirements for the claimed version.
- **OBA-compatible**: satisfies core invariants but lacks explicitly designated optional modules (must enumerate missing modules).
- **OBA-inspired**: draws ideas but makes no compatibility claim; must not imply equivalence.
- **Non-conform / Fork**: breaks invariants, auditability, or conflict rules; must not be marketed as conform/compatible.

### Boundary declaration (required for forks)
Any fork MUST publish:
- which invariants changed and why,
- a compatibility statement (“not compatible with version X.Y.Z”),
- a mapping/bridge plan if interoperability is claimed,
- a distinct name or qualifier that prevents confusion in citations and audits.

If a fork uses OBA terminology, it MUST mark all divergences explicitly. “Same words, different meaning” is prohibited.

## B00.CH01.P07.S04 Interoperability: mapping to sector canvases and jurisdiction profiles

### Derived artefacts must reference, not redefine
Sector canvases and jurisdiction profiles are derived layers. They MAY:
- instantiate parameters within allowed ranges,
- select optional modules explicitly,
- provide operationalization constraints and data schemas,
- add local procedural requirements.

They MUST NOT:
- redefine canonical terms,
- alter invariants,
- introduce silent exceptions,
- replace evidence standards with proprietary substitutes.

### Mapping requirements (bridging documents)
Any derived artefact MUST provide a mapping that a third party can follow:
- which canon version it targets (definitieset-ID + version),
- which parameters are set and their values,
- which optional modules are enabled/disabled,
- local terms mapped to canonical terms (one-way mapping; canon remains the source of truth),
- jurisdiction-specific legal constructs mapped to canonical object relations (control/benefit/block, etc.).

### Cross-jurisdiction comparability (minimum)
Where comparisons across jurisdictions/sectors are expected, derived artefacts MUST ensure:
- identical canonical metrics are still computed (even if supplemented locally),
- any local deviations are flagged as “non-comparable unless bridged,”
- the bridge includes conversion rules and known uncertainty.

### Hard stop: no black-box interoperability
Interoperability claims are invalid if the mapping is not reproducible. If a sector canvas/jurisdiction profile requires non-public logic, unverifiable data transformations, or hidden thresholds, it cannot carry an OBA compatibility label.
