# B00.CH01.P04 Anti-drift rules (semantic discipline)

This paragraph defines the semantic discipline that makes the Core Spec enforceable over time. “Drift” is any change in meaning that occurs without an explicit versioned change procedure. Drift is more dangerous than open disagreement: it allows actors to claim alignment while quietly mutating the underlying semantics (“OBA-washing by interpretation”).

Anti-drift rules therefore constrain *how* language may be used, *where* meaning may be introduced, and *which sources* may be invoked to resolve ambiguity. The Core Spec treats semantic discipline as an operational security layer for governance: if semantics can be bent, every invariant becomes optional in practice.

---

## B00.CH01.P04.S01 Ban on shadow definitions and synonym substitution

### Shadow definitions (forbidden)
A **shadow definition** is any statement that introduces or alters the meaning of a canonical term/symbol/quantity outside the designated canonical definition units (Core Spec definitional paragraphs and registered definitional updates).

Shadow definitions include, but are not limited to:
- redefining a term in a local document “for clarity,”
- introducing a “working definition” that differs from canon,
- replacing a canonical term with a near-synonym that subtly changes scope,
- embedding new meaning inside examples, footnotes, marketing, or UI labels.

**Rule:** Implementations MUST *reference* canonical definitions; they MUST NOT re-define them. If re-definition is required, it is a **major change** and must follow the change procedure and naming rules (fork discipline).

### Synonym substitution (restricted)
Synonyms are a primary drift vector because they allow meaning to move while appearing linguistically harmless.

**Rule:** Canonical terms are treated as *technical tokens*, not narrative prose. Substitution is allowed only if:
1. the alias is explicitly registered in the **term registry** as an allowed alias, and  
2. the alias is mapped injectively to the same canonical meaning, and  
3. the usage includes an explicit pointer to the canonical term at first use (in the same artifact).

Otherwise, synonym substitution is **non-conform**.

### Anti-ambiguity clause
When in doubt whether a phrase constitutes a shadow definition, the classification MUST default to “shadow definition” (conservative). Drift prevention is fail-closed by design.

## B00.CH01.P04.S02 Hierarchy of interpretation sources (Core Spec > Codex > books > commentary)

When documents conflict, enforcement requires a deterministic resolution order. The Core Spec therefore defines a strict source hierarchy for interpretation.

### Source hierarchy (normative)
1. **Core Spec (Kernspec / B00)**  
   Definitions, axioms, invariants, conflict rules, and the canonical registries.
2. **Codex / Standards**  
   Engineering artifacts that implement or operationalize the Core Spec (schemas, test suites, audit formats). They may add *derived* constraints, but cannot override Core Spec semantics.
3. **Books (1–4)**  
   Expository expansion, motivation, casework, sector narratives, and interpretation guidance. Books must refer to Core Spec terms; they do not define them.
4. **Commentary / marketing / presentations / informal notes**  
   Non-normative by default.

### Interpretation rule
Ambiguity MUST be resolved by the highest-ranked applicable source. Lower-ranked sources may clarify *how to apply* a rule, but cannot change *what the rule means*.

### Non-citation rule
If an argument relies on commentary while contradicting a higher-ranked source, it is invalid for any OBA compatibility claim.

### Fail-closed on conflict
If two sources conflict and neither contains an explicit conflict-resolution rule applicable to the case, the interpretation MUST select the **stricter** reading with respect to:
- restricting power,
- restricting scope expansion,
- increasing auditability requirements,
- and preventing privilege creation via ambiguity.

(“Strict” here is functional: it is the reading least likely to enable E, laundering, or bypass.)

## B00.CH01.P04.S03 Consistency requirement: symbols and terms are injective (one term → one meaning)

Semantic stability requires that tokens map cleanly to meanings. The Core Spec enforces *injective semantics*: each canonical term or symbol refers to exactly one meaning within a given definition-set version.

### Injectivity rules (normative)
Within a given definition-set version:

1. **One token → one meaning**  
   A canonical term/symbol MUST NOT denote multiple concepts depending on context, sector, or audience. Context may parameterize values or scope, but must not alter meaning.

2. **One meaning → one token (preferred for kernel terms)**  
   Core kernel meanings SHOULD have a single canonical token; aliases are allowed only when strictly mapped and registry-managed (see P03 registries).

3. **No local rebinding**  
   Documents MUST NOT redefine a canonical symbol for local convenience (e.g., redefining `R` to mean “resilience” in prose). Canonical symbols are reserved.

4. **Typed usage**  
   Where types are defined (stock/flow, time index, units), usage MUST respect those types. A meaning-preserving “abuse of notation” is forbidden when it can alter interpretation or comparability.

### Drift detection heuristic (normative posture)
If a token appears to be used with two different meanings in an artifact set, the implementation is presumed **non-conform** until it demonstrates:
- explicit registry references,
- consistent type/unit/time-index compliance,
- and paragraph-level citations grounding each use.

## B00.CH01.P04.S04 Bridge texts / restatements: allowed when explicitly non-canonical and traceable

The canon may need “bridges” to help readers migrate across versions or across forks, and “restatements” to improve readability. These are permitted only under strict labeling and traceability to prevent shadow canon formation.

### Restatements (allowed, non-normative by default)
A **restatement** is a rephrasing intended to be meaning-preserving.

Rules:
- Restatements MUST be explicitly labeled as **restatement** and MUST include the source paragraph IDs they restate.
- Restatements MUST NOT be cited as the primary authority in place of the canonical paragraph; citations must point to canon.
- If a restatement is discovered to change meaning, it is treated as a **semantic change** and triggers major-change handling (or removal).

### Bridging texts (allowed, non-canonical)
A **bridge** is a mapping document between:
- version A → version B (within the same canon lineage), or
- fork X → fork Y (cross-lineage mapping).

Rules:
- Bridges MUST declare both endpoints (definition-set IDs + versions) and MUST define a mapping function or correspondence table for affected terms/parameters/metrics.
- Bridges MUST declare whether invariants are preserved or violated under the mapping.
- Bridges are *interpretation aids*, not sources of truth. They cannot override either endpoint canon.

### Prohibition on “shadow canon”
A bridge or restatement that becomes the de facto reference point (used instead of canon) constitutes drift.

**Rule:** Any implementation that cites a bridge/restate text without also citing the underlying canonical paragraph IDs is non-conform for purposes of OBA compatibility claims.

### Traceability requirement
Every bridge/restate artifact MUST be traceable via:
- stable identifiers,
- versioned publication,
- and an audit trail linking the artifact to the specific canonical releases it maps.

Without traceability, the artifact is treated as commentary and has no normative weight.
