# B00.CH01.P06 Canon governance and change discipline

This paragraph defines the governance and change discipline for the canon. The aim is to allow evolution without semantic drift, silent privilege creation, or retroactive re-interpretation. Canon changes are valid only when they are **classed**, **procedurally ratified**, **publicly logged**, and **testably safe** with respect to invariants.

The canon is not “a document that can be edited.” It is a sequence of **immutable releases** with explicit compatibility status and controlled deprecation.

---

## B00.CH01.P06.S01 Change classes: patch / minor / major (semantic)

All changes MUST be classified as exactly one of: **PATCH**, **MINOR**, or **MAJOR**. Classification is semantic, not editorial.

### PATCH (non-semantic clarification)
A PATCH is permitted only if it does **not change meaning** and does **not change any test outcome** under the same inputs and parameters.

Allowed PATCH examples:
- clarifying wording while preserving formal content,
- adding examples explicitly marked *non-normative*,
- fixing typos, formatting, cross-references,
- tightening ambiguity by choosing the already-implied interpretation *without changing outputs*.

PATCH requirements:
- Must include an **equivalence claim**: “no semantic change,” plus a justification.
- Must pass a **regression test** suite demonstrating invariant outputs are preserved.

### MINOR (extensions within invariants)
A MINOR change may add capability while preserving all invariants and preserving backward interpretability.

Allowed MINOR examples:
- adding optional modules that do not weaken any invariant,
- adding new canonical metrics where old metrics remain valid,
- expanding taxonomies (e.g., new contract types) with explicit mappings,
- parameter-range extensions that remain inside invariant rails.

MINOR requirements:
- Must publish migration guidance and mapping.
- Must not silently invalidate prior “conform” results; where results differ, the cause must be attributable to the new optional module or explicit parameter choice.

### MAJOR (invariant-impacting or conflict-rule changes)
A MAJOR change includes any change that:
- alters an invariant,
- changes the meaning of a canonical term or symbol,
- changes conflict rules, consolidation thresholds, or fail-closed defaults,
- changes what is considered measurable/auditable for conformity,
- introduces or legitimizes new exception classes.

MAJOR changes are treated as **fork-risk events** by default and require stronger ratification and explicit compatibility boundaries.

## B00.CH01.P06.S02 Change procedure: proposal, review, audit, ratification

No change becomes canonical by edit. Canonical status is earned only through the following procedure.

### Step 1 — Proposal (public and structured)
Every proposed change MUST publish:
- change class (PATCH/MINOR/MAJOR) and rationale,
- affected paragraph IDs and a machine-readable diff (where feasible),
- expected impact on invariants and tests,
- any parameter interactions,
- migration and deprecation implications.

### Step 2 — Review (semantic + adversarial)
Review MUST include:
- semantic review (does meaning change, does scope creep occur),
- adversarial review (how could this be gamed, where are loopholes),
- compatibility review (does it break prior mappings),
- privacy-minimalism review (does it require new sensitive observables).

### Step 3 — Audit (testability and enforceability)
Audit MUST verify:
- updated rules are **measurable** and **auditable**,
- regression tests pass (for PATCH/MINOR),
- new tests are specified for any new rule,
- evidence standards remain enforceable (no “trust me” regressions),
- anti-omzeiling coverage is not reduced.

### Step 4 — Ratification (authority + threshold)
Ratification MUST be:
- explicit (recorded vote/decision),
- time-stamped,
- tied to an immutable release artifact,
- subject to the dispute protocol.

Ratification threshold is stricter for higher classes:
- PATCH: standard majority / standard quorum.
- MINOR: supermajority or increased quorum (canon policy choice), plus mandatory migration notes.
- MAJOR: supermajority + external audit sign-off, and explicit fork/compatibility handling.

If procedure is incomplete, the change is **non-canonical** by definition.

## B00.CH01.P06.S03 Deprecation and backward compatibility: conditions and timelines

### Backward compatibility (normative)
Canon releases MUST define a backward-compatibility policy. At minimum:

- A compatibility window during which older versions remain “supported” for claims, audits, and dispute resolution.
- A mapping policy stating when bridging documents are required to compare results across versions.

Backward compatibility means: an evaluator can unambiguously interpret a claim tied to an older version without guessing semantics.

### Deprecation (controlled removal)
Deprecation is the only legitimate path to removal. It MUST include:

- a **deprecation notice** with rationale,
- explicit status tags per element: **discouraged**, **deprecated**, **removed**,
- a migration path (mapping, replacements, impact),
- a timeline with dates or release counts (the canon may choose “time” or “N releases,” but it must be explicit),
- a statement of what happens to prior results (restatement or grandfathering rules).

### No silent breakage
If a term, metric, or rule is removed or changed in a way that affects outputs, this cannot be PATCH. It is MINOR or MAJOR and must trigger the relevant migration discipline.

### Sunsets for temporary exceptions
Any temporary exception or crisis-mode rule MUST have a sunset condition at creation time:
- date-based or indicator-based,
- with rollback plan,
- with re-ratification required to extend.
Absent a sunset, the exception is invalid.

## B00.CH01.P06.S04 Emergency patches and rollback: incident regime without semantic erosion

Emergency change mechanisms exist to address discovered exploits, measurement defects, security breaches, or governance compromises—without allowing “emergency” to become a loophole for semantic erosion.

### Incident triggers (normative)
Emergency action is permitted only when at least one of the following is documented:
- active exploitation/omzeiling that defeats an invariant,
- critical measurement defect (systematic misclassification, broken auditability),
- security breach affecting integrity of logs/data/releases,
- drift event: divergence between declared canon and applied interpretation in practice.

### Emergency patch constraints
Emergency patches MUST:
- be time-bounded,
- be narrowly scoped to restore enforceability,
- preserve invariants unless explicitly declared as MAJOR (in which case fork-risk and ratification rules apply),
- include immediate publication of: what happened, what changed, and what evidence supports the fix.

Emergency patches may be expedited procedurally, but they may not bypass:
- classification,
- public changelog,
- auditability checks,
- post-hoc review and ratification within a defined short window.

### Rollback and recovery
The canon MUST define rollback conditions and procedure:
- criteria for reverting an emergency patch (e.g., false positive, unintended scope expansion),
- how to handle affected claims (restatement rules),
- integrity restoration (re-issue signed artifacts, invalidate compromised builds),
- explicit “state of the world” communication: which version is canonical for which dates and claims.

### Non-negotiable: no semantic erosion by crisis
A crisis cannot be used to introduce privileges, broaden scope, or weaken evidence standards. Any attempt to do so is treated as MAJOR and subject to fork protocol and heightened scrutiny.
