# B00.CH11.P06 — Fork protocol: when and how forks arise

This paragraph defines the **fork protocol** for OBA: when a fork exists, how it must be declared, documented, and named, and how
interoperability between forks is permitted. Forks are allowed as a governance reality, but must be **explicit** to prevent
confusion, semantic drift, and compatibility-by-branding.

---

## B00.CH11.P06.S01 — Fork triggers: change of invariant, redefinition, hidden exceptions, black-box governance

A fork exists when an implementation deviates from the OBA class in ways that change meaning, weaken constraints, or break
auditability. Fork status is determined by **tests and artifacts**, not by stated intent.

### Fork triggers (non-exhaustive)
- **Invariant change**: altering, suspending, or replacing any invariant requirement.
- **Redefinition**: redefining canonical terms outside canonical governance, including silent synonym substitution that changes scope.
- **Hidden exceptions**: discretionary carve-outs, undocumented exemptions, or scope slicing that hollow out constraints.
- **Black-box governance**: decisions, classifications, or enforcement based on undisclosed methods, inaccessible data, or non-reproducible logic.

### Conformance requirements (binding)
- If any fork trigger is present, the implementation MUST be treated as **Non-conform / Fork** immediately (fail-closed).
- An implementation MUST NOT claim compatibility labels while any fork trigger is unresolved.

---

## B00.CH11.P06.S02 — Fork documentation: explicit changelog, rationale, impact on invariants

Forks must be **documented** so that observers can identify exactly what changed and what the consequences are.

### Mandatory fork documentation (minimum)
- **Fork declaration**: explicit statement that this is a fork and not OBA-compatible.
- **Changelog**: a structured list of changes, each linked to the canonical source it diverges from.
- **Rationale**: reasons for each change (policy goal, constraint, feasibility, jurisdictional conflict).
- **Impact on invariants**: a clear statement per change indicating:
  - which invariant(s) are affected,
  - whether the change weakens/tightens constraints,
  - what new tests replace canonical tests (if any),
  - what new failure modes are introduced.
- **Evidence and methods**: if alternative tests are proposed, methods must be published and auditable.

### Conformance requirements (binding)
- A fork without the mandatory documentation MUST be treated as **unpublishable as a compatibility-relevant artifact** and MUST NOT
  use the OBA name.
- Fork documentation MUST be versioned and publicly accessible.

---

## B00.CH11.P06.S03 — Fork naming: mandatory distinction, no “OBA” without compatibility label

Naming is governance: public confusion is treated as harm to compatibility integrity.

### Naming rules
- Forks MUST use a **distinct name** that prevents confusion with OBA.
- The string **“OBA”** MUST NOT be used in a fork name, product name, programme name, or institutional label unless accompanied by a
  clear compatibility label and evidence bundle (per name-usage rules).
- Public communication MUST display the fork status prominently and consistently.

### Conformance requirements (binding)
- Any use of “OBA” without an allowed compatibility label and evidence MUST be treated as **misrepresentation** and triggers immediate
  downgrade to **Non-conform / Fork** plus corrective duty (see communication rules).
- Any ambiguous naming that could plausibly be read as OBA compatibility MUST be corrected; until corrected, status is non-conform.

---

## B00.CH11.P06.S04 — Interoperability: mapping between forks only via explicit bridging docs

Interoperability between OBA and forks (or between forks) is permitted only via explicit, published mapping artifacts. Implicit
claims of equivalence are forbidden.

### Bridging documentation (minimum)
- **Mapping table**: term-by-term mapping (or explicit “no mapping possible”) between definition sets.
- **Invariant delta**: explicit listing of invariant differences and their practical consequences.
- **Test translation**: if outputs are compared, the translation method and lossiness must be disclosed.
- **Scope statement**: what the bridge does and does not guarantee (no blanket equivalence).

### Conformance requirements (binding)
- Cross-fork interoperability claims MUST NOT be made without published bridging docs.
- Bridging docs MUST NOT assert equivalence where invariant deltas exist; they may only describe correspondence and limitations.
- In absence of bridging docs, systems MUST treat forks as **non-interoperable** for compatibility assertions (fail-closed).
