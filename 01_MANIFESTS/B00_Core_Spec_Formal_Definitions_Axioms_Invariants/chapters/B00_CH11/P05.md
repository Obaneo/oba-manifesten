# B00.CH11.P05 — Compatibility labels and status levels (name usage)

This paragraph defines the permitted **compatibility labels** and the binding rules for **name usage**. “OBA” is treated as a
protected class-name: its use is only allowed when the corresponding **status criteria** are met and the required **evidence set**
is published. Labels are not marketing adjectives; they are **formal claims** governed by the compatibility tests and the source
hierarchy.

---

## B00.CH11.P05.S01 — “OBA-conform”: meets all invariants + audit requirements

**OBA-conform** is the highest compatibility status. It asserts full conformance with the invariant set and the minimum
auditability requirements for the declared scope.

### Criteria (minimum)
- All **invariants** are satisfied within claim scope.
- **Definition-set closure** holds for all used terms (traceable to canonical sources).
- **Auditability** requirements are met (measurable, reproducible, public methods).
- **Anti-avoidance** layer is present and enforceable for the scope.
- Outcome monitoring is in place per compatibility requirements.

### Conformance requirements (binding)
- “OBA-conform” MUST NOT be used unless the full evidence bundle is published and the compatibility tests pass.
- Any detected invariant breach or auditability breach MUST trigger immediate downgrade (fail-closed).

---

## B00.CH11.P05.S02 — “OBA-compatible”: meets core invariants but lacks optional modules (canonically defined)

**OBA-compatible** asserts conformance with the **core invariant rails**, but allows the absence of specified **optional modules**
that are canonically defined as non-essential for class membership (e.g., additional reporting layers, extended sector canvases,
advanced monitoring modules).

### Criteria (minimum)
- All **core invariants** are satisfied within claim scope.
- Definition-set closure and auditability minimums are met for the implemented components.
- Missing components MUST be explicitly listed as **optional modules** (as canonically defined), not silently omitted.

### Conformance requirements (binding)
- “OBA-compatible” MUST include a published **module matrix** indicating which optional modules are implemented vs not implemented.
- If any core invariant is missing or weakened, the status MUST be “Non-conform / Fork”, not “OBA-compatible”.
- “OBA-compatible” MUST NOT be used as a substitute for “OBA-conform” without disclosing the missing optional modules.

---

## B00.CH11.P05.S03 — “OBA-inspired”: refers to ideas without compatibility claim (permitted label)

**OBA-inspired** is a permitted label for work that borrows concepts, framing, or partial tools from OBA but does not assert class
membership.

### Permitted use
- Referencing OBA ideas, terminology, or goals without claiming compatibility.
- Educational material, commentary, prototypes, or partial implementations without audit-grade evidence.

### Restrictions
- “OBA-inspired” MUST NOT be used to imply that compatibility tests have been passed.
- “OBA-inspired” MUST NOT be used to access OBA-gated privileges, registries, or commons programmes reserved for compatible status.

### Conformance requirements (binding)
- Any artifact labeled “OBA-inspired” MUST include a clear disclaimer: **no compatibility claim** and **no status label** beyond
  “OBA-inspired”.
- If the artifact makes operational claims equivalent to compatibility (e.g., “meets OBA requirements”), it MUST be upgraded to a
  formal compatibility claim and tested, or it MUST be corrected.

---

## B00.CH11.P05.S04 — “Non-conform / Fork”: breaks invariants or auditability; restricted name usage

**Non-conform / Fork** applies when an implementation fails invariants, fails auditability, redefines canonical terms, introduces
forbidden exceptions, or cannot publish the required evidence. Forks are allowed to exist, but MUST be explicitly named and must
not trade on the OBA label as if they were compatible.

### Triggers (non-exhaustive)
- Any **invariant breach** or invariant hollowing by exception.
- Failure of **auditability** (black-box, non-disclosure, non-reproducibility).
- Redefinition of canonical terms outside governance.
- Parameter choices outside allowed bounds.
- Proven misrepresentation of status labels.

### Name usage restrictions (binding)
- “OBA”, “OBA-conform”, and “OBA-compatible” MUST NOT be used for non-conform implementations.
- Forks MUST use distinct naming that prevents confusion, and MUST state fork status prominently in public communication.
- Any uncertainty about status (missing evidence, unresolved conflict) MUST be treated as **non-conform** until resolved (fail-closed).
