# B00.CH11 — Compatibility and forks: parameter space, procedure, conflict rules and name usage

This chapter defines **compatibility** in OBA as a **formal, testable claim** and specifies how meaning is kept stable across
definitions, implementations, jurisdictions, and sector variants. It prevents **semantic drift** and **compatibility-by-branding**
by enforcing (i) a **source hierarchy**, (ii) a strict **invariant vs parameter** boundary, (iii) minimal **compatibility tests**,
(iv) evidence-bound **labels and name usage**, and (v) a documented **fork protocol** with mandatory distinction and bridging rules.

## How to use this chapter

- If you are **publishing an OBA implementation**: anchor every claim to a **definition-set ID + version**, keep all terms
  traceable to canonical sources, and run the **compatibility tests** before using any OBA label.
- If you are **reviewing third-party claims**: require published evidence, audit methods, and definition references; downgrade
  status when requirements are missing or unverifiable.
- If you are **designing sector canvases or local variants**: only fill **parameters within bounds**; do not redefine terms or
  weaken invariants; publish the minimum sector disclosure set.
- If you are **handling conflicts**: apply the conflict rules (definition/implementation/parameter/jurisdiction); use hard stops
  when black-box governance, non-disclosure, or proven misrepresentation occurs.

## Status

This chapter is **normative** for all **compatibility claims** and **name usage**. If a claim cannot be anchored to canonical
sources, cannot be audited, or breaks invariants, it must be treated as **non-conform / fork** until remedied.
