# B00.CH11.P03 — Invariants versus parameters (what may vary)

This paragraph defines the boundary between **invariants** (non-negotiable class requirements) and **parameters** (allowed degrees
of freedom) within OBA. Compatibility is only meaningful if this boundary is enforced: invariants preserve class identity, while
parameters allow contextual tuning across sectors, jurisdictions, and time.

---

## B00.CH11.P03.S01 — Invariants: P/E/C function, R/B structure, cap principles, commons order properties, ΔM forbidden channels

**Invariants** are the constitutive requirements of the OBA class. Changing an invariant changes the class and therefore triggers a
fork.

### Canonical invariant set (minimum)
- **P/E/C function**: the classification function and its role in identifying extractive components MUST remain intact.
- **R/B structure**: the canonical structure for computing and constraining R/B profiles MUST remain intact.
- **Cap principles**: the existence and enforceability of accumulation caps (e.g., wealth/income cap principles) MUST remain intact.
- **Commons order properties**: the required properties for commons governance, access, maintenance, and publication MUST remain intact.
- **ΔM forbidden channels**: prohibited monetary channels and leakage constraints MUST remain intact.

### Conformance requirements (binding)
- Any implementation claiming OBA status MUST preserve all invariants within its claim scope.
- Any change that alters an invariant MUST be treated as a **fork** and MUST follow the fork protocol and naming rules.
- Invariants MUST NOT be bypassed through exemptions, discretionary carve-outs, or “equivalent outcomes” claims unless such
  equivalence is canonically defined and testable.

---

## B00.CH11.P03.S02 — Parameters: α, cap levels, baseline access volumes, indexations, time resolutions (within bounds)

**Parameters** are explicitly allowed degrees of freedom that tune OBA within invariant rails. Parameters may vary across
jurisdictions, sectors, or time, but only within canonically defined bounds and procedures.

### Examples of parameters (non-exhaustive)
- **α** (R/B floor or threshold parameter), within defined bounds.
- **Cap levels** (numerical levels under the cap principles), within defined bounds and update rules.
- **Baseline access volumes** for essentials/commons access entitlements (where applicable), within defined bounds.
- **Indexations** (inflation/price/wage references) and update cadence, within defined bounds.
- **Time resolutions** (monthly/quarterly/annual reporting windows; detection windows), within defined bounds.

### Conformance requirements (binding)
- Parameter choices MUST be explicitly published as part of the implementation’s claim metadata.
- Parameter values MUST remain within canonically allowed bounds; outside-bound values render the claim **non-conform** until remedied.
- Parameter variation MUST NOT change the meaning of invariants or reduce auditability.

---

## B00.CH11.P03.S03 — Forbidden variation: exceptions that hollow out invariants (semantic break)

Certain “variations” are forbidden because they preserve the surface label while breaking the class.

### Forbidden patterns (non-exhaustive)
- **Invariant hollowing**: introducing exceptions that exempt dominant actors, high-impact sectors, or key channels from invariant tests.
- **Discretionary escape hatches**: compatibility contingent on case-by-case waivers rather than passing formal checks.
- **Black-box substitutions**: replacing canonical tests with opaque scoring, unverifiable models, or unpublished methods.
- **Scope slicing**: narrowing the claim scope to exclude the very mechanisms that would fail invariants, while still using OBA branding.

### Conformance requirements (binding)
- Any exception that weakens or suspends an invariant MUST be treated as a **semantic break** and therefore a **fork trigger**.
- If such an exception is detected, the affected claim MUST be downgraded to **non-conform / fork** immediately (fail-closed).

---

## B00.CH11.P03.S04 — Parameter rules: change procedure, evidence, impact analysis, sunsets

Parameter flexibility requires procedural discipline to prevent gradual erosion and capture. Parameter changes therefore require a
formal change procedure with evidence, impact analysis, and expiry discipline.

### Required change procedure (minimum)
- **Change request**: explicit proposal identifying parameter(s), current value, proposed value, and rationale.
- **Evidence dossier**: data and methods supporting the change, including uncertainty and sensitivity.
- **Impact analysis**: expected effects on P/E/C indicators, R/B profiles, cap bindingness, commons performance, and leakage risks.
- **Publication**: public record of the change, including effective date and version linkage.
- **Sunset clause**: predefined review date and conditions for continuation/rollback.

### Conformance requirements (binding)
- Parameter changes MUST follow the published change procedure and MUST be traceable to a versioned record.
- Parameter changes without evidence, impact analysis, and publication MUST be treated as **invalid**, and any dependent OBA claim
  MUST be treated as **non-conform** until corrected.
- Sunsets MUST be enforced; expired parameters revert to the last valid setting (or to canonical defaults where defined) until renewed.
