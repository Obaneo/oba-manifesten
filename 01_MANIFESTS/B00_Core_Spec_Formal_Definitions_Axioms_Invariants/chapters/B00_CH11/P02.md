# B00.CH11.P02 — Compatibility layers (hierarchy of sources)

This paragraph defines the **hierarchy of sources** that governs meaning, conformance, and dispute resolution in OBA.
Because “compatibility” is a **formal class claim**, all terms, rules, and procedures used in that claim MUST be anchored to
canonical sources in a strict precedence order. This prevents **shadow canons**, selective quotation, and redefinition-by-commentary.

---

## B00.CH11.P02.S01 — Source hierarchy: Kernel Spec > Standards/Codex > books > commentary/marketing

OBA meaning is governed by a strict **source precedence**. Lower layers may explain, operationalize, or contextualize higher layers,
but may not contradict, weaken, or redefine them.

### Layer definitions (highest to lowest authority)
1. **Kernel Spec** (canonical): definitions, invariants, class requirements, conflict primitives.
2. **Standards / Codex** (operational): schemas, methods, templates, audit procedures, reference computations; MUST be Kernel-consistent.
3. **Books (1–4)** (application logic): elaboration, examples, domain mapping; MUST remain consistent with Kernel and Codex.
4. **Commentary / marketing / public comms** (non-canonical): narrative explanation only; MUST NOT define or alter requirements.

### Conformance requirements (binding)
- Any document or implementation that asserts an OBA label MUST follow this hierarchy for all definitions and requirements used.
- If a lower layer conflicts with a higher layer, the lower layer MUST be treated as **non-canonical** and MUST NOT be used to
  justify compatibility.
- Commentary/marketing MUST be explicitly treated as **non-normative** and MUST NOT introduce new definitions, exceptions, or
  substitute tests.

---

## B00.CH11.P02.S02 — Canonical reference: definition-set ID and version as required part of every claim

Every compatibility claim MUST be explicitly tied to a **definition-set identifier and version**. Without this anchor, the claim is
semantically ambiguous and cannot be audited or disputed.

### Required claim metadata (minimum)
- **definition_set_id**
- **definition_set_version**
- **artifact references** (at least: Kernel Spec version; any Codex/Standard versions used)
- **scope of claim** (system/module/jurisdiction/sector canvas)

### Conformance requirements (binding)
- Any use of an OBA status label MUST include the **definition-set ID + version** as part of the claim (not optional metadata).
- Claims lacking this reference MUST be treated as **non-conform** until corrected (fail-closed).
- If multiple definition-set references are mixed within one claim or publication, the claim MUST be split into separate claims
  or treated as non-conform.

---

## B00.CH11.P02.S03 — Interpretation rule: refer instead of redefining (anti-drift)

Interpretation in OBA is governed by a **reference rule**: when a term is used, the correct action is to **refer to** its canonical
definition, not to restate or “clarify” it in a way that changes its boundaries.

### Rules of interpretation
- **Referential use**: cite the canonical definition and use it unchanged.
- **Operational add-ons**: implementation details MAY be added only if they do not change canonical meaning and remain traceable.
- **No synonym substitution**: replacing canonical terms with near-synonyms is disallowed if it alters classification or tests.
- **No exception invention**: exceptions are invalid unless they exist in canonical sources and meet the change procedure.

### Conformance requirements (binding)
- Any artifact that introduces a new definition for an existing canonical term MUST be treated as a **fork trigger** unless the
  change is processed through canonical governance.
- Any “interpretation” that modifies thresholds, scope, or class requirements outside parameter space MUST be treated as
  non-conform until remedied.

---

## B00.CH11.P02.S04 — Fail-closed: in case of source conflict, the strictest canonical interpretation applies

When sources conflict, OBA applies a **fail-closed** rule to preserve class integrity and prevent loopholes. In a conflict,
the applicable interpretation is the one that **maximizes constraint** consistent with the highest-authority sources.

### Conflict resolution rule
- **Precedence**: higher layer prevails over lower layer (per S01).
- **Strictness**: if two canonical sources at the same layer plausibly allow multiple readings, the reading that is **strictest**
  with respect to invariants and auditability prevails until formally resolved.

### Conformance requirements (binding)
- Any unresolved conflict affecting definitions, invariants, or auditability MUST result in **non-conform status** for the affected
  claim scope until resolution or patch publication.
- Entities MUST NOT continue to use an OBA status label while relying on a permissive interpretation that is not canonically
  resolved.
- Resolution MUST be recorded as a versioned canonical update (Kernel governance and/or Codex update), and the claim metadata
  MUST be updated accordingly.
