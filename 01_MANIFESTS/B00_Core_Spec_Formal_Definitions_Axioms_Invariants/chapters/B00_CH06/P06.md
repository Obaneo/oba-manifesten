# B00.CH06.P06 — I-MAX parameterisation and cap regime

This paragraph defines how **I-MAX** is parameterised as a canonical cap regime. I-MAX is not merely “a limit on
income”; it is a binding interface consisting of:
- cap form (absolute limit vs threshold + skimming),
- parameter values (unit, indexation, allowed cohort/sector variation),
- reference anchors (how parameters relate to wages, productivity, and R/B targets),
- and strict controls against discretionary exceptions.

Parameterisation is normative: it determines incentives, avoidance surfaces, labour allocation effects, and the
interaction with W-MAX and R/B. Therefore parameter changes must follow the canonical **Kernspec procedure** and
must be versioned.

---

## B00.CH06.P06.S01 — Definition of I-MAX: absolute cap vs cap + skimming function (canonical choice)

I-MAX can be implemented in one of two canonical forms. The regime MUST explicitly choose one and specify the
mechanics.

### Form A — Absolute cap (hard limit)
- I must not exceed **I-MAX** within the enforcement period.
- A breach triggers mandatory remedies that reduce the effective income capture above the cap (timing and remedy set
  specified in P07).
- Hard caps require strong anti-deferral and event-driven triggers; otherwise income is pushed into delayed forms.

### Form B — Threshold + skimming function (soft cap with automatic capture)
- I may exceed a threshold, but excess income is subject to an automatic **skimming function**:
  - **skim = f(I − I-MAX)** with explicit function form and parameters.
- Skimming must be automatic and non-discretionary; otherwise enforcement becomes negotiable and capturable.
- Skim destination must be canonical (e.g., conversion to C under admissibility rules, or other declared sinks).

Canonical choice requirement:
- the regime MUST state whether I-MAX is a hard boundary or a threshold with skimming, and must specify how the
  selected form interacts with deferral and mixed income components.

### Conformance requirements (binding)

- Any I-MAX implementation MUST specify cap form and mechanics; “income is capped” without form is non-conform.
- Any skimming function must be explicit, parameterised, and auditable; discretionary skimming is non-conform.

---

## B00.CH06.P06.S02 — Parameters: indexation, cohort/sector variation (only via Kernspec procedure)

I-MAX parameterisation includes (minimum):

- **Unit and basis:** nominal currency, real indexed unit, or ratio-based anchor (must be explicit).
- **Indexation rule:** inflation index, median wage index, productivity-linked index, or other canonical index;
  frequency and method must be declared.
- **Period and averaging:** whether the cap applies per year, per month, or with rolling windows; any averaging must
  be explicit and designed to reduce gaming (not to add discretion).
- **Cohort/sector variation (if any):** allowed only under strict canonical constraints, because it is a capture surface.

Governance constraint (binding):
- parameter choices and changes may occur only via the **Kernspec procedure** (evidence, impact analysis, ratification,
  versioning, sunset/rollback where relevant). Ad hoc adjustments void conformance.

### Conformance requirements (binding)

- I-MAX parameters MUST be published, versioned, and stable within release; silent drift is non-conform.
- Any cohort/sector variation must be explicitly justified, bounded, and audited for discrimination/capture patterns;
  otherwise it is forbidden.

---

## B00.CH06.P06.S03 — Reference anchors: median wage ratio, R/B target path, productivity bands

I-MAX parameters should be anchored to canonical reference frames to maintain coherence with lived-world order and to
avoid arbitrary numbers.

Canonical anchor candidates (regime may combine; must be explicit):

1) **Median wage ratio anchor**
   - define I-MAX as a multiple of median wage (or median labour income) within a jurisdiction/sector, providing a
     stable compression reference and an audit-friendly public metric.

2) **R/B target path anchor**
   - define or validate I-MAX against a target trajectory for improving R/B profiles (especially tails below α),
     ensuring flow caps are justified by order outcomes rather than optics.

3) **Productivity bands anchor**
   - align allowable top flows with productivity bands or functional contribution bands (where measurable), but avoid
     circular self-justification (“high pay proves high productivity”). Measurement must be external and auditable.

Anchors are not themselves sufficient; they are reference points used to parameterise and to evaluate cap adequacy.

### Conformance requirements (binding)

- Any I-MAX regime MUST publish its anchors and how parameters map to them; otherwise the cap becomes arbitrary and
  politically unstable.
- If anchors are black-box indices, the regime is non-conform (auditability requirement).

---

## B00.CH06.P06.S04 — Forbidden variation: exceptions based on status, lobbying or ad-hoc deals

I-MAX is incompatible with discretionary privilege exceptions. Exceptions are a primary capture vector.

Forbidden variation bases include (non-exhaustive):
- status/celebrity/legacy privilege,
- sectoral lobbying carve-outs (“finance exception”, “tech exception”),
- bespoke negotiated compensation treatments,
- ad hoc “national champion” deals,
- selective enforcement or selective base exclusions.

Canonical rule:
- any exception must be function-justified, generalisable, parameterised, and adopted only via canonical procedure.
- if exceptions are introduced outside that procedure, the compatibility claim is suspended.

### Conformance requirements (binding)

- Any I-MAX regime with status/lobbying/ad-hoc exception channels is non-conform for OBA-grade compatibility claims.
- If enforcement outcomes differ across comparable subjects without canonical basis, the regime is capturable and
  must be treated as non-compatible until remediated.
