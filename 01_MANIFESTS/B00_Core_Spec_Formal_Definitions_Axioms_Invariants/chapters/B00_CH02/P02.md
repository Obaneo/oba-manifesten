# B00.CH02.P02 Time, resolution and aggregation (indexing)

This paragraph defines the canonical time-indexing discipline for the Core Spec and sets the rules for aggregation across time, actors, cohorts, and domains. OBA-critical metrics must be comparable across implementations and auditable across scales (micro → macro). That requires (i) explicit time indices, (ii) declared resolution, (iii) type-consistent aggregation operators, and (iv) reconciliation constraints that prevent “statistical laundering” (e.g., averages hiding tail failure).

Time indexing is not optional. Any quantity or rule that can vary over time MUST declare how time enters the symbol (as an index, argument, or implicit resolution) and MUST specify how values are aggregated or compared across periods. Where resolution or aggregation is ambiguous, evaluation MUST be conservative and MUST fail closed.

Scope of this paragraph:

- Applies to all OBA-critical quantities, definitions, tests, and published metrics that are time-indexed or aggregated.
- Defines standard resolutions and conversion rules (day/month/year) and forbids silent annualization or smoothing.
- Specifies admissible aggregations per quantity type (stock/flow/rate/ratio/distribution).
- Requires reconciliation constraints linking micro-level data to macro aggregates and accounting identities.

Conformance requirements (binding):

- Any time-varying quantity MUST declare a time index `t` and a resolution (or explicitly declare itself as timeless/structural).
- Any aggregation MUST be type-consistent and MUST declare its operator (sum/mean/percentile/distribution) and domain of aggregation (time/actors/cohorts).
- Any published macro statistic used for OBA claims MUST be reconcilable to micro-level observables within declared uncertainty bounds; otherwise the claim MUST fail closed.

## B00.CH02.P02.S01 Time index t and standard resolutions (day/month/year)

The Core Spec uses `t` as the canonical time index. `t` denotes discrete periods at a declared resolution. The standard resolutions are:

- `t = day`: daily periods (calendar day basis, timezone explicitly declared where relevant).
- `t = month`: monthly periods (calendar month basis).
- `t = year`: yearly periods (calendar year basis; fiscal year allowed only if explicitly declared and mapped).

A time-indexed quantity MUST specify the resolution explicitly or inherit it from a declared local “time context” that itself is normative and unambiguous (e.g., a section-level declaration “All quantities are monthly unless stated otherwise”). Silent changes of resolution are prohibited.

Time boundaries and conventions:

- Period membership MUST be defined (inclusive/exclusive boundaries) if the choice can change outcomes materially.
- Timezone and cut-off rules MUST be specified when dealing with event-timestamped flows.
- If a quantity is defined as an average over a period (e.g., average stock), the averaging rule MUST be specified (e.g., end-of-period, time-weighted average).

Resolution conversions:

- Flows: converting from higher resolution to lower resolution is additive (e.g., daily flows summed to month). Converting from lower to higher resolution requires an explicit allocation rule and MUST be marked as imputed.
- Stocks: converting across resolutions is a selection/averaging rule (e.g., end-of-month stock), not a sum.

Conformance requirements (binding):

- Any OBA-critical quantity that varies over time MUST include `t` explicitly (index/argument) and MUST declare its resolution (day/month/year or explicitly declared alternative).
- Any conversion across resolutions MUST declare the operator and any imputation; silent annualization, smoothing, or interpolation is non-conform.
- If time boundaries/timezone choices could change classification or compliance outcomes, those conventions MUST be specified; otherwise evaluation MUST fail closed.

## B00.CH02.P02.S02 Aggregation rules (additive, mean, percentiles, distributions)

Aggregation is the act of combining observations across an index set (time, actors, cohorts, sectors, contracts). Because OBA evaluation depends on distributive properties (e.g., R/B tail outcomes), aggregation MUST be explicit and type-correct.

Canonical aggregation operators:

- **Additive (Σ)**: Used for flows and for decomposable quantities where summation preserves meaning (e.g., total transfers T across actors over the same period).
- **Mean / expected value (E[·])**: Used for bounded ratios or rates only when explicitly defined and when averaging does not destroy the evaluative meaning.
- **Percentiles (p10, p25, median, p75, p90)**: Required where distributional guarantees matter (e.g., R/B≥α must not be represented solely by a mean).
- **Full distribution / histogram / CDF**: Required when tail risk or threshold compliance is central; at minimum, published summaries MUST include key percentiles and the under-threshold share.
- **Weighted aggregations**: Allowed only with declared weights and justification (population weights, exposure weights), and MUST be reproducible.

Type-consistency constraints:

- Stocks are not summed across time; flows are not averaged without declaring the period and weighting.
- Ratios (e.g., R/B) MUST NOT be “macro-averaged” in a way that hides distributional failure. The canonical approach is:
  - compute the ratio at the unit of analysis (actor/cohort) first,
  - then publish distribution statistics and under-α share,
  - and only then publish any mean/aggregate as supplementary.

Aggregation metadata:

Any aggregated metric used for an OBA claim MUST declare:

- unit of analysis (actor/household/entity/cohort),
- aggregation domain (over time, over units, over sectors),
- operator (sum/mean/percentiles/distribution),
- weighting scheme (if any),
- and uncertainty treatment (sampling, imputation, missingness).

Conformance requirements (binding):

- Aggregations MUST be explicitly declared (operator + index domain + unit of analysis); implicit aggregation is non-conform.
- For any OBA-critical claim involving thresholds, floors, or “minimums” (e.g., R/B≥α), distributional summaries (percentiles + under-threshold share) are REQUIRED; means alone are insufficient and MUST NOT be used to assert conformance.
- Any weighting MUST be declared and reproducible; undisclosed weights are treated as opacity and MUST fail closed.

## B00.CH02.P02.S03 Stock-versus-flow conventions (balance sheet vs income/result)

OBA distinguishes **stocks** (state variables at a point or over a period) from **flows** (movements during a period). Confusing the two is a primary source of measurement drift and audit failure.

Canonical conventions:

- **Stock (S)**: A quantity defined at a time point or as a period-level state (e.g., wealth W(t), capacity G(t)). Stocks have units like currency, units of capacity, or rights/claims counts.
- **Flow (F)**: A quantity accumulated during a period (e.g., income I(t), transfers T(t), burdens L(t), ΔM(t)). Flows have units like currency per period.

Representation rules:

- A flow MUST be tied to a period (t). A stock MUST specify the observation moment rule (end-of-period, start-of-period, or average).
- Changes in stocks are expressed with Δ: `ΔS(t) = S(t) − S(t−1)` at declared resolution.
- Mixing stock and flow in one expression requires explicit mapping (e.g., converting stock to an imputed annuity flow is allowed only if the function and assumptions are declared and auditable).

Accounting alignment:

- Balance-sheet style quantities (assets/liabilities/claims) are stocks.
- Income/result style quantities (receipts/expenses/transfers) are flows.
- Any statement that uses “per year” language MUST correspond to a flow or to a stock-to-flow mapping that is explicitly specified.

Conformance requirements (binding):

- Any OBA-critical quantity MUST be classified as stock or flow (or explicitly as a rate/ratio derived from them) in the symbol registry.
- Any expression combining stocks and flows MUST define the conversion rule explicitly; otherwise it is ambiguous and MUST fail closed.
- Implementations MUST NOT treat a stock as a flow (or vice versa) via implicit annualization, amortization, or capitalization without declaring the transformation.

## B00.CH02.P02.S04 Reconciliation: micro→macro consistency and accounting identities

OBA claims must be checkable from the bottom up. Macro dashboards that cannot be reconciled to micro observables are treated as non-auditable, and therefore non-conform for any claim that depends on them.

Micro→macro reconciliation has two layers:

1) **Arithmetic reconciliation**  
   Aggregates must add up within declared uncertainty. Examples:
   - Total flows across actors should match published sector totals after consistent consolidation and double-counting rules.
   - Published decompositions (e.g., B split by component) must sum to B within tolerance.

2) **Identity reconciliation**  
   Where the Core Spec defines accounting identities, implementations MUST respect them (subject to explicit error terms). Examples include identities of the form:
   - `N(t) = B(t) − T(t)`
   - `R(t) = N(t) − L(t)`
   as well as any future identities defined in the canon (e.g., for caps, ΔM channels, or commons metrics).

Uncertainty and error terms:

- Reconciliation MUST declare acceptable tolerances and sources of discrepancy (sampling error, timing mismatch, valuation differences).
- If reconciliation fails beyond tolerance, the implementation MUST either (i) correct the data/method, or (ii) publish the discrepancy and downgrade/withhold the dependent conformance claim.

Audit requirements:

- Implementations MUST publish enough metadata to reproduce reconciliation checks (schemas, mappings, transformations, and aggregation steps).
- Where privacy constraints apply, “open method / closed data” is acceptable, but the method must still permit independent verification via audits or controlled access.

Conformance requirements (binding):

- Any macro statistic used to assert OBA conformance/compatibility MUST be reconcilable to micro observables and canonical identities within declared tolerances.
- Any identity defined by the Core Spec MUST hold by construction or MUST include an explicit, bounded error term with explanation; silent identity breaks are non-conform.
- If reconciliation cannot be performed due to missing data, opaque transformations, or proprietary black boxes, evaluation MUST fail closed for any claim that relies on the unreconciled metric.
