B00.CH02.P01 Notation principles and symbol registry
This paragraph defines the canonical notation discipline for the Core Spec and establishes the requirements for the symbol registry. The purpose is not aesthetic uniformity; it is semantic closure and auditability. If the same symbol can mean different things in different places—or if the same quantity can be expressed without type/unit/index discipline—then (i) independent evaluation becomes impossible, (ii) implementations can “pass” by interpretation, and (iii) drift becomes indistinguishable from evolution.

The Core Spec therefore treats notation as a binding interface between (a) text, (b) data, and (c) evaluation. Every OBA-critical statement that uses symbols MUST be resolvable to a registry entry that specifies, at minimum: meaning, type, unit, domain, and time-index conventions. Any ambiguity in notation is treated as an ambiguity in the underlying rule and is therefore subject to conservative interpretation and fail-closed evaluation.

Scope of this paragraph.
- This paragraph governs all canonical symbols and derived expressions used in the Core Spec and in any document that claims OBA-(conform/compatible).
- The symbol registry is a normative artifact: it is required for conformance claims and for reproducible audits.
- This paragraph does not require a particular publishing format (Markdown/CSV/JSON), but it DOES require that the registry is accessible, versioned, immutable per release, and internally consistent.

Conformance requirements (binding).
- Any symbol used in an OBA-critical definition, invariant, cap rule, ΔM rule, commons rule, or evaluation test MUST have a registry entry or MUST be written out in fully explicit prose without introducing new local shorthand.
- Any implementation that introduces additional symbols MUST extend the registry in a versioned, traceable way; it MUST NOT redefine existing entries.
- Where a notation ambiguity would enlarge scope, discretion, or authority, interpretation MUST be conservative and evaluation MUST fail closed until the ambiguity is resolved canonically.

B00.CH02.P01.S01 Symbols are canonical and context-free (no local redefinitions)
Canonical symbols are global identifiers: their meaning does not depend on chapter, sector, jurisdiction, or narrative context. A symbol is not “explained again” with a new meaning; it is either referenced (same meaning) or it is not used.

Context-free means:
- No local glossaries that override the registry.
- No “in this section, X means …” if X already exists in the registry.
- No synonym substitution where the old symbol remains but the underlying semantics shifts.
- No silent shifts in measurement basis (e.g., cash vs accrual) without explicit registry-defined variants.

Allowed: specialization by indices (jurisdiction/sector/cohort/actor), and explicit function arguments, provided that the base symbol’s meaning remains unchanged and the indexing semantics are canonical.

Conformance requirements (binding).
- Implementations MUST NOT introduce local redefinitions of canonical symbols.
- A symbol MUST NOT be reused for a different concept, even if the original symbol is “not used here.”
- If a concept requires a different meaning, a new symbol MUST be introduced with a new registry entry and an explicit relationship to the original (e.g., X_cash vs X_accrual), or the concept MUST be expressed in words.
- If an evaluator cannot map a symbol unambiguously to the registry, the relevant claim MUST be treated as non-auditable and therefore non-conform (fail closed) until corrected.

B00.CH02.P01.S02 Quantities have type, unit, domain and time index
Every canonical quantity is defined by a minimal metadata tuple:

1) Type
Type is the semantic category required for correct reasoning and aggregation. At minimum, quantities MUST declare whether they are:
- Stock (state variable at time t; balance-sheet-like)
- Flow (amount over an interval ending at t; income/result-like)
- Ratio/Index (dimensionless or indexed value)
- Boolean/Predicate (true/false conditions used in tests)
- Set/Distribution (e.g., cohort profiles, percentiles)

2) Unit
Units MUST be explicit and consistent. Monetary values MUST specify the currency unit and whether values are nominal or real (deflated), including the deflator/index reference if real. Non-monetary units (time, energy, volume, service capacity) MUST use a declared unit system.

3) Domain
Domain specifies the allowed range and interpretation constraints: non-negativity, bounded intervals, discrete sets, and admissible missingness. Domains are not advisory: they are conformance constraints.

4) Time index
All quantities MUST specify time indexing conventions:
- The time variable t MUST be explicit for time-varying quantities.
- The default resolution (day/month/year) MUST be declared.
- Stock quantities MUST specify the timestamp convention (e.g., end-of-period vs point-in-time).
- Flow quantities MUST specify the interval convention (e.g., during period [t−1, t]) and whether they are accrued or cash-based.

Conformance requirements (binding).
- Any quantity used in a definition or invariant MUST declare type/unit/domain/time index either directly in text or via the registry entry it references.
- Aggregations MUST respect type: flows can be summed over time; stocks generally cannot be summed across entities without consolidation rules; ratios require explicit weighting rules.
- If unit or time conventions are missing or inconsistent, the affected computation MUST be treated as invalid for OBA evaluation (fail closed) until corrected.
- Mixing cash/accrual, nominal/real, or stock/flow WITHOUT explicit registry-defined transformation rules is non-conform.

B00.CH02.P01.S03 Subscripts/superscripts for jurisdiction, sector, cohort, actor
Indices are not decoration; they are binding scoping operators. Canonical indexing is used to specialize a quantity by jurisdiction, sector, cohort, and/or actor without changing its base meaning.

Canonical index classes.
- Jurisdiction index (J): legal/administrative scope where the rule applies (e.g., tax/transfer regime, residency, enforcement perimeter).
- Sector index (S): economic sector or domain partition used for attribution, benchmarking, or policy-specific parameterization.
- Cohort index (K): population subgroup used for distributional observables (deciles, household types, vulnerability classes, region bands).
- Actor index (A): specific actor/entity reference (natural person, legal entity, vehicle) as defined in the object model.

Canonical placement and meaning.
- Subscripts are used for scoping/conditioning (i.e., “this quantity as measured for scope X”).
- Superscripts are reserved for formally-declared variants (e.g., valuation basis, scenario tag, methodological basis) only if the registry defines that superscript family. Superscripts MUST NOT be used ad hoc.

Canonical ordering (recommended, unless explicitly overridden by the registry for a specific symbol):
X_{J,S,K,A}(t)
This ordering is a readability convention; the binding requirement is that each index is explicit and unambiguous.

Conflict rule.
If stacked subscripts or superscripts become ambiguous (e.g., X_{a,b} where b might be sector or cohort), the expression MUST be rewritten using explicit function arguments or named index labels, e.g.:
X(scope={J:…, S:…, K:…, A:…}, t)

Conformance requirements (binding).
- Any index used MUST come from a declared index class (J/S/K/A or other canonically declared classes) and MUST NOT be overloaded locally.
- Sector or jurisdiction “codes” MUST be published as part of the implementation’s documentation layer, but the index CLASS semantics remain canonical.
- Implementations MUST NOT encode substantive rule changes inside indices (e.g., using a custom sector label to smuggle a different definition).
- If an index is required to interpret a claim (e.g., R/B by cohort), omission of that index is a conformance failure unless the registry explicitly declares a default and its rationale.

B00.CH02.P01.S04 Operators and functions (Σ, Π, Δ, f(·), g(·)) and their semantics
The Core Spec uses a restricted set of mathematical operators and named functions. Each operator has canonical semantics, and each named function MUST be declared with a signature and type/unit behavior.

Σ (summation).
- Σ aggregates over an explicitly declared index set.
- The index domain MUST be specified (e.g., Σ_{i∈K}).
- Σ over flows is permitted when summing compatible units over disjoint partitions.
- Σ over stocks is only permitted under explicit consolidation rules that prevent double counting.

Π (product).
- Π denotes product over an index set and is used sparingly, typically for chained factors or multiplicative decompositions.
- Units must remain valid under multiplication; if the resulting unit is not meaningful, the expression is invalid unless explicitly defined as an index construction.

Δ (difference / change).
- ΔX(t) is the canonical discrete-time change operator.
- Default meaning: ΔX(t) = X(t) − X(t−1) at the declared base resolution of X, unless a different lag is explicitly stated (e.g., Δ_{m} for month-on-month).
- For flows, Δ may denote change in the flow rate/amount across periods; for stocks, Δ denotes net change in state.
- Δ MUST NOT be used ambiguously to mean both “difference” and “derivative”; continuous-time interpretations require explicit notation and are non-default.

f(·), g(·) (named functions).
- f and g denote named functions that transform inputs into outputs.
- Any function used in an OBA-critical rule MUST be declared (in the registry or in a dedicated function register) with:
  - Name/ID
  - Input signature (types/units/domains)
  - Output type/unit/domain
  - Monotonicity or bounding properties if relied upon by invariants
  - Default handling of missing data and uncertainty (including conservative defaults)
- “Black-box” functions are non-conform when used for critical classification or enforcement decisions unless the auditability requirements (inputs, procedure, reproducibility, and decision trace) are satisfied.

Conformance requirements (binding).
- Every use of Σ/Π/Δ MUST specify the relevant index set or time step whenever omission could change meaning.
- Any function used to produce classifications (e.g., P/E/C splits), cap bases (W-base/I-base), ΔM channel eligibility, or UBC test outputs MUST be declared and auditable; otherwise the resulting claim is non-conform (fail closed).
- Operator overloading (redefining Σ/Δ semantics locally) is forbidden.
- If an operator expression cannot be checked for dimensional consistency (units) and index consistency (domains), it MUST NOT be used as the basis for an OBA claim.
