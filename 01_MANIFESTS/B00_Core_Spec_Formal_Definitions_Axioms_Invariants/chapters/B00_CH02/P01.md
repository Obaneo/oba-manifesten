# B00.CH02.P01 Notation principles and symbol registry

This paragraph defines the canonical notation discipline for the Core Spec and establishes binding requirements for the symbol registry. The purpose is not aesthetic uniformity; it is semantic closure and auditability. If the same symbol can mean different things in different places—or if a quantity can be expressed without type/unit/index discipline—then (i) independent evaluation becomes impossible, (ii) implementations can “pass” by interpretation, and (iii) drift becomes indistinguishable from legitimate evolution.

The Core Spec therefore treats notation as a binding interface between (a) normative text, (b) data, and (c) evaluation procedures. Every OBA-critical statement that uses symbols MUST be resolvable to a registry entry specifying, at minimum: meaning, quantity type, unit, domain, and time-index conventions.

Scope of this paragraph:

- Governs all canonical symbols and derived expressions used in the Core Spec and in any document that carries an OBA conformance/compatibility claim.
- Makes the symbol registry a normative artifact: required for conformance claims and reproducible audits.
- Does not mandate a publishing format (Markdown/CSV/JSON), but DOES require that the registry is accessible, versioned, immutable per release, and internally consistent.

Conformance requirements (binding):

- Any symbol used in an OBA-critical definition, invariant, cap rule, ΔM rule, commons rule, or evaluation test MUST have a registry entry, OR MUST be written out in fully explicit prose without introducing new local shorthand.
- Any implementation that introduces additional symbols MUST extend the registry in a versioned, traceable way; it MUST NOT redefine existing entries.
- Where a notation ambiguity would enlarge scope, discretion, or authority, interpretation MUST be conservative and evaluation MUST fail closed until resolved canonically.

## B00.CH02.P01.S01 Symbols are canonical and context-free (no local redefinitions)

A symbol is canonical when its meaning is fixed by the Core Spec and does not vary by chapter, paragraph, sector canvas, jurisdiction profile, or implementation. “Context-free” means there are no “local” redefinitions such as: “in this section, let R mean …” if R is already a canonical symbol. If additional nuance is required, it MUST be expressed by indices (subscripts/superscripts), typed variants, or by defining a new symbol that does not collide with canonical ones.

Canonical symbols are therefore governed by a strict non-collision rule:

- One symbol → one meaning (global within the Core Spec release).
- One meaning → one preferred symbol (aliases may exist only as explicitly declared non-normative conveniences).

The symbol registry is the enforcement point. Each symbol entry must specify:

- canonical name (glyph/ASCII fallback),
- human-readable meaning,
- formal quantity type (e.g., stock/flow/rate/index),
- unit(s) and dimensional constraints,
- valid index set(s) and default index ordering,
- admissible transformations/aggregations (if constrained),
- and normative notes (e.g., “reserved”, “deprecated”, “discouraged”).

Conformance requirements (binding):

- Canonical symbols MUST NOT be redefined locally (no “let X mean …” if X is canonical).
- If an implementation needs a new concept, it MUST introduce a new symbol (non-colliding) and MUST register it; it MUST NOT overload an existing canonical symbol.
- Any alias, abbreviation, or typographic variant MUST either (i) map to a single canonical symbol unambiguously, or (ii) be treated as non-canonical and MUST NOT appear in OBA-critical rules.

## B00.CH02.P01.S02 Quantities have type, unit, domain and time index

Every quantitative symbol denotes a quantity with a declared structure. At minimum, each quantity MUST specify:

1) **Type**  
   The quantity type determines admissible operations and aggregation rules. Canonical minimum types include (at least): stock, flow, rate, ratio, index, threshold/parameter, categorical label, and boolean predicate.

2) **Unit**  
   Units must be explicit and consistent. Where dimensionless quantities exist (e.g., ratios), they MUST still declare “dimensionless” explicitly. Conversions MUST be declared and reproducible.

3) **Domain**  
   The domain is the set of valid values (e.g., ℝ, ℝ≥0, [0,1], categorical set) and any constraints (monotonicity, boundedness). Sign conventions MUST be explicit where relevant (e.g., inflow positive, outflow negative) and MUST be consistent within the release.

4) **Time index**  
   If a quantity is time-indexed, its index MUST be explicit (e.g., t at a defined resolution). If not time-indexed, it MUST be explicit that it is timeless/structural (e.g., an invariant definition or a static classification).

This discipline is essential because OBA rules depend on distinguishing: stocks vs flows, levels vs changes, and quantities vs parameters.

Conformance requirements (binding):

- Any quantitative symbol used in OBA-critical reasoning MUST declare type, unit, domain, and (if applicable) time index.
- If type/unit/domain/index cannot be determined from the registry entry + local statement, the symbol usage is ambiguous and MUST cause evaluation to fail closed.
- Implementations MUST NOT treat unit or type as “implicit knowledge” (e.g., currency, annualization) for OBA-critical claims; such conventions MUST be declared.

## B00.CH02.P01.S03 Subscripts/superscripts for jurisdiction, sector, cohort, actor

Indices are the canonical mechanism for scoping without redefining meaning. Subscripts/superscripts encode *which instance* of a canonical quantity is referenced, not what the quantity *means*. Indices MUST therefore be treated as part of the symbol’s formal signature.

Canonical index classes include (non-exhaustive):

- **Jurisdiction** (e.g., country/legal regime): `^J`
- **Sector / domain** (e.g., housing/energy/health): `^S`
- **Cohort** (e.g., decile, household type, region): `_c`
- **Actor / entity** (e.g., person, firm, vehicle): `_a`
- **Time**: `_t` (or `t` as an explicit argument)

Default ordering and formatting MUST be specified in the registry. A recommended canonical pattern is:

- superscripts for “regime-like” scoping (jurisdiction/sector),
- subscripts for “instance-like” scoping (actor/cohort/time),
- comma-separated multi-indices for readability: `X^{J,S}_{a,c,t}`.

Where a domain requires additional index classes (e.g., instrument, contract, platform layer), these MUST be introduced as explicit index symbols with declared domains and MUST be registered.

Conformance requirements (binding):

- Scope variation MUST be expressed via indices or explicit arguments; it MUST NOT be expressed by redefining the base symbol.
- Index sets and their allowed values MUST be declared (registry entry or local definition referencing registry).
- If an index is omitted, the default MUST be defined (e.g., “aggregate over jurisdiction J0” or “global”), otherwise omission is ambiguity and MUST fail closed.

## B00.CH02.P01.S04 Operators and functions (Σ, Π, Δ, f(·), g(·)) and their semantics

Operators and functions are not decorative: they encode evaluation semantics. Any expression using operators/functions MUST be interpretable without hidden assumptions.

Canonical operator semantics:

- **Σ (summation)**: MUST specify the index variable and the set/range (e.g., `Σ_{i∈I}`), and MUST respect quantity type (e.g., summing flows across actors over the same period is admissible; summing ratios is not unless explicitly defined).
- **Π (product)**: MUST specify the index and set; SHOULD be used sparingly and only where the domain supports multiplicative composition.
- **Δ (change operator)**: MUST specify the interval and base resolution (e.g., `ΔX(t) = X(t) − X(t−1)` at stated resolution). For stocks vs flows, Δ semantics MUST be explicit (change in level vs change in rate).
- **f(·), g(·) (functions)**: MUST declare domain/codomain, inputs, and any constraints required for evaluation (e.g., monotonicity, boundedness, piecewise definitions). If a function is implementation-dependent, it MUST be declared as a parameterized function with declared admissible parameter space.

Ambiguity controls:

- No “implicit” normalization (annualization, inflation adjustment, per-capita scaling) is allowed in OBA-critical expressions without explicit notation or declared preprocessing steps.
- No hidden maximization/minimization or “best effort” semantics: evaluation procedures MUST be explicit and reproducible.

Conformance requirements (binding):

- Any operator use MUST specify its index set/range and MUST be type-consistent with the quantities it operates on.
- Any Δ operator MUST specify the time interval and resolution; otherwise the expression is non-auditable and MUST fail closed.
- Any function used in OBA-critical rules MUST be defined (registry or referenced definition) with sufficient precision to reproduce outputs; black-box functions are non-conform where auditability is required.
