# B00.CH02.P09 Commons object model (access and maintenance)

Within OBA, **commons** is not an ownership label and not a rhetorical category. It is a **formal order object**: a regime defined by enforceable properties of **access**, **boundary rules**, **maintenance duty**, and **contestability**. The commons object model exists to make “commons” operational in evaluation: it specifies what must be true (and measurable) for an asset, service, infrastructure layer, dataset, protocol, or institution to be treated as commons within OBA claims.

The commons model is tightly coupled to remainder-space and power discipline. A functioning commons regime increases real exit options, constrains lock-in, and reduces structural burdens (L), thereby improving **R/B** profiles. Conversely, “commons” that is not auditable, not contestable, or captured by toll-gates is not commons in the OBA sense; it is an extractive layer wearing a commons label.

Conformance requirements (binding):

- Any claim that a resource is “commons” MUST be expressed as a commons object with explicit access, boundary, maintenance, and governance attributes.
- Commons status MUST be denied (fail closed) if access, maintenance, or contestability properties are not measurable and enforceable.
- Commons classification MUST be evaluated functionally: if the resource behaves as a toll gate (E), it is non-commons regardless of ownership form.

## B00.CH02.P09.S01 Commons as order object: access, boundary rules, maintenance duty

A commons object is defined by a minimum set of order properties. These properties are normative and must be implementable as rules, not merely goals.

### (1) Access
Access specifies who can use the commons, under what baseline conditions, and with what non-discrimination constraints.

Canonical access attributes (minimum):

- **baseline_access_right**: a defined minimum access level (service level / volume / coverage) that is guaranteed to the eligible set.
- **non_discrimination_rule**: constraints preventing arbitrary exclusion or hidden price discrimination for baseline access.
- **pricing_rule** (if priced): cost-recovery + bounded margin; no monopoly tolling for baseline.

### (2) Boundary rules
Boundary rules define eligibility and permissible uses, including anti-abuse constraints. Boundary rules are not “exclusion for profit”; they are integrity and sustainability constraints.

Canonical boundary attributes (minimum):

- **eligibility**: who is inside the boundary (residency, membership, contribution basis), expressed in objective criteria.
- **use_constraints**: fair use, rate limits, safety constraints, and anti-extraction protections where needed.
- **violation_process**: enforcement steps that are contestable and proportionate.

### (3) Maintenance duty
Maintenance duty makes commons durable. Without explicit lifecycle obligations, “commons” becomes a decaying promise or a pretext for later privatization.

Canonical maintenance attributes (minimum):

- **maintenance_standard**: service levels, reliability targets, repairability, resilience requirements.
- **lifecycle_plan**: capex/opex responsibilities, replacement schedules, technical debt limits.
- **funding_link**: defined mechanism by which maintenance is continuously financed (including prohibition of extractive dependency).

Conformance requirements (binding):

- A resource MUST NOT be classified as commons unless baseline access, boundary rules, and maintenance duty are explicitly specified and enforceable.
- Commons access MUST include a baseline right; “access at the provider’s discretion” is non-commons.
- Maintenance duty MUST be lifecycle-complete; one-off build without durable maintenance obligations is non-commons for OBA purposes.

## B00.CH02.P09.S02 ΔG (growth/quality/capacity) as state variable and metric set

Commons requires a state variable that distinguishes real capacity from nominal funding. OBA uses **ΔG(t)** to represent the change in commons capacity/quality/continuity over time.

Canonical definition:

- **G(t)**: state of the commons at time t, represented as a vector of capacity and quality metrics appropriate to the commons category.
- **ΔG(t) = G(t) − G(t−1)**: change over the defined period.

ΔG is not necessarily “growth”; it includes:

- **build/upgrades** (capacity expansion),
- **maintenance** (preventing degradation; ΔG stabilizing near zero),
- **replacement** (keeping effective capacity intact),
- **resilience improvements** (reducing failure probability and recovery time).

Minimum ΔG metric set (category-dependent, must be declared):

- **capacity metrics**: throughput, coverage, availability of baseline units.
- **quality metrics**: error rates, latency, reliability, safety, clinical outcomes (where applicable).
- **continuity metrics**: uptime, MTTR, redundancy, incident frequency.
- **cost-per-baseline-unit**: cost efficiency for baseline delivery (to detect hidden tolling or capture).

Conformance requirements (binding):

- Any commons object MUST declare its ΔG metric set and measurement procedure.
- Claims of commons improvement MUST reference ΔG (or ΔG-stabilization) outcomes, not merely budgets or inputs.
- If ΔG cannot be measured credibly, commons status MUST fail closed until a compliant metric set and method are provided.

## B00.CH02.P09.S03 Minimum governance: powers, liability, contestability

Commons status requires a governance minimum that prevents commons-washing and capture. Governance is treated as constitutive: without it, access and maintenance obligations are not credible.

Canonical governance minimum (must be explicit):

### (1) Powers (bounded authority)
- authority to allocate resources and enforce boundary rules,
- authority to contract for build/maintenance (with anti-lock-in constraints),
- authority to operate in a defined emergency mode (with sunset/rollback).

### (2) Liability (duty of care)
- clearly assigned accountability for negligence, service failures, conflicts of interest,
- enforceable remedies for users when baseline access is violated,
- sanctionability for misreporting, capture behavior, or procurement abuse.

### (3) Contestability (appeal and audit)
- a defined **dispute/appeal** process for exclusion, pricing, quality failures, or governance abuses,
- transparency requirements sufficient for independent review,
- audit rights and publication of key metrics, decisions, and contracts (subject to privacy-minimalism).

Conformance requirements (binding):

- A commons object MUST identify accountable roles (mandator/owner, steward, operator, auditor) and assign powers and liabilities.
- Commons governance MUST include contestability; “no appeal” regimes are non-commons.
- Governance arrangements that create non-auditable discretion or structural conflicts of interest MUST be treated as capture-risk and may invalidate commons status (fail closed) unless mitigations are binding and verifiable.

## B00.CH02.P09.S04 Public option, hybrid layers and interoperability with markets

OBA treats the **public option** as the minimal operational form of commons in domains where exit options discipline power (especially essentials, networks, and natural monopolies). A public option is not defined by state ownership; it is defined by the ability to provide baseline access under commons rules such that users have a credible alternative to extractive providers.

### Public option (canonical role)
- provides a baseline service that is non-extractive and accessible,
- anchors prices and limits tolling via contestable exit,
- provides a reference implementation for standards and interoperability.

### Hybrid layers (allowed structure)
Commons can coexist with competitive market layers:

- **commons core**: baseline rails/infrastructure/data/protocols under commons governance,
- **competitive edges**: differentiated offerings on top, allowed if they do not undermine baseline access or reintroduce lock-in through the core.

Hybrid is conforming only if the core remains:

- non-extractive (no tolling on baseline),
- interoperable (open standards, portability),
- contestable (no discretionary gatekeeping).

### Interoperability with markets
Interoperability is treated as an anti-lock-in obligation in commons-adjacent domains:

- open interfaces/standards where applicable,
- portability of user state/data/credentials,
- caps on switching frictions and contract lock-ins in baseline domains.

Conformance requirements (binding):

- Commons implementations in power-sensitive domains SHOULD provide a public option or equivalent credible exit mechanism; where absent, the implementation MUST demonstrate an alternative discipline mechanism that is at least as strong and auditable.
- Hybrid models MUST preserve commons-core integrity: competitive layers MUST NOT impose tolls, lock-in, or discriminatory access on the baseline core.
- Interoperability obligations MUST be enforceable; “open” claims without portability and switching feasibility are non-conform for commons status.
