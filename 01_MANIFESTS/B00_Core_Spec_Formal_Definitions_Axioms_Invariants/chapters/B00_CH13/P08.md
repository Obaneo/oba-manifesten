# B00.CH13.P08 — Deprecation: phase-out of terms, rules and modules

This paragraph defines the canon deprecation regime: how OBA phases out terms, rules, and modules without drift, silent breaks, or
compatibility laundering. Deprecation is a governed transition mechanism with explicit timelines, migration paths, and status effects.
When deprecation expires, continued use becomes non-conform.

---

## B00.CH13.P08.S01 — Deprecation notice: timeline, rationale, impact, migration path

Deprecation requires advance notice and a predictable transition path.

### Minimum deprecation notice fields (required)
- **What is deprecated**: term/rule/module identifier(s) and the canon version introducing deprecation.
- **Timeline**: dates for (i) discouragement start, (ii) deprecation effective, (iii) removal or end-of-support.
- **Rationale**: why the element is deprecated (ambiguity, exploit surface, replacement, consolidation).
- **Impact**: what breaks or changes (compatibility tests, measurement methods, registries, reporting obligations).
- **Migration path**: the replacement element(s), bridging/mapping instructions, and required implementation steps.

### Conformance requirements (binding)
- Deprecations MUST be published in changelog + registries and must be citable as canonical artifacts.
- If migration guidance is absent, the deprecation is incomplete and may not be enforced as removal until guidance exists; however,
  claims relying on deprecated elements must disclose deprecation status.

---

## B00.CH13.P08.S02 — Deprecation tags: “discouraged”, “deprecated”, “removed” (canonical)

OBA uses canonical tags to communicate deprecation stage unambiguously.

### Tag semantics (binding)
- **Discouraged**: still supported, but not recommended for new work; migration should begin.
- **Deprecated**: supported only for backward-compatibility within the declared window; new implementations must not adopt it.
- **Removed**: no longer supported; cannot be used for compatibility claims or canonical test satisfaction.

### Conformance requirements (binding)
- Each deprecated element MUST carry an explicit tag in the canon and in registries.
- Implementations MUST publish which deprecated elements they still rely on and the planned migration status within the compatibility window.

---

## B00.CH13.P08.S03 — Sunsets: automatic expiry of temporary exceptions/crisis modes

Temporary exceptions and crisis modes are permitted only if they are time-bounded by default. Sunsets prevent exception stacking and
capture.

### Sunset requirements (minimum)
- **Expiry date**: automatic expiration is mandatory for any temporary exception/crisis regime.
- **Scope**: the precise scope of the exception (what it affects, what it does not affect).
- **Review trigger**: criteria for renewal vs termination, including evidence and impact evaluation.
- **Default termination**: if review does not occur or evidence is missing, the exception expires automatically.

### Conformance requirements (binding)
- Exceptions without sunsets are forbidden and constitute a fork trigger (semantic hollowing risk).
- Renewals must be explicit, versioned acts; indefinite “temporary” regimes are prohibited.

---

## B00.CH13.P08.S04 — Hard stop: expired modules lose compatibility status

Expiration has teeth: when a module/term/rule is removed or an exception sunset expires, compatibility claims must update or fail.

### Hard stop rule
- After expiration/removal:
  - an implementation cannot claim compatibility on the expired element,
  - any compatibility claim that depends on it becomes invalid for that scope.

### Conformance requirements (binding)
- If an implementation continues to rely on removed/expired elements for compatibility-critical behavior, it MUST be treated as
  **non-conform** until migrated.
- Registries MUST automatically downgrade or flag status when expiry conditions are met and no verified migration is recorded.
