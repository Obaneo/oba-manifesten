# B00.CH13.P07 — Backward compatibility: policy and guarantees

This paragraph defines backward compatibility as a governance guarantee that preserves audit continuity and prevents surprise breaks
in implementations. Backward compatibility means: (i) older canon versions remain valid for a defined window, (ii) upgrades must not
silently change outputs without disclosure, and (iii) migrations must be reproducible and bridged where semantics or schemas change.

---

## B00.CH13.P07.S01 — Compatibility windows: how long old versions remain “supported”

OBA must specify support windows so implementations can operate predictably and auditors can reproduce past determinations.

### Compatibility window rule
- Each release MUST declare:
  - which prior versions remain supported,
  - the duration of support (time-bound window),
  - conditions for early end-of-support (e.g., security/integrity incidents, exploit discovery),
  - what “supported” means (audit reproducibility, registry availability, permitted label use).

### Conformance requirements (binding)
- Registries and archives MUST keep supported versions retrievable and verifiable (hash/signature verification must remain possible).
- Claims pinned to supported versions remain valid in principle, subject to auditability and measurement standards.
- Unsupported versions MUST be labeled as such in registries; continued compatibility claims on unsupported versions require explicit exception or upgrade.

---

## B00.CH13.P07.S02 — Compatibility tests: implementations must demonstrate outputs do not break

When implementations upgrade canon versions, they must demonstrate that compatibility-critical outputs remain within acceptable bounds,
or else explicitly declare the break.

### Upgrade testing requirements (minimum)
- **Pinned inputs**: use fixed reference datasets and scenarios representative of the implementation scope.
- **Old vs new comparison**: compute outputs under old and new canon versions using registered methods.
- **Acceptance criteria**:
  - for patch releases: outputs must be identical within strict tolerances (formal equivalence expectation),
  - for minor releases: outputs must remain compatible within declared bands, except where optional modules are adopted,
  - for major releases: breaks are expected; bridging/migration must be published and claims reissued.

### Conformance requirements (binding)
- An implementation MUST NOT assert continuity across versions without publishing upgrade test results and referencing the bridge (if needed).
- If upgrade tests show breaks beyond declared bands and no bridge exists, the implementation’s compatibility status MUST be treated
  as **uncertain** and therefore **non-conform** until corrected (fail-closed).

---

## B00.CH13.P07.S03 — Data and model migration: schema evolution with reproducibility

Version changes often require schema evolution (data fields, encoding, cohort keys, method metadata) and model updates. Migration must
preserve reproducibility and audit lineage.

### Migration requirements (minimum)
- **Schema versioning**: explicit schema IDs/versions for datasets and method outputs.
- **Migration scripts/specs**: versioned procedures for transforming old schema/data to new schema/data.
- **Dual-run period**: where feasible, run old and new pipelines in parallel for validation.
- **Reproducibility**: third parties can reproduce migrated outputs from pinned inputs and the published migration procedure.

### Conformance requirements (binding)
- Migrations MUST be logged, hashed, and auditable; silent data rewrites are forbidden.
- If migration breaks lineage or reproducibility, compatibility-critical decisions MUST be curtailed and status may be suspended
  (fail-closed) until integrity is restored.

---

## B00.CH13.P07.S04 — Ban on silent breaks: breaking changes require major bump + notice

Breaking changes are permitted only when explicitly declared and governed; silent breaks are prohibited.

### Silent-break prohibition
- Any change that can alter:
  - compatibility test outcomes,
  - classification boundaries,
  - parameter bounds/defaults in ways that affect decisions,
  - measurement method semantics or normalisation conventions,
  must not be shipped without explicit version bump and disclosure.

### Conformance requirements (binding)
- Breaking changes MUST be shipped as **MAJOR** releases and MUST include:
  - changelog + diff + impact analysis,
  - bridging/migration guidance,
  - registry updates and implementer notice via canonical channels.
- If a silent break is discovered, canon integrity is compromised: affected status claims MUST be treated as **uncertain** and
  therefore **non-conform** until the break is re-released correctly and audited (fail-closed).
