# B00.CH13.P02 — Release structure and identification (definition-set ID + version)

This paragraph defines how canonical OBA artifacts are released, identified, and verified. Releases must be immutable, uniquely
identifiable, and auditable over time. A release is not “a document state”; it is a formally published artifact with a stable ID,
semantic version, and integrity proofs that allow third parties to verify they are reading the same canon.

---

## B00.CH13.P02.S01 — Versioning scheme: MAJOR.MINOR.PATCH (semantic)

OBA uses **semantic versioning** to classify the meaning-impact of changes and to enforce compatibility discipline.

### SemVer rule
- **MAJOR**: changes that alter invariants, definitions, conflict rules, or otherwise change class meaning (fork risk).
- **MINOR**: extensions within invariants (e.g., new optional modules, parameter-space extensions) that preserve class meaning.
- **PATCH**: clarifications or corrections that do not change meaning; formal equivalence must be demonstrated.

### Conformance requirements (binding)
- Every canonical release MUST carry a SemVer identifier: `MAJOR.MINOR.PATCH`.
- The change class MUST be justified in the changelog; misclassification (e.g., a meaning change shipped as patch) is an integrity breach.
- Implementations MUST declare which SemVer ranges they support; “floating latest” is forbidden for compatibility claims.

---

## B00.CH13.P02.S02 — Release ID: date, hash, signature, immutable artifact

Each release must be uniquely and verifiably identified. OBA requires a release ID that supports tamper-evident verification.

### Mandatory release identity fields (minimum)
- **Release date** (publication date; UTC or declared timezone)
- **Content hash** (hash of the immutable artifact package)
- **Signature** (cryptographic signature by authorized publisher/registrar where required)
- **Immutable artifact pointer** (content-addressed location in registry/archive)

### Conformance requirements (binding)
- A canonical release MUST be immutable: the artifact referenced by the release ID MUST NOT change after publication.
- If hashes/signatures do not verify, or if the artifact is mutable, the release MUST be treated as invalid (fail-closed) until corrected.
- Verification instructions MUST be published with the release (how to verify hash/signature and obtain the artifact).

---

## B00.CH13.P02.S03 — Definition-set ID binding: version binds to definition sets (I–VI) and parameters

A canon version is not only a label; it binds a specific package of definition sets and parameter specifications.

### Binding rule
- Each release MUST declare:
  - the **definition sets** included (e.g., I–VI, or equivalent canonical bundles),
  - the exact **parameter-space specification** (bounds, defaults, and change procedures),
  - the canonical dependencies (Kernel Spec version, Codex/Standards versions, measurement method registry versions where applicable).

### Conformance requirements (binding)
- Any compatibility claim MUST reference the exact definition-set ID + version used (not just “OBA vX”).
- Mixing multiple definition-set versions within one claim scope without explicit partitioning is forbidden and renders the claim non-conform.
- If parameter specifications differ from the bound release without a governed update, this constitutes a fork trigger.

---

## B00.CH13.P02.S04 — Publication channels: registry, archive, mirrors, verification instructions

Canonical releases must be accessible, citable, and resilient to single-point failure. OBA therefore requires multiple publication
channels and clear verification guidance.

### Required publication channels (minimum)
- **Canon registry**: authoritative index of releases and their identities (SemVer, hashes, signatures).
- **Archive**: long-term immutable storage (snapshot, citability, retention guarantees).
- **Mirrors**: redundant copies under independent hosting to prevent disappearance or capture.
- **Verification instructions**: step-by-step guidance to fetch artifacts and verify integrity proofs.

### Conformance requirements (binding)
- A release MUST NOT be treated as canonical unless it is registered and retrievable via the registry + archive pathway.
- If the registry is unavailable or integrity cannot be verified, systems MUST fail closed: treat canon status as suspended until verification is restored.
- Mirrors must be listed in the registry; mirror divergence (different content under same release ID) is an integrity incident.
