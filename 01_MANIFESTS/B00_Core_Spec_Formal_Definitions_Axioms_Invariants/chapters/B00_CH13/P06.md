# B00.CH13.P06 — Bridging: mappings between versions and between forks

This paragraph defines **bridging**: explicit, versioned mapping artifacts that translate terms, parameters, and metrics across canon
versions and across forks. Bridging is necessary for migration and comparison, but it is also a drift risk. Therefore, bridges must
be explicit, testable, and constrained: a bridge may describe correspondence and limitations; it must not silently redefine canon.

---

## B00.CH13.P06.S01 — Bridge documents: explicit translation of definitions/parameters/metrics

A bridge document is a formal annex that maps between a **source** canon (or fork) and a **target** canon (or fork).

### Minimum bridge contents (required)
- **Source identity**: definition-set ID + version (and fork ID where applicable).
- **Target identity**: definition-set ID + version (and fork ID where applicable).
- **Term mapping**:
  - old term → new term mapping, including “no mapping” and “one-to-many/many-to-one” cases,
  - notes on boundary changes and classification consequences.
- **Parameter mapping**:
  - old parameter → new parameter mapping, including bounds changes and default shifts,
  - explicit rule for translating in-bound/out-of-bound values.
- **Metric mapping**:
  - old metric definition → new metric definition mapping,
  - restatement of computation rules and normalisation conventions,
  - declared lossiness where exact translation is impossible.
- **Scope and limits**:
  - what the bridge guarantees (and does not guarantee),
  - known non-equivalences and failure modes.

### Conformance requirements (binding)
- Any cross-version comparability claim MUST cite a bridge document when semantics differ or when outputs are compared across versions.
- If mapping is missing or incomplete, cross-version/fork claims MUST be treated as **uncertain** and therefore **non-conform**
  (fail-closed) for compatibility-relevant uses.

## B00.CH13.P06.S02 — Use cases: sector canvases, jurisdiction implementations, dataset migrations

Bridges are required whenever semantics or schema change affects downstream artifacts.

### Primary use cases (non-exhaustive)
- **Sector canvases**: maintaining sector-level mappings when canonical definitions or parameters evolve.
- **Jurisdiction implementations**: translating local implementations pinned to older versions into newer canon versions.
- **Dataset migrations**: migrating stored datasets, schemas, and measurement pipelines across definition/method changes.
- **Audit continuity**: enabling auditors to re-evaluate prior determinations under new canon without retroactive semantic confusion.

### Conformance requirements (binding)
- Any implementation upgrade that changes version pins MUST either:
  - demonstrate equivalence (patch/restatement path), or
  - provide a bridge + migration evidence (minor/major path).
- Where datasets are migrated, both pre- and post-migration artifacts MUST be versioned and reproducible.

---

## B00.CH13.P06.S03 — Correctness criteria: preserve invariant claims or explicitly declare a break

Bridges must be correct in a precise sense: they must not claim equivalence where invariant meaning differs.

### Correctness criteria (minimum)
- **Invariant preservation**: if the source and target share the same invariants (and meaning), the bridge must preserve invariant-relevant claims.
- **Explicit break declaration**: if invariants differ, the bridge MUST declare the break and must not assert compatibility equivalence.
- **Outcome stability bands**: where translation is approximate, the bridge must declare tolerance bands and uncertainty, and specify
  which comparisons remain valid.

### Conformance requirements (binding)
- A bridge MUST never be used to “smuggle” a fork into OBA compatibility via loose mappings.
- If invariant deltas exist, any claim of compatibility equivalence is forbidden; only limited interoperability claims with explicit
  limitations are permitted.

---

## B00.CH13.P06.S04 — Interoperability: a bridge is an annex, not a new canon (no shadow definitions)

Bridges are supporting artifacts; they must not become alternative sources of meaning.

### Rule
- A bridge is an **annex**: it references source and target canons; it does not define a third semantic system.
- Bridge documents MUST NOT introduce new normative definitions outside what is required to express mapping; any new definition is a
  drift vector and is prohibited unless elevated through canonical governance.

### Conformance requirements (binding)
- Bridge documents MUST not be treated as canonical definitions; they must point back to canonical sources on both sides.
- If a bridge introduces shadow definitions or is used as a substitute for canonical sources, it is a prohibited shadow canon and
  triggers fail-closed suspension of dependent comparability/compatibility claims until corrected.
