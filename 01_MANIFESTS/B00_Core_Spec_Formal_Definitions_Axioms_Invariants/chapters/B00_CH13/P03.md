# B00.CH13.P03 — Change classes: what counts as patch/minor/major

This paragraph defines the formal **change classes** used to govern canon evolution under semantic versioning. The change class is
not a release-note label; it is a binding classification that determines compatibility continuity, audit reproducibility, and fork
risk. Misclassifying a change (shipping meaning change as patch/minor) is treated as an integrity breach.

---

## B00.CH13.P03.S01 — Patch: clarification without meaning change (formal equivalence must be shown)

A **patch** is permitted only when the change does not alter meaning, requirements, or test outcomes under the canon’s intended
interpretation.

### Patch characteristics
- Clarifies wording, resolves ambiguity, fixes typos, corrects references, or improves structure **without changing semantics**.
- May add examples or explanatory text that is explicitly non-normative and does not constrain interpretations beyond the existing canon.

### Formal equivalence requirement
- Patch releases MUST demonstrate **formal equivalence**:
  - no change in definitions’ extension/intension,
  - no change in invariants,
  - no change in compatibility tests’ pass/fail conditions for the same inputs.

### Conformance requirements (binding)
- A patch MUST include a proof/argument of equivalence (as specified by Codex/Standards), and a diff that supports the claim.
- If equivalence cannot be shown, the change MUST be classified as minor or major, or rejected.

---

## B00.CH13.P03.S02 — Minor: parameter extension or new optional module within invariants

A **minor** release adds capability without changing the OBA class meaning.

### Minor characteristics
- Extends **parameter space** within invariant rails (e.g., adds allowed parameter ranges, new indexation options, additional time resolutions).
- Adds **new optional modules** (canonically defined) that do not alter core requirements for compatibility labels unless adopted.
- Adds new measurement methods or templates that implement existing canonical objects without redefining them.

### Conformance requirements (binding)
- Minor releases MUST preserve invariants and must not redefine canonical terms.
- Minor releases MUST declare:
  - what is new,
  - whether adoption is optional vs required,
  - any new metadata requirements for claims that opt in.
- Backward compatibility expectations MUST be stated (what remains valid, what requires bridging for comparability).

---

## B00.CH13.P03.S03 — Major: change to an invariant, definitions, or conflict rules (fork risk)

A **major** release changes meaning: it alters what OBA is, what it requires, or how conflicts are resolved.

### Major triggers (non-exhaustive)
- Any change to an **invariant** (P/E/C function, R/B structure, cap principles, forbidden channels, commons order properties).
- Any change to **canonical definitions** that changes scope, boundaries, or classification outcomes.
- Any change to **conflict rules** (source hierarchy, fail-closed semantics, dispute primitives).
- Any change that alters compatibility test logic in a way that can change pass/fail outcomes for the same inputs.

### Conformance requirements (binding)
- Major releases MUST include:
  - explicit invariant delta list,
  - impact analysis on compatibility and audits,
  - bridging/restatement plan for continuity where possible.
- Major releases MUST be treated as **fork-risk events**: implementations must explicitly opt in and update compatibility claims accordingly.

---

## B00.CH13.P03.S04 — Prohibited change: retroactive semantics without restatement/bridge

Certain change patterns are forbidden because they destroy audit reproducibility and enable silent drift.

### Prohibited patterns (non-exhaustive)
- **Retroactive semantics**: changing the meaning of past releases by editing or reinterpreting them without a new release.
- **Silent breaks**: altering tests, parameters, or definitions in a way that changes outcomes without a major bump and disclosure.
- **Unmapped rewrites**: rewriting definitions or rules without publishing a mapping from old to new (restatement/bridge).

### Conformance requirements (binding)
- Any change that would alter historical interpretation MUST be issued as a new release and MUST be accompanied by:
  - a restatement (if formally equivalent) or
  - a bridge document (if meaning differs), including correctness criteria and limitations.
- If retroactive semantics are detected (mutable canon or silent edits), canon integrity is suspended and systems MUST fail closed until
  integrity is restored.
