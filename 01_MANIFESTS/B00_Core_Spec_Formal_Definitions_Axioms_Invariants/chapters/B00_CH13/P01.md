# B00.CH13.P01 — Purpose, scope and normative status of version control

This paragraph defines canon version control as a **normative requirement** in OBA. OBA is a formal class with testable requirements;
that class can only be enforced if the meaning of its sources is stable, citable, and resistant to silent mutation. Version control
is therefore not tooling preference but governance: it specifies what counts as canonical, how it changes, and how integrity is
proved over time.

---

## B00.CH13.P01.S01 — Version control as order invariant: semantic stability is enforceability

Semantic stability is a prerequisite for enforcement. If canonical meaning can change without explicit release, changelog, and
verifiable identity, then audits cannot reproduce prior determinations and compatibility claims become non-testable.

### Core rule
- **No stable semantics → no enforceability**: any claim, audit, or dispute resolution requires immutable references to specific
  versions of canonical sources.

### Conformance requirements (binding)
- Canonical artifacts MUST be released as immutable, version-identified publications (no mutable “living canon”).
- Any compatibility claim MUST reference the specific definition-set ID + version; ambiguity in version identity invalidates the
  claim (fail-closed).
- Silent edits to canonical artifacts are forbidden; detection of silent edits triggers integrity failure handling (see hard stops).

---

## B00.CH13.P01.S02 — Purpose: controlled evolution without drift, without “shadow canons”

Version control exists to enable evolution while preventing drift and fragmentation.

### Purposes (minimum)
- **Controlled evolution**: allow improvements, clarifications, and extensions through governed releases.
- **Anti-drift**: prevent meaning shifts through informal rewrites, re-interpretations, or partial documents.
- **Anti–shadow canon**: prevent parallel, semi-official sources from acquiring de facto authority outside the release process.
- **Dispute operability**: make disagreements resolvable by pointing to versioned artifacts and diffs.

### Conformance requirements (binding)
- Any change that materially affects meaning, requirements, or tests MUST be processed through the release procedure and classified
  by change class (patch/minor/major).
- Any artifact that functions as a competing source of meaning without being released and registered is a prohibited shadow canon.

---

## B00.CH13.P01.S03 — Scope: Kernel Spec, definition sets, parameters, Codex/Standards, measurement methods

Version control applies to all sources that affect compatibility claims, audit procedures, or enforcement outcomes.

### Covered artifacts (minimum)
- **Kernel Spec**: canonical definitions, invariants, conflict rules.
- **Definition sets** (I–VI or equivalent): the packaged canonical term sets used in implementations.
- **Parameters**: allowed parameter spaces, defaults, and bound changes (including change procedures and sunsets).
- **Codex / Standards**: operational schemas, templates, and audit procedures that implement canonical objects.
- **Measurement methods**: registered measurement procedures, normalisation conventions, uncertainty regimes, and reproducibility artifacts.

### Conformance requirements (binding)
- Each covered artifact MUST have: identifier, version, release record, changelog, and integrity proof where required.
- Implementations MUST pin to specific versions of these artifacts; floating references (“latest”) are not permitted for compatibility claims.

---

## B00.CH13.P01.S04 — Relation to compatibility, forks, auditability and publication requirements

Version control is the backbone that makes compatibility, fork governance, and auditability possible.

### Relations
- **Compatibility**: compatibility is a claim about conformance to a specific canon version; version identity is mandatory claim metadata.
- **Forks**: forks are semantic branches; they must be declared and versioned, with explicit invariant deltas and bridging docs if interoperating.
- **Auditability**: audits require reproducible reference artifacts; versioned releases enable re-running past audits.
- **Publication requirements**: public registers, changelogs, diffs, and immutable archives make claims contestable.

### Conformance requirements (binding)
- Any compatibility label or audit finding MUST reference the canon versions used (definition-set ID + version, plus relevant Codex/method versions).
- Where version identity is missing, disputed, or compromised, status MUST be treated as **uncertain** and therefore **non-conform**
  until integrity is restored (fail-closed).
