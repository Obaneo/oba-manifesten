# B00.CH13.P05 — Restatements: canonical rephrasings without substantive change

This paragraph defines **restatements**: canonical rephrasings intended to improve readability, modular integration, or editorial
consistency without changing meaning. Restatements are high-risk drift vectors; therefore OBA permits them only under strict formal
equivalence and traceability rules. A restatement is not a “new interpretation” and must not introduce any semantic delta.

---

## B00.CH13.P05.S01 — Purpose: readability and integration without drift

Restatements exist to improve the usability of the canon while preserving semantics.

### Permitted purposes (non-exhaustive)
- Improve readability, structure, and cross-referencing.
- Integrate scattered definitions into a clearer canonical layout.
- Harmonize terminology and editorial style while preserving canonical meaning.
- Provide consolidated canonical text for implementers without changing requirements.

### Conformance requirements (binding)
- A restatement MUST explicitly declare that it is a restatement and MUST reference the source version being restated.
- Restatements MUST NOT be used to “fix” semantic problems; semantic changes require minor/major releases (per change-class rules).

---

## B00.CH13.P05.S02 — Permissibility: only with demonstrable formal equivalence

A restatement is permitted only if formal equivalence can be demonstrated relative to the referenced source version.

### Formal equivalence criteria (minimum)
- No change to:
  - the extension/intension of definitions (what is included/excluded),
  - invariants and their enforcement logic,
  - compatibility tests’ pass/fail conditions for the same inputs,
  - parameter bounds and change procedures.
- Any added explanatory text must be explicitly marked non-normative unless it already exists as normative in the source.

### Conformance requirements (binding)
- Restatements MUST include an equivalence demonstration (proof or structured argument per Codex/Standards).
- If equivalence cannot be shown, the artifact MUST NOT be labeled a restatement and MUST instead be processed as a semantic change
  (minor/major) or rejected.

---

## B00.CH13.P05.S03 — Traceability: restatement references source version + proof of equivalence

Restatements must be fully traceable so auditors can map from restated text back to the exact canonical sources.

### Traceability requirements (minimum)
- **Source pointer**: source definition-set ID + version and artifact path/anchors.
- **Restatement ID**: unique identifier and version for the restatement artifact.
- **Mapping**: section-by-section mapping from source to restated text (anchors), including moved/merged/split sections.
- **Equivalence proof**: attached proof/argument and the test suite used to validate equivalence where applicable.
- **Integrity proofs**: hashes/signatures consistent with the release identity regime.

### Conformance requirements (binding)
- A restatement without mapping and equivalence proof MUST be treated as non-canonical for compatibility purposes.
- Implementations MUST reference the underlying source version for semantic claims; restatement text may be used as a reading layer
  only if traceability is maintained.

---

## B00.CH13.P05.S04 — Hard stop: a restatement that shifts meaning = major change (fork/ratification)

A restatement that alters meaning is not a restatement. It is a semantic change and therefore a major governance event.

### Hard stop rule
- If a restatement changes:
  - definition boundaries,
  - invariants,
  - conflict rules,
  - test outcomes for the same inputs,
  then it constitutes a **major change** (fork/ratification risk).

### Conformance requirements (binding)
- Detected semantic drift in a claimed restatement triggers:
  - invalidation of the restatement as canonical,
  - reclassification of the change as major,
  - required publication of changelog, diffs, and impact analysis,
  - and, where applicable, explicit fork declaration if consensus/ratification is not obtained.
- Until resolved, any claims relying on the drifted restatement MUST be treated as **uncertain** and therefore **non-conform**
  (fail-closed).
