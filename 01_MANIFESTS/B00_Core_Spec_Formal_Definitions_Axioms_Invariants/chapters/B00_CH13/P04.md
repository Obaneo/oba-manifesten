# B00.CH13.P04 — Changelog requirements (transparency and impact)

This paragraph defines mandatory **changelog** and **diff** requirements for canon releases. A release without a high-integrity
changelog is not auditable: third parties cannot determine what changed, why it changed, or whether compatibility claims remain valid.
Changelogs are therefore normative artifacts, not optional release notes.

---

## B00.CH13.P04.S01 — Minimum fields: what, why, who, date, review, tests, impact on invariants

Every canon release MUST include a changelog entry with a minimum structured field set.

### Minimum changelog fields (required)
- **Release identifier**: definition-set ID + version (and release ID: date/hash/signature pointer).
- **What changed**: concise enumeration of changes, grouped by artifact (Kernel/definition sets/parameters/Codex/methods).
- **Why changed**: rationale for each change (problem addressed, ambiguity resolved, extension needed).
- **Who**: editor/author, reviewers, ratifiers (roles and identifiers as defined by governance).
- **When**: publication date; effective date if different.
- **Review record**: review criteria applied; approvals/quorum notes for major changes.
- **Tests**: compatibility/audit tests run on the release artifacts; results summary and pointers to test artifacts.
- **Impact on invariants**: explicit statement:
  - “no invariant impact” for patch/minor, or
  - invariant delta list for major.

### Conformance requirements (binding)
- If any minimum field is missing, the release MUST be treated as incomplete and non-canonical for compatibility purposes until corrected.
- The changelog MUST be immutable and versioned with the release.

---

## B00.CH13.P04.S02 — Diff publication: text diff + formal mapping (old→new terms/rules)

Changelogs must be backed by concrete diffs and explicit semantic mappings.

### Diff requirements (minimum)
- **Text diff**: a human-readable diff showing changes in normative text and schemas.
- **Formal mapping**: an explicit mapping from old to new for:
  - renamed terms,
  - modified definitions,
  - altered rules/tests,
  - parameter-space changes,
  - deprecated/removed elements.

### Conformance requirements (binding)
- Any change that affects definitions, rules, or metrics MUST provide a formal mapping (old→new) sufficient to support bridging and migration.
- If mapping is absent, dependent implementations cannot demonstrate continuity; compatibility status must be treated as uncertain and
  therefore **non-conform** (fail-closed).

---

## B00.CH13.P04.S03 — Impact analysis: effects on R/B, P/E/C, caps, ΔM, commons and auditability

Changes must be assessed for their downstream effects on the core evaluation objects and on auditability.

### Minimum impact analysis scope (required)
- **R/B**: expected changes in computation, cohort definitions, thresholds, distributions, or reporting.
- **P/E/C**: effects on classification, decomposition, allocation rules, and observables.
- **Caps (W/I)**: effects on bases, valuations, thresholds, exemptions, enforcement logic.
- **ΔM channels**: effects on channel definitions, prohibited channels, leakage tests, routing rules.
- **Commons**: effects on commons order properties, observables, ΔG reporting, access/maintenance requirements.
- **Auditability**: effects on lineage, reproducibility, method registration, and minimum publication requirements.

### Conformance requirements (binding)
- Minor and major releases MUST include an impact analysis; patch releases MUST include an explicit “no semantic impact” justification.
- If impact analysis is missing for changes that plausibly affect outcomes, the release is incomplete and triggers fail-closed treatment
  for compatibility claims depending on the affected artifacts.

---

## B00.CH13.P04.S04 — Communication: compatibility-label updates and public summary without marketing

Canonical changes affect how status labels are used and interpreted. Communication must therefore be factual, versioned, and non-promotional.

### Communication requirements (minimum)
- **Compatibility-label implications**: state whether any label criteria, tests, or evidence requirements changed.
- **Implementation guidance**: what implementers must do (pin versions, migrate, run tests, update registers).
- **Public summary**: a concise summary of changes and their intent, without rhetorical marketing claims.
- **Correction duty**: if prior public claims are invalidated by the change, publish rectifications and update registers.

### Conformance requirements (binding)
- Releases MUST not be accompanied by “marketing summaries” that contradict or exceed the changelog; public summaries must reference
  the canonical changelog and diffs.
- If label criteria change, registries MUST be updated and implementers must be notified through the canonical channels; silent label
  changes are forbidden and constitute an integrity breach.
