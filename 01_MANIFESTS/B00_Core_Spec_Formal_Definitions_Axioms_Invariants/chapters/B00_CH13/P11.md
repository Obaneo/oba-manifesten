# B00.CH13.P11 — Registers and proof of integrity

This paragraph defines the required registers and integrity proofs that make OBA canon and compatibility claims verifiable over time.
Registers are not administrative extras; they are the public substrate that prevents silent edits, shadow canons, and unverifiable
status claims. Integrity is proven through immutable artifacts, cryptographic identity, provenance records, and long-term archiving.

---

## B00.CH13.P11.S01 — Canon registry: list of releases, hashes, signatures, mirrors

The canon registry is the authoritative index of what counts as canonical and how to verify it.

### Canon registry minimum fields (required)
- **Release identity**: definition-set ID + version; release date.
- **Integrity proofs**: content hash(es) and signature(s); verification keys/chain where applicable.
- **Artifact pointers**: immutable locations for the release package (registry pointer + archive pointer).
- **Mirrors**: independent mirror locations and their verification procedure.
- **Change metadata**: change class (patch/minor/major), changelog pointer, diff pointer, impact analysis pointer.

### Conformance requirements (binding)
- No artifact is canonical unless listed in the canon registry with verifiable integrity proofs.
- If hashes/signatures fail, or mirrors diverge, canon status is suspended for the affected release until resolved (fail-closed).
- Registry entries are immutable; corrections are made via new entries/revisions with explicit records, not by overwriting history.

## B00.CH13.P11.S02 — Compatibility registry: implementations, status, exceptions, audit results

The compatibility registry makes status claims discoverable and prevents compatibility-by-branding.

### Compatibility registry minimum fields (required)
- **Implementation identifier** (and jurisdiction/sector scope where relevant).
- **Status label** (OBA-conform / OBA-compatible / OBA-inspired / non-conform / fork).
- **Claim scope**: modules, sectors, jurisdictions, time window.
- **Canon pins**: definition-set ID + version (and relevant Codex/Standards and method versions).
- **Evidence bundle pointers**: methods, core statistics, uncertainty, lineage references.
- **Exceptions**: published exceptions with canonical basis, scope, sunset, review outcome.
- **Audit results**: audit dates, scope, findings, remediation status; suspensions/downgrades with rationale.
- **Change history**: status changes and version migrations.

### Conformance requirements (binding)
- Any public compatibility claim MUST correspond to a compatibility registry entry; otherwise it is treated as non-conform.
- Unpublished exceptions are forbidden and constitute a fork/capture trigger.
- Audit outcomes affecting status MUST be reflected in the registry without delay.

## B00.CH13.P11.S03 — Provenance: who published what and when (tamper evidence)

Provenance records establish authorship, responsibility, and tamper evidence for canon and status declarations.

### Provenance requirements (minimum)
- **Publisher identity**: who published the release/entry (role, mandate, signing identity).
- **Timestamp**: when it was published and when it became effective.
- **Approval trail**: reviewers/ratifiers and decision thresholds (quorum/supermajority where applicable).
- **Linkage**: association between canon releases and dependent registry updates (compatibility changes, deprecations, incident notices).

### Conformance requirements (binding)
- Provenance must be verifiable (signed entries or equivalent integrity mechanism).
- If provenance is missing or unverifiable for a canon release or status entry, the artifact/claim MUST be treated as **uncertain**
  and therefore cannot ground compatibility privileges (fail-closed).
- Key compromise or identity ambiguity triggers incident procedure and may require re-signing/re-publication.

---

## B00.CH13.P11.S04 — Archiving: long-term access, citability, immutable snapshots

OBA requires long-term access to past canon and evidence so audits and disputes remain reproducible over time.

### Archiving requirements (minimum)
- **Immutable snapshots**: archived release packages and evidence bundles as content-addressed artifacts.
- **Citability**: stable identifiers suitable for reference in audits, disputes, and public communication.
- **Retention policy**: declared retention windows (at least for supported versions, and longer for historic audit reproducibility).
- **Access resilience**: multiple archives/mirrors; documented retrieval and verification instructions.

### Conformance requirements (binding)
- If archived access is lost or artifacts become non-retrievable, affected canon/status claims MUST be treated as **non-verifiable**
  and therefore **non-conform** for compatibility grounding until access is restored (fail-closed).
- Archives must preserve history; removals or redactions must be recorded as events with justification and alternative verification routes.
