# B03.CH03.P05 — Mandate operationalisation: from promise to testable assignment

In OBA, a mandate is not “what we intend to do,” but a **testable assignment** with explicit rails, evidence duties, and
pre-committed correction paths. Operationalising a mandate means translating political language into (i) measurable targets on the
OBA test axes, (ii) auditable definitions and methods, (iii) sequencing that separates binding steps from evaluation moments, and
(iv) an exception regime that cannot silently erode invariants. This paragraph specifies the minimum translation rules that turn a
mandate into an executable, reviewable contract.

---

## B03.CH03.P05.S01 — Mandate text in test axes: E, caps, commons/ΔG, R/B, ΔM

Mandate text must be expressed in the canonical axes so that the system can distinguish legitimate parameter choices from
constitutive rail changes. Each mandate must make explicit what is being optimised, what is bounded, and what constitutes failure.

### Conformance requirements (binding)
- A mandate MUST be expressed as a set of claims on **E, caps, commons/ΔG, R/B, and ΔM**, each with:
  - a target direction (↑/↓/bound/maintain),
  - a measurement object (what is counted),
  - a method reference (where the calculation rules live),
  - and an audit hook (logs/registers required).
- If a mandate cannot be mapped to the axes without redefining terms, it MUST be treated as **underspecified** and cannot be
  executed as an OBA mandate (fail-closed).
- Any implied constitutive change (definitions, bindingness, audit access, boundary rules) MUST be separated out and routed through
  constitutive mandate procedures.

---

## B03.CH03.P05.S02 — KPIs without gaming: red flags, uncertainty bands, “unknown” discipline

OBA treats KPI design as a risk surface: narrow metrics invite Goodharting, proxy laundering, and selective enforcement. KPIs must
therefore be paired with **red-flag indicators**, explicit uncertainty handling, and rules that preserve measurement integrity
under pressure.

### Conformance requirements (binding)
- Every KPI MUST declare:
  - what it measures,
  - what it does *not* measure (known blind spots),
  - and which failure modes it can be gamed through.
- KPI reporting MUST include **uncertainty bands** where measurement is model-based or sample-based, and MUST permit an explicit
  **“unknown”** state when confidence is insufficient.
- A mandate MUST define a minimum set of **red flags** (e.g., exception ratio↑, sanction rate↓, reproducibility↓, near-cap
  clustering) that trigger enhanced audit or hard stops.

---

## B03.CH03.P05.S03 — Timeline and sequencing: binding steps versus evaluation moments

Operational mandates require explicit sequencing so politics cannot retroactively relabel failure as “not yet evaluated,” and so
implementation cannot outrun auditability. The key distinction is between **binding commitments** (must happen unless formally
rolled back) and **evaluation checkpoints** (where continuation is conditional).

### Conformance requirements (binding)
- The mandate MUST specify:
  - binding steps (what must be done, by when),
  - evaluation moments (when the evidence is reviewed),
  - and stop/adjust thresholds (what evidence triggers change).
- Any step that materially affects caps, commons access, or ΔM allocation MUST not precede the availability of minimum audit inputs
  (definitions, logging, registers).
- Sequencing MUST include an explicit rule for regression risk: if drift signals trigger, the default action is **pause or rollback**
  unless explicitly overridden by a valid emergency mandate.

---

## B03.CH03.P05.S04 — Exception discipline: sunsets/rollback fixed in advance

Exceptions are the primary channel through which mandates become hollow. OBA therefore requires exception handling to be pre-bound
as part of the mandate: what exceptions are possible, for how long, under which evidence, and how reversal works.

### Conformance requirements (binding)
- Any allowed exception MUST have:
  - a scope definition,
  - a time-bounded sunset,
  - non-stackability constraints,
  - and explicit rollback conditions (technical/contractual reversibility).
- Renewal MUST require a higher threshold than the initial exception (re-authorisation), and renewals MUST be logged as renewals
  (no relabeling).
- If rollback is not technically feasible (vendor lock-in, missing logs), the mandate MUST treat the pathway as **prohibited** until
  reversibility is restored.

---

## B03.CH03.P05.S05 — Public scorecards: definitions, baseline, restatements

Mandates remain contestable only if progress can be independently checked. Public scorecards are therefore a mandatory interface:
they publish baseline, definitions, and trend outputs in a format that supports replication and correction without propaganda.

### Conformance requirements (binding)
- A mandate MUST publish a scorecard with:
  - the definition set + version references used,
  - baseline values and measurement periods,
  - trend outputs per axis (E/caps/ΔG/RB/ΔM),
  - and the escalation status (normal / enhanced audit / hard stop).
- Corrections MUST be handled via **restatements** with bridging notes; historical series must not be silently rewritten.
- If public reporting is blocked or materially delayed, the mandate enters **non-conform risk status** and triggers the predefined
  escalation path (audit intervention / pause / rollback depending on severity).
