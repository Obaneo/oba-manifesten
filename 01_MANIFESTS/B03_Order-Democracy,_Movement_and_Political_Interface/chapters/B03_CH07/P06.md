# B03.CH07.P06 — Registries and version control: traceability over time and jurisdictions

This paragraph outlines the essential **registries and version control mechanisms** necessary for ensuring **traceability** of
forks, variants, and extensions over time and across jurisdictions. The use of **unique IDs**, **version pinning**, and **interoperability**
ensures that changes are **trackable**, **compatible**, and **reversible** where needed.

## Core principles
- **Traceability**: Every fork or variant must be **uniquely identifiable** and its **history** must be fully trackable.
- **Backward compatibility**: Changes must be **compatible** with previous versions, and clear rules must be in place for how
  compatibility is maintained over time.
- **Cross-border compatibility**: The system must account for **inter-jurisdictional consistency**, ensuring that forks and variants
  remain compatible across different legal and regulatory environments.

---

## B03.CH07.P06.S01 — Fork registry: unique IDs, scope, status, date, rationale

Each fork, variant, or extension must be **registered** with a **unique ID** and must include the **scope**, **status**, **date**, and
**rationale** for the change. This ensures that each change is **well-documented** and can be **referenced** in the future.

### Core principles
- **Unique IDs**: Every fork, variant, or extension must have a **unique identifier** to track its changes.
- **Scope and status**: The **scope** of the change (e.g., global, jurisdictional) must be clearly stated, along with its current
  **status** (e.g., active, deprecated).
- **Date and rationale**: The **date** of the change and the **rationale** for the change must be included to provide **historical context**.

### Conformance requirements (binding)
- A **fork registry** must be maintained with all required metadata for each **change**, ensuring that every change can be
  **referenced** and its **history traced**.

---

## B03.CH07.P06.S02 — Definition sets: version pinning and backward compatibility rules

A **definition set** must be versioned and **backward-compatible**. Changes to definitions must be documented with **version pinning**
to ensure consistency over time. If a definition is modified, **previous versions** must remain **referable** and **operable**.

### Core principles
- **Version pinning**: Each change to a definition or set of definitions must be **versioned** to ensure that older versions
  remain valid.
- **Backward compatibility**: New versions of definitions must maintain **compatibility** with previous versions or provide
  **migration paths** for users of the old versions.

### Conformance requirements (binding)
- Any **modification to a definition set** must include **clear version control**, and any non-backward-compatible changes must
  have **migration paths** for users of older versions.

---

## B03.CH07.P06.S03 — Bridging: mapping between variants for comparison and migration

When variants diverge, a **bridging process** must be in place to map the changes between the **different variants**. This allows
for **comparisons**, **migration**, and **integration** of new versions with existing systems or frameworks.

### Core principles
- **Mapping variants**: A clear **mapping** of changes must be established to facilitate comparisons between variants.
- **Migration support**: The process should allow for **easy migration** of users or systems from one version to another.

### Conformance requirements (binding)
- **Bridging documents** must be published to allow **comparison** and **migration** between versions of the system.

---

## B03.CH07.P06.S04 — Deprecation: sunset of failed forks/variants, migration paths

Any **failed** or **deprecated** forks or variants must be clearly marked with a **sunset date** and **migration path** to ensure that
legacy versions can transition smoothly to newer, supported versions.

### Core principles
- **Deprecation**: Any fork or variant that is no longer considered valid or supported must be clearly **deprecated**.
- **Sunset date**: A **sunset date** must be set for deprecated versions to allow users ample time to migrate to the newer version.
- **Migration paths**: A **clear migration path** should be provided to guide users through the transition process.

### Conformance requirements (binding)
- All deprecated forks or variants must have an **official deprecation notice** and **migration path** to ensure **smooth transitions**.

---

## B03.CH07.P06.S05 — Interoperability: minimum cross-border compatibility metadata

For variants and forks to work across **jurisdictions**, **cross-border compatibility** rules must be defined. These rules will provide
the **minimum metadata** necessary to ensure **interoperability** between forks and variants across different legal and regulatory
environments.

### Core principles
- **Cross-border compatibility**: Each fork or variant must be compatible across **jurisdictions**, taking into account
  **different legal** and **regulatory requirements**.
- **Compatibility metadata**: The **minimum metadata** necessary for cross-border compatibility must be clearly defined and
  included in each variant's registry.

### Conformance requirements (binding)
- Every fork or variant must include **compatibility metadata** to ensure its **interoperability** across jurisdictions.
