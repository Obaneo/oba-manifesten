# B03.CH04.P10 — Evaluation and version control: learning without a core break

This paragraph defines the **evaluation loop** and **version discipline** for commons-democracy so it can learn from operations,
incidents, and parameter tuning without eroding constitutive rails. Commons governance is a live system: access pressures shift,
maintenance backlogs accumulate, vendor strategies evolve, and political cycles try to bend scarcity rules into carve-outs. If
learning is unmanaged, it becomes drift: quiet redefinitions, exception stacking, and metric gaming. Therefore evaluation must be
structured as (i) a **dashboard minimum** that makes capture and gating observable, (ii) an **incident review protocol** that forces
root-cause and remedy, (iii) a **traceable changelog** that distinguishes parametric tuning from constitutive changes, (iv) a **fork
threshold** with naming rules when governance deviates from rails, and (v) a **handover** of required signals into the democratic
consistency test (B03.CH12).

---

## B03.CH04.P10.S01 — Dashboard minimum: access, quality, maintenance, gating signals

A commons that cannot be observed cannot be governed; a commons that is only observed on output metrics can be captured.

### Dashboard minimum (non-exhaustive)
- **Access**: eligibility counts, denials by category, queue times, prioritisation outcomes, appeal volumes/outcomes.
- **Quality**: uptime/reliability, coverage, failure rates, user-reported defects (with anti-spam rails).
- **Maintenance**: backlog size/age distribution, maintenance spend vs plan, lifecycle compliance, incident recurrence.
- **Gating/toll proxies**: paid priority attempts, bundling pressure, vendor exclusivity, “service tiers” drift, exception ratio.
- **Contestability**: time-to-decision on complaints, audit coverage, reproducibility checks, refusal patterns.

### Conformance requirements (binding)
- The dashboard MUST be public at an appropriate aggregation level and MUST be version-pinned to the definition set used.
- Metrics MUST include uncertainty bands and “unknown” reporting where measurement is incomplete; hiding unknowns is non-conform.

## B03.CH04.P10.S02 — Incident reviews: root cause, recovery plan, sanctions where appropriate

Incidents are governance facts, not PR problems; the purpose is restoration and prevention, not narrative control.

### Incident review protocol (minimum)
- **Triggering**: service minima breach, gating attempt, audit anomaly, exception spike, reproducibility failure.
- **Root-cause taxonomy**: operational failure, maintenance neglect, vendor breach, governance failure, capture interference.
- **Recovery plan**: timeline, responsible roles, budget impact, interim continuity steps, rollback actions if needed.
- **Sanctions path**: when abuse or negligence is confirmed, apply sanctions proportional to harm and recurrence.

### Conformance requirements (binding)
- Every material incident MUST produce a published incident report and MUST update the decision log and exception register.
- “No-fault” framing MUST NOT be used to bypass accountability when governance or vendor behaviour is causal.

## B03.CH04.P10.S03 — Parameter changes: thresholds/rules within rails (traceable changelog)

Commons governance needs tuning (rates, thresholds, prioritisation weights), but tuning must remain inside rails.

### Change management (minimum)
- **Change proposal**: parameter delta, rationale, expected impact, distributional note, and measurement plan.
- **Compatibility check**: confirm no constitutive rail is altered (access default, anti-toll rules, contestability, auditability).
- **Changelog entry**: version ID, effective date, backward compatibility notes, deprecation/migration path if applicable.

### Conformance requirements (binding)
- Parameter changes MUST be reversible (rollback-ready) unless explicitly justified and authorised under a higher threshold.
- Any change that affects measurement definitions MUST include restatements/bridging to preserve time-series comparability.

## B03.CH04.P10.S04 — Forks: when commons governance becomes a variant and how to label it

Not all divergence is drift; some divergence is legitimate variation. The constraint is that variation must be **declared**.

### Fork/variant threshold signals
- **Constitutive deviation**: introduction of paid priority, structural carve-outs, weakened appeal rights, black-box allocation.
- **Auditability loss**: closed computation rules, refusal of replication, missing logs, vendor “trust us” regimes.
- **Exception normalisation**: repeated renewals without sunsets, stacking exceptions to simulate a new baseline.

### Conformance requirements (binding)
- If a constitutive deviation occurs, the commons governance MUST be classified (extension/variant/fork) and MUST be labeled publicly.
- Continued use of “commons” or “OBA-compatible” language without the correct status label is non-conform and triggers correction.

## B03.CH04.P10.S05 — Link to the democratic consistency test: inputs to B03.CH12

Commons governance evaluation is not local-only; it is an input into the regime-level test of democratic consistency.

### Required handover inputs (minimum)
- Exception ratio trends and renewals (with sunset compliance).
- Sanction rate and enforcement latency (including vendor sanctions).
- Reproducibility/audit coverage, restatement frequency, and definition-set version churn.
- Participation/representation churn and conflict-of-interest incidents.
- Gating/toll proxy indicators and vendor concentration/lock-in signals.

### Conformance requirements (binding)
- These inputs MUST be delivered in machine-readable form and MUST reference the applicable version IDs.
- Failure to provide required inputs (or provision of unverifiable inputs) MUST degrade status under B03.CH12 (fail-closed logic).
