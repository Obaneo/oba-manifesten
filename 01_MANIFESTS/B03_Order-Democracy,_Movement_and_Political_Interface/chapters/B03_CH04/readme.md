# B03.CH04 — Commons-democracy: governance, access, maintenance, and conflict resolution

This chapter defines **commons-democracy** as the governance layer that makes **commons substitution** viable in practice:
it specifies how access, quality, maintenance (ΔG), investment, and conflict resolution are decided **without recreating toll gates**
or drifting into façade-commons. It provides the institutional and procedural rails that keep commons compatible with the Kernel
Spec invariants (caps bindingness, measurability/auditability, contestability) while remaining democratically governable.

Commons here are treated as an **order object**: neither “the state” nor “the market,” but a public substitute that removes
toll positions by making essential services and shared infrastructures **open within explicit boundary rules**, maintained through
stewardship duties, and protected against capture, gating, and black-box allocation.

## How to use this chapter

- If you are **designing or evaluating a commons institution**: use this chapter as the **governance blueprint** for roles,
  representation, powers, conflict resolution, and anti-capture rails.
- If you are **drafting policy** that claims “commons” status: treat the constitutive rails here as **binding**; do not invent
  local exceptions or alternative meanings.
- If you are **auditing** commons performance: use the transparency, logging, and contestability requirements to test whether
  the commons is operationally open, maintained, and non-extractive (no toll gates by another name).
- If you are **allocating ΔM** into commons: apply the budget/exitability/procurement rails to prevent vendor lock-in and
  black-box governance.

## Status

This chapter is **normative** for any system that claims commons status under OBA: it defines the minimum governance rails for
open access (within boundary rules), contestability, and maintenance discipline, and it specifies the failure conditions under
which a “commons” must be requalified as a market/private toll regime or treated as an incompatible façade.

Changes to this chapter have high systemic impact and therefore require strict changelog discipline, impact analysis, and
compatibility checks against the Kernel Spec and the democratic consistency test (B03.CH12).
