# B03.CH12.P06 — Public reporting and accountability: output formats of the test

This paragraph defines the **public output formats** of the democratic consistency test. The test is not a private control loop; it is a public
accountability instrument. Its outputs must be structured so that independent parties can (i) see the state of governance integrity, (ii) verify the
evidence lineage and definition versions, (iii) observe threshold breaches and triggered actions, and (iv) detect semantic laundering via silent edits.

Public reporting is therefore treated as **governance infrastructure**: fixed schemas, version IDs, registries, changelog discipline, and restatements.
Where the outputs cannot be published due to secrecy, proprietary tooling, or missing logs, the system is already in democratic consistency failure.

## Core principles

* **Publicness is contestability**: without publishable artefacts, governance becomes assertion.
* **Formats must be fixed**: freeform reports invite omission and drift; schemas force completeness.
* **Lineage is the anti-lie**: every number must point to definition IDs, data sources, and computation versions.
* **Corrections must be explicit**: restatements replace silent edits; otherwise history is rewritten.
* **The test itself must be audited**: otherwise the meta-layer becomes the new capture surface.

## B03.CH12.P06.S01 — Consistency report: scorecard per metric, thresholds, trend, status label

The primary output is the **consistency report**: a periodic scorecard that summarises governance integrity across the minimum metric set.

### Required fields (minimum)

* **Report ID and period**: time window, publication date, responsible institution(s).
* **Definition-set and tooling versions**: IDs for definitions, computation rules/models, and protocol thresholds.
* **Metric scorecard**: per metric: current value, threshold bands, trend (with uncertainty), and status (OK/warn/breach).
* **Breaches and triggers**: which thresholds were breached, when, and which response-ladder steps were activated.
* **Compatibility label**: current status label (compatible/partial/incompatible or pass/fail mapping) with rationale pointers.
* **Open issues**: missing data, reproducibility gaps, pending restatements, ongoing investigations.

### Conformance requirements (binding)

* Every metric line **MUST** include threshold context and version IDs; values without lineage are non-compliant.
* Trends **MUST** be accompanied by bridging/restatement notes when definitions changed.
* If data is missing, the report must mark **fail-closed** domains explicitly and state the suspension scope.

## B03.CH12.P06.S02 — Incident reporting: root cause, implicated decisions, exception log, recovery plan

When drift signals trigger escalation, the system must publish an **incident report**. The incident report is not PR; it is a structured forensic record
that supports contestation, remedies, and learning.

### Incident report contents (minimum)

* **Incident ID**: category (semantic/exception/black-box/capture/authoritarian), detected signals, trigger thresholds breached.
* **Root cause hypothesis**: mechanism-level explanation (where drift entered: definition change, procurement, enforcement, exception renewal, audit denial).
* **Implicated decisions**: linked decision log entries, procurement artifacts, exception IDs, and responsible authorities.
* **Scope and harm**: affected domains, populations, commons services, and estimated exposure (with uncertainty).
* **Recovery plan**: rollback actions, reconstitution steps, restatement plan, deadlines, and verification criteria.
* **Interim controls**: hard stops or fail-closed subset operations while recovery proceeds.

### Conformance requirements (binding)

* Incident reports **MUST** include exception registry links and decision lineage; narrative-only reports are prohibited.
* If implicated artifacts cannot be disclosed, the report must state exactly what is withheld, why, and under which review access exists.
* Failure to publish incident reports under threshold breach is itself a drift signal and triggers independent review.

## B03.CH12.P06.S03 — Changelog discipline: rationale, impact analysis, backward compatibility where possible

Changelog discipline prevents semantic drift by forcing every change in definitions, thresholds, models, or protocols to be explicit and reviewable.

### Changelog requirements (minimum)

* **Change ID**: timestamp, authoring body, scope (definition/threshold/model/protocol/data pipeline).
* **Rationale**: why the change is needed; what problem it solves.
* **Impact analysis**: which metrics/series are affected; expected direction/magnitude; uncertainty.
* **Backward compatibility**: whether older interfaces/definitions remain operable; if not, specify migration rules.
* **Restatement linkage**: whether restatement is required; plan and status.

### Conformance requirements (binding)

* No change may be effective without a changelog entry and version bump; silent edits are prohibited.
* If backward compatibility is broken, migration paths are mandatory; otherwise comparability collapses.
* Repeated threshold “relaxation” without substantive justification is capture risk and triggers definition freeze review.

## B03.CH12.P06.S04 — Restatements: transparent corrections and bridging of historical series

Restatements are the formal method for correcting the record when definitions, methods, or tooling change—or when errors are discovered. They are required
to prevent “history rewriting” via semantics.

### Restatement output requirements (minimum)

* **Restatement ID**: scope (which metrics/periods), reason (definition change, bug, data correction, audit finding).
* **Before/after series**: clearly labeled; where full recomputation is infeasible, provide bridging estimates and bounds.
* **Method disclosure**: definition-set versions, code/model versions, data snapshots, and replication instructions.
* **Propagation status**: which dashboards, summaries, and dependent documents have been updated.
* **Interpretation note**: what prior conclusions are invalidated or bounded by the correction.

### Conformance requirements (binding)

* Restatements **MUST** be public and time-stamped; “quiet corrections” are prohibited.
* If restatement lag exceeds thresholds, trend claims must be bounded and certain decisions must fail-closed.
* A regime that repeatedly changes semantics without restatement is incompatible with democratic consistency.

## B03.CH12.P06.S05 — Audit of the test: independent review of methodology and tooling

Because the consistency test is a governance meta-layer, it can itself become a capture surface. Therefore the test must be independently audited for
methodology integrity, tooling independence, and reproducibility.

### Audit-of-the-test requirements (minimum)

* **Methodology review**: verify metric definitions, thresholds, co-occurrence logic, and escalation mappings.
* **Tooling review**: verify that computation is reproducible; check version pinning; confirm independence from vendors being measured.
* **Data lineage review**: verify sources, sampling, missingness handling, and privacy-safe publication.
* **Adversarial testing**: attempts to game metrics, shift definitions, or suppress incidents; validate detection robustness.
* **Public report**: publish findings, remediation plan, and versioned updates to the test.

### Conformance requirements (binding)

* The audit must be performed by bodies structurally independent from execution and procurement.
* If the test cannot be reproduced independently, its outputs lose legitimacy and governance must fail-closed on claims derived from it.
* Audit findings must feed into protocol versioning with changelog and (where needed) restatements.
