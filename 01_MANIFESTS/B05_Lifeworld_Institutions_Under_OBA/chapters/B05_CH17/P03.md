# B05.CH17.P03 — Caps compatibility and incentive redesign (per sector)

This paragraph specifies how each sector case must demonstrate **caps compatibility** and **incentive redesign**. Sector interventions
often fail because they reduce one extraction channel while opening another (arbitrage), or because they ignore where W/I concentration
and block power actually sit (formal ownership vs UBC reality). CH17 therefore requires a UBC look-through exposure map, an incentive
analysis under caps, explicit no-arbitrage constraints, and a remedy set that can be applied within fixed rules.

---

<a id="b05ch17p03s01"></a>
## B05.CH17.P03.S01 — W/I exposure: where claims and concentration sit (UBC look-through)

Caps compatibility begins with an exposure map: where wealth and income claims exist in the sector, who ultimately controls them, and
which positions function as tolls or chokepoints.

### Required fields (template)
- `sector_exposure_map`:
  - `positions[]` (sector-relevant positions: landlords, network operators, insurers, platforms, licensors, intermediaries)
  - `claim_types[]` per position: {rent, fees, carry, royalties, take_rates, interest, concessions}
  - `concentration_proxies` (market share bands, ownership concentration bands, fee stack depth)
- `UBC_look_through`:
  - for each major position cluster:
    - `UBC_subjects[]` (aggregated categories)
    - `control_vectors[]` (control/benefit/block)
    - `benefit_vectors[]`
    - `block_vectors[]`
    - `opacity_gaps[]` (missing disclosure points)

### Normative requirements (RFC 2119)
- Exposure mapping **MUST** use UBC look-through; formal labels are insufficient.
- Concentration **MUST** be represented with at least one proxy (band acceptable).
- Opacity gaps **MUST** be logged; silence is non-conform because it blocks enforcement.

### Conformance tests (minimum)
- **SC-CAP-01 (UBC presence):** at least one UBC look-through path exists for a major sector position.
- **SC-CAP-02 (Concentration proxy):** at least one concentration proxy is reported.
- **SC-CAP-03 (Opacity logging):** opacity gaps are explicitly recorded where disclosure is incomplete.

<a id="b05ch17p03s02"></a>
## B05.CH17.P03.S02 — Incentives: how caps steer behavior; which status shifts to expect

Caps change payoffs. Sector cases must show how actors respond: which behaviors become less attractive, which shift routes emerge, and
where status competition migrates.

### Required fields (template)
- `incentive_map` with:
  - `pre_incentives` (what behavior is rewarded under current regime)
  - `post_incentives_under_caps` (what becomes less rewarded)
  - `expected_adaptation_patterns[]`:
    - {legitimate_adjustment, pseudo_legitimate_shift, evasion_attempt}
  - `status_shift_surfaces[]`:
    - {credentials, networks, platform_visibility, curation/awards, gatekeeping institutions}
- `monitoring_proxies[]`:
  - drop-off/conversion proxies, credential inflation proxies, fee stack growth proxies, portability success rates

### Normative requirements (RFC 2119)
- Incentive analysis **MUST** name expected adaptation patterns and specify monitoring proxies; “actors will comply” is non-conform.
- Status-shift risks **MUST** be identified where the sector relies on gatekeeping (licensing, ranking, procurement).
- Monitoring **MUST** be aggregated and privacy-preserving; it must not become behavioural scoring.

### Conformance tests (minimum)
- **SC-INC-01 (Adaptation modeling):** at least one expected adaptation pattern is listed and linked to a detection proxy.
- **SC-INC-02 (Status migration):** at least one status shift surface is identified (or explicitly justified absent).
- **SC-INC-03 (Proxy discipline):** monitoring proxies include provenance (`method_id` or benchmark version).

<a id="b05ch17p03s03"></a>
## B05.CH17.P03.S03 — No-arbitrage: prevent shifts into unregulated positions or sham constructions

No-arbitrage means: closing one route must not open a substitute route that restores extraction, concentration, or block power. Sector
cases must explicitly list the likely arbitrage moves and the constraints that prevent them.

### Arbitrage move taxonomy (minimum)
- `label_shift` (rent→service fee; wage→fee→royalty)
- `vehicle_shift` (ownership moved to SPVs/nominees; fragmentation)
- `channel_shift` (payment moved to shadow rails; bundling)
- `jurisdiction_shift` (treaty hubs, mailbox substance)
- `status_gate_shift` (credential/network gatekeeping replaces price extraction)

### Required no-arbitrage constraints (template)
- `substance_over_form_rules` (recharacterization triggers)
- `look_through_rules` (UBC attribution; aggregation across vehicles)
- `forbidden_channel_flags` (ΔM and technical rails)
- `portability_and_exit_rules` (prevent lock-in by design)
- `dispute_and_deadline_rules` (prevent delay-as-evasion)

### Normative requirements (RFC 2119)
- Sector cases **MUST** enumerate at least the top arbitrage moves and match each to a constraint.
- If a constraint cannot be implemented, the case **MUST** declare the sector intervention incomplete and route to redesign before scale.
- No-arbitrage constraints **MUST** be enforceable and auditable (evidence classes, logs).

### Conformance tests (minimum)
- **SC-NA-01 (Move-to-constraint mapping):** each listed arbitrage move maps to a specific constraint.
- **SC-NA-02 (Enforceability):** constraints include evidence requirements and an enforcement owner (role).
- **SC-NA-03 (Fail-closed readiness):** inability to enforce triggers scaling block (link P10).

<a id="b05ch17p03s04"></a>
## B05.CH17.P03.S04 — Remedies: divestment, conversion-to-commons, contract rewrite, bounded returns

Caps compatibility requires remedies that can be applied when concentration or extraction surfaces breach compatibility thresholds. Remedies
must be rule-bound, not negotiated.

### Remedy menu (minimum set; fixed options)
- `divestment_or_deconcentration`:
  - structured divestment to reduce concentrated positions or choke point ownership
- `conversion_to_commons`:
  - convert excess returns or breach value into commons funding or commons capacity expansion (C)
- `contract_rewrite`:
  - mandatory template clauses, fee caps, transparency requirements, portability requirements
- `bounded_returns_regime`:
  - caps on returns for quasi-monopoly positions; regulated returns with auditability
- `replacement_by_public_option`:
  - where contestability cannot be restored, expand the commons/public option

### Normative requirements (RFC 2119)
- Remedies **MUST** be selectable only from a fixed, published menu; bespoke deals are non-conform.
- Each remedy **MUST** specify:
  - trigger condition,
  - time to compliance,
  - evidence pack,
  - and audit publication level (privacy-safe).
- Remedy application **MUST** preserve system function (avoid fire sales where possible) while removing extraction surfaces.

### Conformance tests (minimum)
- **SC-RMD-01 (Menu integrity):** remedies used are within the fixed menu.
- **SC-RMD-02 (Trigger definition):** each remedy has an explicit trigger condition and evidence pack.
- **SC-RMD-03 (Auditability):** remedy execution generates logs and an aggregated audit summary.

---

### Output format (caps compatibility annex)

At minimum, each sector case **MUST** emit a caps-compatibility annex (table or structured list) with:

- `sector_position` | `claim_type` | `UBC_subject_category` | `concentration_proxy` | `arbitrage_moves` | `constraints` |
  `remedy_trigger` | `remedy_menu_option` | `evidence_pack_ref`

If this annex cannot be produced, caps compatibility is not demonstrated and the sector case is NON-CONFORM.
