# B05.CH17.P02 — Canonical template structure (one sector case)

This paragraph defines the **canonical template structure** for a single sector case. The template is intended to be cloned across
sectors and jurisdictions without changing definitions. It is a **machine-bindable** object: each section corresponds to field groups
that can be emitted in structured form (Codex schemas) and audited via minimum evidence packs. The template is designed to expose: (i)
what the sector is, (ii) where it bottlenecks, (iii) where extraction sits, and (iv) what the commons/public option is.

---

<a id="b05ch17p02s01"></a>
## B05.CH17.P02.S01 — Context: sector boundaries, users, dependencies, choke points

The context section defines the sector case boundaries and the system shape: who uses the sector, what dependencies exist, and where choke
points concentrate block power.

### Required fields (template)
- `sector_id` (e.g., housing/energy/healthcare/digital; extensible)
- `sector_boundary`:
  - what is included and excluded (scope notes)
- `user_cohorts[]` (aggregated):
  - who depends on the sector (household cohorts, firms, public bodies)
- `service_units[]`:
  - what is delivered (e.g., kWh, visits, dwelling-months, identity sessions)
- `dependencies[]`:
  - upstream and cross-sector dependencies (labor, permitting, infrastructure, digital identity, finance)
- `choke_points[]`:
  - points where control/block power concentrates (licensing boards, network operators, platforms, landlords, insurers)

### Evidence minimum (classes)
- service definitions and boundary notes
- dependency map evidence class (docs/standards/public records)
- choke point evidence class (contracts, licensing rules, market structure proxies)

### Normative requirements (RFC 2119)
- Context **MUST** be explicit enough to prevent “sector drift” and scope creep.
- Choke points **MUST** be listed as concrete control surfaces, not “market is concentrated” generalities.
- User cohorts **MUST** be aggregated and privacy-safe.

### Conformance tests (minimum)
- **SC-TPL-CTX-01 (Boundary):** sector boundary includes in/out rules.
- **SC-TPL-CTX-02 (Choke points):** at least one choke point is identified with evidence class linkage.
- **SC-TPL-CTX-03 (Dependencies):** dependencies list exists (can be short but non-empty).

<a id="b05ch17p02s02"></a>
## B05.CH17.P02.S02 — Bottlenecks: scarcity/capacity/permits/skills/infrastructure; time as a constraint

Bottlenecks are the binding constraints that produce scarcity, queues, and non-contestability. Time is treated as a first-class
constraint.

### Required fields (template)
- `bottlenecks[]` with, per bottleneck:
  - `bottleneck_type` ∈ {capacity, scarcity, permits, skills, infrastructure, supply_chain, information, governance}
  - `constraint_description`
  - `time_constraint`:
    - queue/wait time proxy, backlog proxy, or lead-time proxy (band acceptable)
  - `binding_indicator_proxy`:
    - utilization, backlog growth, permit delays, skill vacancy rates (proxy definitions)
  - `who_is_affected[]` (cohort refs; aggregated)
  - `failure_mode` (what breaks when constraint binds)
  - `evidence_class[]`

### Normative requirements (RFC 2119)
- Each bottleneck **MUST** have at least one measurable proxy (band acceptable) and an affected cohort mapping.
- Bottlenecks **MUST** include time constraints; omitting time yields a non-lifeworld case.
- Bottlenecks **MUST** be distinguished from E sources: bottleneck is scarcity/capacity; E is extraction on top of scarcity.

### Conformance tests (minimum)
- **SC-TPL-BOT-01 (Proxy):** each bottleneck has a binding indicator proxy and a time constraint proxy.
- **SC-TPL-BOT-02 (Cohorts):** affected cohorts are referenced for each bottleneck.
- **SC-TPL-BOT-03 (Evidence):** evidence class exists for each bottleneck claim.

<a id="b05ch17p02s03"></a>
## B05.CH17.P02.S03 — E sources: fee stacks, lock-in, market power, dark patterns, clamp contracts

E sources are the extraction surfaces: fee stacks, lock-ins, opacity, and coercive contracts that convert dependency into toll payments
or block power.

### Required fields (template)
- `E_sources[]` with, per source:
  - `E_type` ∈ {fee_stack, lock_in, market_power, dark_pattern, clamp_contract, intermediary_toll, data_rent, ranking_gate}
  - `mechanism_description`
  - `where_it_sits` (which choke point or dependency it attaches to)
  - `who_pays` (cohort refs; aggregated)
  - `pricing_or_fee_proxy` (effective rate or fee incidence; band acceptable)
  - `switching_cost_proxy` (cash/time; band acceptable)
  - `opacity_flag` (present/absent)
  - `evidence_pack_ref` (minimum auditpack reference)

### Normative requirements (RFC 2119)
- E sources **MUST** be itemized; “market power exists” is insufficient.
- Each E source **MUST** include at least one measurable proxy (fee rate/incidence, switching cost, penalty frequency).
- E sources **MUST** reference an evidence pack (auditpack) sufficient to prove the toll layer.

### Conformance tests (minimum)
- **SC-TPL-E-01 (Itemization):** E sources list contains concrete mechanisms and locations.
- **SC-TPL-E-02 (Proxy):** each E source has at least one fee/price proxy and one switching/lock-in proxy.
- **SC-TPL-E-03 (Auditpack):** each E source links to an evidence_pack_ref.

<a id="b05ch17p02s04"></a>
## B05.CH17.P02.S04 — Commons/public option: alternative design, governance minima, maintenance plan, procurement rails

The commons/public option is the exit route: an alternative service path that reduces dependency on chokepoints and collapses E surfaces.
It must be operational, governed, and maintainable.

### Required fields (template)
- `commons_option`:
  - `service_scope` (what is covered; what is baseline vs premium)
  - `access_rules` (eligibility, onboarding, non-exclusion defaults)
  - `service_level_minima` (availability, response times, reliability; proxies)
  - `maintenance_plan` (who maintains, cadence, backlog handling)
  - `governance_minima`:
    - roles (operator, auditor, ombuds),
    - contestability (appeal paths),
    - transparency (logs/metrics publication; aggregated)
  - `procurement_rails`:
    - open criteria, conflict checks, auditability, anti-vendor capture constraints
  - `transition_path`:
    - switching steps, portability, gap handling during onboarding
  - `evidence_pack_ref` (procurement + governance + service level evidence minimum)

### Normative requirements (RFC 2119)
- A commons option **MUST** be operationally specified (service levels, access rules, maintenance). “Public option exists” is non-conform.
- Procurement **MUST** be constrained to prevent consultancy/vendor capture (link P10 failure modes).
- The commons option **MUST** include contestability and audit-on-the-auditor hooks via governance minima.

### Conformance tests (minimum)
- **SC-TPL-COM-01 (Operationality):** service level minima + maintenance plan exist.
- **SC-TPL-COM-02 (Procurement rails):** procurement constraints exist and are auditable.
- **SC-TPL-COM-03 (Exit realism):** transition path includes switching + portability + gap handling.

---

### Output format (canonical template skeleton)

At minimum, a sector case **MUST** be able to emit the following machine-parseable skeleton:

1) `context{ sector_id, sector_boundary, user_cohorts[], dependencies[], choke_points[] }`  
2) `bottlenecks[]{ bottleneck_type, time_constraint, binding_indicator_proxy, cohorts, evidence_class }`  
3) `E_sources[]{ E_type, mechanism, fee_proxy, switching_cost_proxy, opacity_flag, evidence_pack_ref }`  
4) `commons_option{ scope, access_rules, service_level_minima, maintenance_plan, governance_minima, procurement_rails, transition_path }`

If any section cannot be instantiated, the sector case is NON-CONFORM and not reusable.
