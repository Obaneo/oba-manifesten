# B05.CH14 — Day-in-the-life I: household with low R/B (before/after, contract lock-ins, commons exits)

This chapter is the first **day-in-the-life** module for OBA. It translates the framework into a concrete household case with **low
R/B** (precarity / high tail exposure): a situation where small shocks cascade into arrears, lockouts, debt spirals, and administrative
clamp. The chapter’s purpose is explicitly **non-PR**: it must show, in reproducible terms, how **BRUTO → NETTO → LASTEN →
RESTRUIMTE** changes under OBA, and which mechanisms cause that change (lock-in removal, fee-stack collapse, baseline access, faster
dispute and restructuring). Narrative is allowed only as a carrier; the truth condition is **measurement linkage** (definition-set IDs,
method_id, and explicit uncertainty).

CH14 is designed to be **anti-washing** and **fail-closed**. A “nice day” story without a lock-in diagnosis and without a measurable
before/after dashboard is disqualifying. Likewise, a story that hides residual frictions or pretends shocks vanish is non-conforming.
The case is also an early-warning tool: if an “after” system still produces arrears cascades, lockouts, long disputes, or selective
execution differences by municipality, that is a design breach requiring redesign.

## How to use this chapter

- If you are **explaining OBA concretely**: use CH14 as a template-driven demonstration of how the rails translate into lifeworld
  outcomes (L down, lock-in down, faster contestability, fewer fee-stacks).
- If you are **designing essentials policy**: use the lock-in map (P03) and fee-stack map (P04) to identify where block power pins the
  household and which rails must change (housing, energy, digital, debt/collections).
- If you are **designing buffers and restructuring**: use the shock moments (P05) and OBA intervention set (P06) to specify how
  emergency buffers, income floors, and fast restructuring prevent tail collapse (link CH04/CH06).
- If you are **building public options/commons exits**: use P07 to define concrete switching paths out of lock-in contracts and to
  specify portability and anti-punitive fee rules.
- If you are **auditing implementation**: use the case dashboard (P09) plus dispute/error handling (P10) as a conformance test and
  early-warning system.

## Status

This chapter is **normative** for using day-in-the-life narratives inside OBA. The standardised case template, lock-in diagnosis,
commons exit mapping, and measurable before/after dashboard are treated as **constitutive** requirements. Any OBA narrative that claims
improved fairness or reduced precarity must be able to instantiate this template and produce the linked measurements. Conversely, if
implementation produces “after” cases with persistent arrears, lockouts, punitive fees, or long dispute cycles, that is evidence of
non-conformance that must trigger redesign and scope restriction to auditable coverage.
