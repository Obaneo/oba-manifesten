# B05.CH14.P12 — Failure modes and hard stops (case as an early-warning system)

This paragraph specifies **failure modes** and **hard stops** for the Day-in-the-Life case. The case is treated as an **early-warning system**: it must detect OBA-washing, new gatekeeping, selective execution, and tail regressions. These are not “lessons learned”; they are **conformance breakers** with fail-closed behaviour. If a failure mode triggers, the case is either disqualified (storytelling-washing) or the system must be redesigned (tail regression / new lock-in).

---

<a id="b05ch14p12s01"></a>
## B05.CH14.P12.S01 — Storytelling-washing: nice day but no measurement linkage → disqualification

Storytelling-washing occurs when the case reads well but fails to bind claims to measurable structure. This is the primary adversary of the Day-in-the-Life method.

### Disqualifying conditions (NON-CONFORM)
A case is **NON-CONFORM** if any of the following holds:
- “Before/after” claims are stated without the dashboard outputs (P09) and without `method_id`.
- Lock-in and fee layers are described without evidence classes (P03/P04 evidence linkage).
- Qualitative improvement claims are present but cannot be traced to:
  - a measurable delta (B,T,N,L,R, lock-in metrics, shock absorption),
  - a declared assumption, or
  - a conformance requirement.
- The “after” case uses simulated assumptions but presents them as observed outcomes.

### Normative requirements (RFC 2119)
- The case **MUST** be disqualified when storytelling-washing is detected; partial credit is not allowed.
- Disqualification **MUST** include an explicit list of missing conformance items (which dashboard tables/links are absent).

### Conformance tests (minimum)
- **DL-SW-01 (Dashboard gate):** missing P09 tables → automatic NON-CONFORM.
- **DL-SW-02 (Evidence gate):** missing evidence linkage for asserted E/lock-in → automatic NON-CONFORM.
- **DL-SW-03 (Traceability):** untraceable qualitative claims are flagged; above threshold count → NON-CONFORM.

<a id="b05ch14p12s02"></a>
## B05.CH14.P12.S02 — New lock-in: public systems that exclude/punish → non-conform

A key risk is that public/commons systems recreate block power: exclusionary eligibility gates, punitive enforcement, opaque criteria, or surveillance drift. OBA treats this as a conformance failure, not a “trade-off”.

### New lock-in indicators (minimum set)
- `exclusion_gates` (documentation burdens, denial-by-friction, inaccessible channels)
- `punitive_enforcement` (rapid sanctions, harsh arrears responses, no provisional relief)
- `opaque_criteria` (non-explainable decisions, discretionary gatekeeping)
- `retaliation_or_chilling_effect` (fear of reporting/appeals)
- `surveillance_drift` (disproportionate monitoring of low R/B households)

### Normative requirements (RFC 2119)
- Any public/commons option **MUST** be evaluated for new lock-in using explicit indicators (P09 commons table + P10 protections).
- If new lock-in is detected, the option is **NON-CONFORM** unless remedied via:
  - open criteria + appeal,
  - reduced proof burden,
  - portability/recovery,
  - and removal of punitive enforcement (dispute-safe baseline).
- Systems **MUST NOT** use behavioural scoring or health/stress signals for eligibility/enforcement.

### Conformance tests (minimum)
- **DL-NLI-01 (Indicator check):** post-case commons options include exclusion/punitive/opacity checks.
- **DL-NLI-02 (Dispute-safe):** provisional relief exists where harm risk exists; absence → NON-CONFORM.
- **DL-NLI-03 (No scoring):** explicit prohibition and audit check against prohibited scoring.

## B05.CH14.P12.S03 — Selective execution: differences by municipality without transparency → legitimacy breach

Selective execution occurs when outcomes depend on local discretion (municipality/provider) without transparent rules, causing unequal rights and creating new “postcode lotteries”. This is a legitimacy breach because OBA claims order compatibility under shared rails.

### Selective execution indicators (minimum set)
- material variance in:
  - time-to-decision / time-to-relief,
  - access coverage / wait times,
  - enforcement aggressiveness (disconnections/evictions/garnishments),
  - dispute win rates or appeal success,
  - proof burden and documentation demands
  across municipalities/providers.
- unexplained exceptions, discretionary denials, or inconsistent rule versions.

### Normative requirements (RFC 2119)
- The system **MUST** publish aggregated comparative metrics across jurisdictions/providers (privacy-safe) for the key dashboard indicators (P09).
- Differences **MUST** be explainable by declared parameters, not hidden discretion.
- If unexplained variance exceeds the declared tolerance band, a legitimacy breach is triggered and remediation is mandatory (standardization, audit, contract rewrite, or public option expansion).

### Conformance tests (minimum)
- **DL-SEL-01 (Comparative publication):** cross-jurisdiction/provider metrics exist for decision times, access, and enforcement.
- **DL-SEL-02 (Rule version control):** rule/method versions are consistent or differences are declared.
- **DL-SEL-03 (Variance trigger):** variance beyond tolerance is detected and routes into audit/remedy.

<a id="b05ch14p12s04"></a>
## B05.CH14.P12.S04 — Fail-closed: if the “after” case shows a worse tail (more arrears/lock-in), redesign is mandatory

The hard stop is outcome-based: if the “after” case worsens tail indicators, OBA does not accept narrative justification. It triggers mandatory redesign.

### Tail regression conditions (hard stop)
A tail regression is triggered if, post intervention:
- `arrears_incidence` increases in housing or energy, or
- `disconnection/eviction threat timeline` becomes shorter or more punitive, or
- `switching_cost` increases (cash or time), or
- `dispute_duration` increases without compensating provisional relief, or
- `cascade_multiplier` increases for any standardized shock (P05), or
- `RB_post` declines at the tail-relevant band (or uncertainty band includes meaningful worsening) without an explicit documented cause outside the rail scope.

### Normative requirements (RFC 2119)
- If a tail regression is detected, the system **MUST** treat the intervention set as insufficient and **MUST** redesign the responsible rail(s).
- Redesign **MUST** be traceable: which lock-in surface or fee layer caused regression, which rail is changed, and how the change will be re-tested.
- The system **MUST NOT** ship or claim conformance on an “after” state that fails the tail tests, even if some averages improve.

### Conformance tests (minimum)
- **DL-FC-TAIL-01 (Regression gate):** any tail regression condition → FAIL-CLOSED (no conformance claim).
- **DL-FC-TAIL-02 (Attribution):** regression requires attribution to a surface/layer (P03/P04) and a redesign action.
- **DL-FC-TAIL-03 (Re-test):** redesigned rail triggers re-run of the standardized shocks and dashboard deltas.

---

### Output format (early-warning register)

At minimum, the case **MUST** emit an early-warning register (table or structured list) with:

- `failure_mode` | `trigger_indicator` | `threshold_or_condition` | `detected` | `impact_surface` | `required_action` | `status`

Where required_action ∈ {disqualify_case, launch_audit, contract_rewrite, expand_public_option, rollback, redesign_rail, publish_variance_report}.
