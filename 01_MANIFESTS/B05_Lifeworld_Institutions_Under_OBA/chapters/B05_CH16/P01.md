# B05.CH16.P01 — Purpose, scope, and method for the high-income/wealth case

This paragraph defines the purpose, scope, and method for Day-in-the-Life Case III: a **high income/wealth** profile before and after
OBA cap enforcement. The case is a **conformance instrument**, not a narrative artefact: it exists to show—concretely and testably—how
**I-MAX** and **W-MAX** operate as events, how **UBC look-through** prevents form games, how remedies reallocate without system damage, and
how evasion attempts are detected and neutralised via auditpacks, presumptions, and dispute boundaries.

---

<a id="b05ch16p01s01"></a>
## B05.CH16.P01.S01 — Purpose: make visible how caps and anti-evasion operate in the lifeworld (no caricature, but testable)

The purpose is to make “caps at the top” operationally legible. This requires avoiding caricature: the case must not rely on moral
theatre or assumed motives. Instead it must specify **testable mechanisms**: income/wealth architecture, control structures, cap events,
evasion shifts, detection rules, and enforcement outcomes.

### Normative requirements (RFC 2119)
- The case **MUST** model **cap events** (I-MAX/W-MAX) as explicit triggers with timing, valuation/exposure logic, and enforceable
  consequences (remedies and/or provisional enforcement under opacity).
- The case **MUST** represent **anti-evasion** as a shift taxonomy applied to structures and transactions, not as speculation about intent.
- The case **MUST** link every enforcement claim to provenance: `definitionset_id`, `method_id`, evidence classes, and uncertainty bands.
- The case **MUST NOT** caricature the subject or substitute narrative plausibility for enforcement logic.

### Conformance tests (minimum)
- **DL16-PUR-01 (Cap-event presence):** at least one I-MAX event and one W-MAX event (or explicit “none triggered” with proof) are modeled.
- **DL16-PUR-02 (Shift modeling):** at least one explicit evasion shift attempt is described and mapped to detection/remedy logic.
- **DL16-PUR-03 (Provenance):** cap outcomes cite `method_id` and evidence classes (valuation + control map + transactions).

<a id="b05ch16p01s02"></a>
## B05.CH16.P01.S02 — Scope: high I and/or high W, ownership structures, carry/fees, real estate/portfolios, international mobility

The scope covers the real architecture of high positions: layered ownership, mixed income types, valuation discretion, and the ability to
shift across borders and instruments.

### In-scope (binding)
- High income and/or high wealth profiles:
  - salary/bonus/vesting,
  - dividends/interest,
  - fees/royalties/licensing,
  - carry/performance allocations,
  - in-kind perks.
- Ownership and control structures:
  - holdings, trusts, SPVs, partnerships, nominee/beneficial ownership, trustees, layered vehicles.
- Wealth composition and valuation risk:
  - public equity, real estate, private funds, derivatives/synthetics, IP claims, concentrated positions.
- Cross-cap arbitrage channels:
  - deferral, debt extraction, SPV pricing, synthetic exposure.
- International mobility and leakage:
  - residency changes, control-center relocation, asset migration, treaty mismatch.
- Enforcement interfaces:
  - disclosure duties, auditpacks, presumptions, escrow/lockbox, sanctions.

### Out-of-scope (explicit)
- Personal moral judgement or biography.
- Political campaigning and macro-ideological debate (this is an enforcement case).
- Non-testable claims about motives as proof.

### Normative requirements (RFC 2119)
- The case **MUST** remain privacy-safe and non-identifying, but **MUST** be concrete enough to test look-through, valuation, and exposure.
- If international mobility is invoked, the case **MUST** include explicit exit triggers and anti-arbitrage boundaries (link P10).

### Conformance tests (minimum)
- **DL16-SCP-01 (Structure coverage):** at least one layered ownership element (trust/SPV/partnership) is present or explicitly excluded
  with rationale.
- **DL16-SCP-02 (Instrument coverage):** at least three income/wealth instrument types are represented (e.g., salary + equity + real estate).
- **DL16-SCP-03 (Mobility clarity):** if mobility is in scope, residency/control-center triggers are declared.

## B05.CH16.P01.S03 — Method: case template with cap events, remedies, auditpacks, dispute-flow, and evasion attempts

A high-income/wealth day-in-the-life case is a **standardized specimen**: it must be reproducible, auditable, and capable of exposing
evasion shifts under stress.

### Required case fields (template)
- `definitionset_id` — normative definitions in force (caps, UBC, exposure, valuation, forbidden channels, dispute timing).
- `method_id` — calculation, valuation, and evidence handling rules; versioned.
- `case_mode` ∈ {`observed_after`, `simulated_after`}
  - If `simulated_after`, enforcement assumptions **MUST** be enumerated and uncertainty widened.
- `time_window_pre`, `time_window_post` — comparable periods.
- `evidence_classes[]`:
  - ownership docs (categories),
  - transaction ledgers (categories),
  - valuations/appraisals (categories),
  - custody/broker records (categories),
  - contract terms for fees/carry (categories).
- `auditpack_ref` — minimum auditpack set for each asserted cap event or remedy.
- `dispute_flow_profile` — time bounds, escrow/lockbox rules, provisional enforcement triggers.
- `shift_attempts[]` — explicit evasion attempts modeled and tagged (legal/technical/financial).

### Minimum method sequence
1) Build baseline architecture: B-components + W-components + structure graph + UBC map (P02).
2) Identify cap event triggers and timing windows (P03) and compute exposure/valuation bands.
3) Apply cap rules and determine breach status; if opacity, apply presumptions + provisional enforcement.
4) Select remedies from fixed rule set (P04), log choices, and apply reallocation mechanics.
5) Run adaptation/evasion attempts (P05–P08) and apply detection + remedy rails.
6) Execute dispute-flow (P09) with escrow/lockbox boundaries and deadlines.
7) Emit dashboard outputs (P12) and early-warning triggers (P14).

### Normative requirements (RFC 2119)
- The case **MUST** be reproducible from declared inputs and `method_id` (same inputs → same outputs).
- The case **MUST** treat opacity as actionable: missing disclosure triggers conservative valuation/presumptions and provisional enforcement.
- Remedies **MUST** be rule-bound; bespoke negotiation is non-conform.
- Evasion attempts **MUST** be explicitly modeled; “we assume compliance” is non-conform.

### Conformance tests (minimum)
- **DL16-MTH-01 (Template completeness):** `definitionset_id`, `method_id`, time windows, evidence classes, auditpack refs, dispute profile,
  and shift_attempts exist.
- **DL16-MTH-02 (Reproducibility):** cap computations can be re-derived from method + evidence classes.
- **DL16-MTH-03 (Opacity handling):** opacity triggers presumptions + provisional enforcement (logged).

## B05.CH16.P01.S04 — Fail-closed: a case without explicit evasion routes (shifts) and without enforcement logic is unrealistic

This chapter uses a hard rule: CH16 exists to prove that caps are enforceable against high-structure evasion. If the case omits evasion
routes or enforcement logic, it is disqualified as unrealistic.

### FAIL-CLOSED rules (binding)
A high-income/wealth day-in-the-life case is **NON-CONFORM** if any of the following holds:
- No explicit cap events are modeled (or “none triggered” is asserted without evidence class).
- No explicit UBC look-through/control map is produced for the ownership graph.
- No explicit shift/evasion attempts are modeled (legal/technical/financial), or shifts are listed without detection/remedy logic.
- Opacity is treated as “unknown” rather than triggering conservative presumptions and provisional enforcement.
- Remedies are presented as bespoke deals or discretionary exceptions rather than fixed, versioned rule options.

### Remedy requirement (binding)
- If a case is flagged **NON-CONFORM**, it **MUST** be rewritten by adding missing cap-event logic, UBC mapping, shift attempts, and
  enforcement rails; narrative polishing is explicitly insufficient.

### Conformance tests (minimum)
- **DL16-FC-01 (Cap-event gate):** missing cap events → automatic NON-CONFORM.
- **DL16-FC-02 (UBC gate):** missing UBC control map → automatic NON-CONFORM.
- **DL16-FC-03 (Shift+enforcement gate):** missing explicit shift attempts with detection/remedy → automatic NON-CONFORM.
- **DL16-FC-04 (Opacity gate):** missing opacity presumptions/provisional enforcement logic → automatic NON-CONFORM.
