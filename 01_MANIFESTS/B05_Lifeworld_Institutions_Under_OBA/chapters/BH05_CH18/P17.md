# B05.CH18.P17 — Evolutionary infrastructure: failure modes as fuel for controlled iteration

This paragraph specifies the **evolutionary infrastructure** that turns failure modes into controlled iteration rather than collapse. CH18
assumes implementations will encounter resentment, sabotage, evasion, drift, and capture pressures. The question is not “can we avoid
failure” but “can we iterate without semantic drift, hidden edits, or legitimacy loss.” The answer is a disciplined patch cycle, backward
compatibility constraints, rollback discipline under harm, and a two-speed update model: **fast Codex updates**, **slow core (Kernspec)
updates**.

---

<a id="b05ch18p17s01"></a>
## B05.CH18.P17.S01 — Patch cycle: detect → hypothesis → intervention → audit → public restatement → deprecation

### Core mechanism
Iteration must be **bounded and auditable**. The patch cycle ensures each change has a causal hypothesis, measurable test, and public
restatement, preventing “quiet drifting fixes” that erode trust.

### Patch cycle stages (binding)
1) `detect`:
   - indicator breach detected (from P19 dashboards), with event_id and scope
2) `hypothesis`:
   - causal hypothesis stated: which mechanism produced the breach (bottleneck/E/ΔM leakage/procedure drift)
3) `intervention`:
   - rule/template/procedure/tool change proposed within Codex or (rare) Kernspec boundary
4) `audit`:
   - run auditpacks; test for leakage, selectivity, integrity and privacy compliance
5) `public_restatement`:
   - publish aggregated restatement: what changed, why, expected deltas, observed deltas (with uncertainty)
6) `deprecation`:
   - deprecate legacy templates/clauses/channels; define migration path and sunset dates

### Required fields (template)
- `patch_id`
- `trigger_indicator_ref`
- `hypothesis_statement`
- `change_set_ref` (rules/templates/method versions)
- `audit_results_ref`
- `restatement_ref` (aggregated publication)
- `deprecation_plan_ref` (what is removed; when; migration)

### Normative requirements (RFC 2119)
- Every patch **MUST** carry a hypothesis and be testable; “cleanup changes” without causal framing are drift risk.
- Public restatement **MUST** occur; hidden patches are integrity breaches.
- Deprecation **MUST** be explicit; otherwise legacy systems become shadow regimes.

### Conformance tests (minimum)
- **EVOL-01 (Stage completeness):** patches include detect→hypothesis→intervention→audit→restatement→deprecation.
- **EVOL-02 (Publication):** restatement exists and is published in aggregated form.

## B05.CH18.P17.S02 — Backward compatibility: changes improve the lifeworld without a semantic core break

### Core mechanism
Iteration must not break the semantic core. Backward compatibility rules ensure that improvements can be applied without redefining what
terms mean, avoiding “moving targets” that destroy conformance.

### Required backward-compatibility rules (minimum set)
- `semantic_core_fixed`:
  - B,T,N,L,R; E; bottleneck; commons; caps; ΔM channels remain defined by Kernspec
- `parameter_and_template_evolution`:
  - most changes happen as parameter tuning, template updates, and Codex method versioning
- `migration_paths`:
  - for each deprecated contract/template, define migration steps and time bounds
- `comparability_preservation`:
  - restatement rules for metrics when methods change; preserve time series with version markers

### Normative requirements (RFC 2119)
- Changes **MUST NOT** redefine base concepts in Codex patches; core changes require Kernspec-level process.
- Backward compatibility **MUST** be maintained via migration and restatement rather than silent redefinition.

### Conformance tests (minimum)
- **EVOL-03 (Core boundary):** each change declares whether it is Codex-level or Kernspec-level; Codex changes cannot alter core meanings.
- **EVOL-04 (Migration):** deprecated artifacts have migration paths and timelines.

## B05.CH18.P17.S03 — Rollback discipline: harm to L/tails/privacy/integrity triggers immediate rollback

### Core mechanism
Iteration can harm the lifeworld. The system must therefore have rollback discipline: if a patch causes measurable harm or breaches
privacy/integrity, it is rolled back quickly and publicly.

### Rollback triggers (binding; minimum set)
- `L_worsens` beyond uncertainty for target cohorts
- `tails_worsen` (arrears/lockouts/wait-time exceedances/cost spikes rise)
- `time_friction_worsens` (cycle times/drop-off/appeal backlog rise)
- `privacy_breach` or join-safety violation
- `integrity_breach` (silent edits, missing lineage, signature failures)
- `selective_enforcement_signal` increases beyond tolerance

### Rollback actions (minimum set)
- `immediate_revert` to last known-good version (templates/methods/rules)
- `containment` (freeze high-risk changes; preserve logs)
- `incident_publication` (aggregated) + `restatement`
- `root_cause_audit` + revised hypothesis
- `recertification` before re-release

### Normative requirements (RFC 2119)
- Rollback **MUST** be fast and rule-triggered; “wait and see” under harm is non-conform.
- Rollback **MUST** be published (aggregated) with reason codes; secrecy is an integrity breach.

### Conformance tests (minimum)
- **EVOL-05 (Trigger mapping):** rollback triggers map to automatic rollback actions.
- **EVOL-06 (Publication):** rollback events produce an incident report and restatement.

## B05.CH18.P17.S04 — Speed vs stability: fast Codex updates, slow core updates (Kernspec remains canonical)

### Core mechanism
To survive adaptation pressure, the system needs speed. To preserve legitimacy and semantic integrity, it needs stability. This yields a
two-speed governance model.

### Two-speed model (binding)
- `fast_layer` (Codex):
  - shift taxonomy updates, channel classifications, contract template revisions, parameter tuning, benchmark updates
  - release cadence can be frequent (weeks/months) with strict restatement/versioning
- `slow_layer` (Kernspec):
  - foundational definitions and invariants
  - changes are rare, explicitly governed, and treated as semantic core events

### Normative requirements (RFC 2119)
- Most iteration **MUST** occur in Codex, with transparent versioning and precedents.
- Kernspec **MUST** remain canonical; frequent core edits create semantic collapse and capture risk.
- The boundary **MUST** be explicit in every patch record.

### Conformance tests (minimum)
- **EVOL-07 (Layer declaration):** every change declares Codex vs Kernspec scope.
- **EVOL-08 (Release discipline):** Codex releases include version notes, restatements, and deprecations.

---

### Output format (patch registry)

At minimum, CH18 **MUST** maintain a patch registry (table or structured list) with:

- `patch_id` | `trigger_indicator` | `hypothesis` | `layer` (Codex/Kernspec) | `change_set_ref` | `audit_ref` |
  `restatement_ref` | `rollback_flag` | `deprecation_ref` | `status`

If the patch registry cannot be produced, iteration becomes opaque drift and CH18 is non-conform.
