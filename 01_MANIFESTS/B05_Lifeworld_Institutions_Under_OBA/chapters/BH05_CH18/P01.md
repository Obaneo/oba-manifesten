# B05.CH18.P01 — Purpose, scope, and normative status of lifeworld failure modes

This paragraph defines the purpose, scope, and normative status of **lifeworld failure modes** in OBA. CH18 exists because “formal
compliance” is not sufficient: systems can satisfy written rules while producing lived outcomes that are worse, more humiliating, more
fragile, or more captured. CH18 therefore defines early-warning indicators and stop rules that detect when the lifeworld is being broken
and forces repair through audit, restatement, rollback, and governance reset.

---

<a id="b05ch18p01s01"></a>
## B05.CH18.P01.S01 — Purpose: systematic early-warning and stop rules for implementations that “formally comply” but break the lifeworld

The purpose is to prevent an implementation from hiding behind compliance theatre. A system is only “working” if lifeworld integrity
improves (L down, tails down, time burden down) and remains contestable and auditable. CH18 operationalises this as a standardized failure
mode taxonomy with measurable proxies and escalation paths.

### Normative requirements (RFC 2119)
- Implementations **MUST** treat lifeworld integrity as the truth condition for success, not rule completion.
- Early-warning indicators **MUST** be defined for each failure mode class and monitored continuously (aggregated).
- Stop rules **MUST** exist: when indicators repeat, scaling is blocked until repair and re-test.
- Repair is not messaging: **restatement, rollback, and redesign** are required mechanisms.

### Conformance tests (minimum)
- **LW-01 (Indicators defined):** indicators exist for resentment/sabotage/evasion/drift/capture.
- **LW-02 (Stop rules defined):** explicit stop rules exist and are operationally enforceable.
- **LW-03 (Repair path exists):** forensic audit + restatement + redesign + recertification path exists (P20).

---

<a id="b05ch18p01s02"></a>
## B05.CH18.P01.S02 — Scope: resentment, sabotage, evasion, bureaucratic drift, capture (local/national/sector)

CH18 applies across the full implementation surface: local institutions, national rails, and sector templates.

### In-scope (binding)
- **Resentment**: experienced injustice/friction despite macro claims; signal, not propaganda.
- **Sabotage**: active interference (slow-roll, understaffing, data degradation, strikes, vandalism, veto politics).
- **Evasion**: extraction shifting into new legal/technical/financial/international forms.
- **Bureaucratic drift**: Goodhart, procedure inflation, data maximalism, tooling complexity, exception culture.
- **Capture**: economic/political/epistemic/cultural capture of institutions, standards, enforcement, and narratives.

### Scope levels
- `local` (municipal execution, frontline access, ombuds and dispute flow)
- `sector` (CH17 templates; procurement and standards; bottlenecks and E surfaces)
- `national` (caps, channel governance, anti-evasion, audit institutions, crisis rails)

### Normative requirements (RFC 2119)
- CH18 **MUST** be applicable at each level (local/sector/national) with consistent indicators and stop rules.
- Failure mode detection **MUST** be privacy-safe and aggregated; microdata publication is prohibited.

### Conformance tests (minimum)
- **LW-04 (Level coverage):** each failure mode class has indicators at local/sector/national levels (as applicable).
- **LW-05 (Privacy discipline):** detection does not require microdata publication.

<a id="b05ch18p01s03"></a>
## B05.CH18.P01.S03 — Binding: lifeworld test (B,T,N,L,R + tails), contestability, auditability, anti-evasion, and crisis rails

Failure modes are bound to concrete rails. The chapter does not define “bad vibes”; it defines breaches against measurable lifeworld
integrity and enforceability constraints.

### Binding rails (required)
- `lifeworld_test`:
  - B,T,N,L,R changes and cohort distributions,
  - tails: arrears/lockouts/wait times/cost spikes,
  - time friction: admin burden, schedule capture, dispute durations.
- `contestability`:
  - objection/appeal paths, time bounds, interim relief, no-retaliation.
- `auditability`:
  - tamper-evident logs, evidence packs, restatements, publication discipline (aggregated).
- `anti_evasion`:
  - shift taxonomy, substance-over-form, look-through, presumptions under opacity, channel governance/leakage tests.
- `crisis_rails`:
  - emergency measures that are bounded, sunset, contestable; no permanent emergency drift.

### Normative requirements (RFC 2119)
- A failure mode **MUST** be expressible as a breach in one or more binding rails; otherwise it is not actionable.
- Contestability and auditability **MUST** be treated as primary; performance without contestability is coercion risk.
- Crisis rails **MUST** be sunset and logged; emergency without sunset is capture risk.

### Conformance tests (minimum)
- **LW-06 (Rail linkage):** each failure mode class links to lifeworld/contestability/auditability/anti-evasion rails.
- **LW-07 (Log discipline):** restatements and incident logs exist and are publishable in aggregated form.
- **LW-08 (Crisis sunset):** any crisis measure has explicit sunset and renewal criteria.

<a id="b05ch18p01s04"></a>
## B05.CH18.P01.S04 — Fail-closed: when breach indicators repeat, scaling is blocked and remediation is mandatory

CH18 is FAIL-CLOSED: repeated breach indicators are treated as evidence of structural incompatibility, not as “implementation noise”.

### FAIL-CLOSED rule (binding)
- If breach indicators for any class repeat beyond threshold within a defined window:
  - **scaling is blocked**,
  - **discretionary powers are constrained** (where relevant),
  - **forensic audit is initiated**,
  - **restatement is published** (aggregated),
  - **remediation/redesign is mandatory**, and
  - **recertification** is required before scaling resumes.

### Required fields (template)
- `breach_thresholds[]` per failure mode class:
  - threshold conditions (bands allowed)
  - time window
  - escalation action set
- `scaling_block_scope`:
  - what is halted (rollout, procurement, new contracts, new channel issuance)
- `remediation_pack`:
  - attribution, rail changes (versioned), retest plan
- `recertification_rule`:
  - criteria to re-enable scaling

### Normative requirements (RFC 2119)
- Thresholds **MUST** be declared in advance; ad hoc escalation is a legitimacy hazard.
- Scaling blocks **MUST** be real (procurement stops, contract issuance stops, channel reclassification) rather than rhetorical.
- Remediation **MUST** produce a versioned change and a re-test; “training” without redesign is non-conform.

### Conformance tests (minimum)
- **LW-FC-01 (Threshold presence):** breach thresholds exist per class.
- **LW-FC-02 (Block enforceability):** a defined scope of halted actions exists and is loggable.
- **LW-FC-03 (Recertification):** re-enable criteria exist and require re-test evidence.
