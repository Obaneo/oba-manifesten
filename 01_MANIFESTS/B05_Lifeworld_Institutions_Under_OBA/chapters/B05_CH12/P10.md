# B05.CH12.P10 — Data and privacy in execution (minimalism without blindness)

This paragraph specifies data and privacy rules for local execution under OBA. Local institutions need data to decide, execute, and
audit, but data systems are a common capture and harm surface: secondary profiling, cross-domain joins, and “risk scoring” can become
coercive block power. Conversely, “privacy” can be used as an excuse for opacity and non-auditability (“blindness”). OBA therefore
requires **minimal necessary** data collection (purpose-limited to decision/execution/audit), tiered disclosure (public aggregates,
regulated micro-access, confidential PII), strict logging (decision and access logs with tamper evidence), and retention caps. Data
maximalism is treated as bureaucratic drift: collecting more data instead of improving competence and process design. Hard stops apply
when data collection expands without necessity or when data is used as a substitute for execution quality.

---

<a id="b05ch12p10s01"></a>
## B05.CH12.P10.S01 — Minimal necessary: data only for decision/execution/audit, no secondary profiling

Data collection is justified only by explicit execution needs.

### Minimal necessary rule (binding)
- Collect only data required to:
  - determine eligibility and priority under published rules,
  - execute the decision (payments, allocations, service scheduling),
  - and audit correctness and non-discrimination.
- Reuse existing data where lawful; do not re-ask users for information that the institution already holds.

### Prohibited secondary uses (binding)
- Profiling for unrelated purposes (marketing, behavioural steering, predictive policing proxies).
- Cross-domain joins that create surveillance profiles across housing/benefits/education/health beyond explicit necessity.
- Using data access as leverage (threats of denial unless additional unrelated data is provided).

### Conformance requirement (binding)
- Maintain a data-purpose register: fields collected → purpose → retention period → access tier.

<a id="b05ch12p10s02"></a>
## B05.CH12.P10.S02 — Tiered disclosure: public (aggregate), regulated (micro), confidential (PII)

OBA separates transparency from privacy risk through tiered disclosure.

### Tiers (binding)
- **Public (aggregate)**: publish metrics required for contestability and oversight (lead times, backlogs, error/appeal rates,
  enforcement volumes, commons access metrics) using privacy-safe aggregation and suppression.
- **Regulated (micro)**: authorised auditors and oversight bodies can access micro-data necessary to reproduce decisions and detect
  discrimination, under strict access controls, logging, and purpose limitation.
- **Confidential (PII)**: personally identifiable information is restricted to execution needs; access is least-privilege and
  time-bounded.

### Join safety (binding)
- Micro-level joins across datasets require explicit justification and must be performed under regulated access with minimisation and
  audit trails; “data lake” joins by default are prohibited.

---

<a id="b05ch12p10s03"></a>
## B05.CH12.P10.S03 — Logging: decision logs, access logs, tamper-evidence, retention caps

Auditability requires logs; privacy requires limits. OBA requires both.

### Logging requirements (binding)
- **Decision logs**: each decision must record rule version, parameters used, inputs, outputs, reason codes, and appeal information.
- **Access logs**: every access to confidential or regulated data is logged with actor identity, purpose code, and timestamp.
- **Tamper evidence**: logs must be append-only or otherwise tamper-evident; changes require signed releases and public summaries where
  appropriate.

### Retention caps (binding)
- Retention periods must be capped and purpose-linked; keep data no longer than necessary for execution and audit.
- Expired data must be deleted or irreversibly aggregated; “keep forever for analytics” is non-conforming.

### Publication requirement (binding)
- Publish aggregated log statistics: access volumes by role, incident counts (unauthorised access attempts), and retention compliance
  indicators (privacy-safe).

<a id="b05ch12p10s04"></a>
## B05.CH12.P10.S04 — Hard stop: data collection as a substitute for competence (bureaucratic drift)

A common failure mode is “measure more, decide less”: expanding data collection instead of fixing processes, training, and rules.

### Drift indicators (binding)
- Requests for increasing documentation without evidence of improved correctness or reduced fraud.
- Expansion of “risk scoring” and profiling tools while lead times, errors, and appeals worsen.
- Data collected “just in case” without explicit purpose and retention caps.

### Hard stop response (binding)
- Suspend non-essential data collection and revert to minimal necessary fields; require a process redesign plan (templates, training,
  tooling) to address the underlying competence gap.
- Prohibit deployment of new scoring/profiling systems without auditability, bias tests, and contestability (link to CH10/CH09 rails
  where applicable).
- Persistent drift triggers governance intervention and procurement review (fail-closed against data-maximalism as governance theatre).
