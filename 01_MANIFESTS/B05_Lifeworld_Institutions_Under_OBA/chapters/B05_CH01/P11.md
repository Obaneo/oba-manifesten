# B05.CH01.P11 — Interface with sector cases and day-in-the-life chapters

This paragraph specifies how the lifeworld layer connects to **sector cases** and “day-in-the-life” chapters without collapsing into
storytelling. The lifeworld layer is a **test interface**: sector cases exist to execute the same test logic in concrete domains
(housing/energy/care/digital), and day-in-the-life chapters exist to surface **where clamps are felt**, **what exit paths exist**, and
**which institutional interventions are responsible**—always with measurable outputs attached.

The interface is therefore standardized: common templates, consistent causal mapping, and mandatory evidence artifacts. This prevents
“case theatre” (narrative capture) and makes cases comparable across regions, time, and implementations.

---

## B05.CH01.P11.S01 — Templates: applying the same test logic to housing/energy/care/digital

Each sector case MUST implement the lifeworld logic with a shared template so that comparisons are meaningful and drift is detectable.
Sector variation is permitted only in parameter values and domain-specific observables—not in the test structure.

### Sector-case template (binding; minimum fields)
- **sector_id**: {housing, energy, care, digital, …}
- **cohort_id(s)**: affected cohorts (explicit cohort grammar)
- **clamp hypothesis**: what is clamping whom, where, and by which mechanism
- **mapping block** (required):
  - P/E/C classification references relevant to the sector case (canonical IDs)
  - B/T/N/L/R mapping to lived quantities used in the case (definition-set references)
  - ΔM channel mapping: which channel objects materially shape the lived outcome
- **measurement block**:
  - observables, proxies, method_id, uncertainty, data-minimalism notes
- **decision/audit block**:
  - decision log references, exception registers, audit triggers, remedies available

### Conformance requirements (binding)
- Cases MUST be comparable by design: same headings, same minimum fields, same output tables.
- Any case that deviates from the template MUST include an explicit deviation note and justification; unjustified deviation is treated
  as a drift indicator.

## B05.CH01.P11.S02 — Case structure: before/after, clamps, exit paths, institutional interventions, measurement outputs

Sector cases MUST be written as **before/after test executions** with explicit clamp mechanics and measurable outcomes. The case is not
“what happened to someone,” but “what changed in the clamp and why.”

### Case structure (binding; minimum sections)

**1) Baseline (before)**
- Essentials access/quality and burdens (L) for specified cohorts
- Lock-in/exit-friction state (fees, portability, switching costs)
- R/B profile effects (residual space, tail risk markers)

**2) Clamp anatomy**
- Contract structures, toll layers, choke points, block-power loci
- Where the clamp is enforced (terms, platforms, identity rails, logistics, procurement)

**3) Exit paths**
- Available exits and their frictions (technical, contractual, institutional)
- Whether exit is realistic for low-capacity cohorts (time, money, knowledge, penalties)

**4) Institutional intervention**
- Which institution acted, under which authority, with which evidence
- What remedy was applied (unbundling, public option, reclassification, procurement rails, sanctions)
- Sunset/rollback and contestability rails

**5) Measured outputs (after)**
- Published tables/indices impacted (B05.CH01.P10 outputs)
- Outcome deltas for cohorts: L, lock-in proxies, tail markers, ΔG/commons access where relevant
- Time-to-effect and durability (does the clamp reappear through substitution?)

### Conformance requirements (binding)
- Cases MUST include measurable outputs aligned to B05.CH01.P10; prose without outputs is non-conform.
- “After” without a baseline is non-conform; “baseline” without clamp anatomy is non-conform.

## B05.CH01.P11.S03 — Link to sector canvas: bottlenecks, E sources, commons option, cap compatibility, R/B effect

Each case MUST link to the sector-level analytical canvas (the stable map that prevents case-by-case reinterpretation). The canvas is
the intermediate representation between macro invariants and lived experience.

### Mandatory canvas linkages (binding)
- **Bottlenecks**: physical, contractual, informational, identity, logistical choke points
- **E sources**: where extraction is produced (take-rate, rent, fee stacks, bundling, lock-in penalties)
- **Commons option**: whether a non-extractive access regime exists (or can exist), with governance and ΔG implications
- **Cap compatibility**: interaction with W/I caps and status incentives (does intervention create new bypass routes?)
- **R/B effects**: impact on residual space, volatility, and tail outcomes for low-capacity cohorts

### Conformance requirements (binding)
- Cases MUST explicitly state whether the clamp is an E-source, a block-power locus, or both, and MUST specify the neutralisation path.
- If a case changes a parameter but leaves the bottleneck intact, it MUST be labeled as partial and treated as potentially unstable.

## B05.CH01.P11.S04 — Link to Codex: which schemas, validators, and audit packs are mandatory per case

To remain machine-auditable and anti-drift, every case MUST reference the Codex artifacts that govern data shapes, validation, and
auditing. Cases are not free-form essays; they are executable test instances.

### Mandatory Codex linkages (binding)
- **schema refs**: which data schemas are used for cohorts, essentials indices, lock-in proxies, incidents, decision logs
- **validator set**: which validators must pass for the case outputs (including join-safety and small-n suppression checks)
- **audit pack**: which audit pack is required (sampling rules, trigger thresholds, dispute flow, restatement procedures)
- **version pinning**: Codex version + definition-set ID versions used to produce outputs

### Conformance requirements (binding)
- Any case without schema + validator + audit-pack references MUST be treated as non-reproducible and therefore non-conform.
- If the Codex artifacts required for a case do not exist, the case MUST be recorded as a “missing tooling dependency” and the
  implementation MUST fail-closed until the dependency is created.
